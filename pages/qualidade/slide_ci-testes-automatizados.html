O problema que CI resolve

"Funciona na minha máquina" — todo dev já disse isso.

Branches longas

Cada dev trabalha isolado por dias ou semanas. Ao juntar o código, surgem conflitos gigantescos e bugs difíceis de rastrear.

Regressões silenciosas

Uma alteração em módulo A quebra módulo B — e ninguém percebe até o código chegar em produção, custando horas de debug urgente.

Feedback lento

Sem automação, o ciclo teste → feedback demora horas ou dias. Erros de hoje são descobertos semanas depois, quando o contexto já foi perdido.

Integração de código sem testes automáticos = confiança cega. Você só sabe que quebrou quando o usuário reclama.

O que é Continuous Integration?

CI é a prática de integrar código ao repositório principal com frequência, com validação automática a cada integração.

Origem

Conceito formalizado por Martin Fowler e popularizado pelo movimento XP (Extreme Programming) no início dos anos 2000.

Princípio central: "se integrar dói, faça com mais frequência até não doer mais."

Premissas essenciais
  • Repositório único e compartilhado (trunk/main)
  • Builds automatizados a cada push
  • Testes automatizados como parte do build
  • Build quebrado = prioridade máxima
  • Feedback em minutos, não em horas

A Pirâmide de Testes em CI

Não são todos os testes que devem rodar do mesmo jeito em CI.

Testes Unitários — rode sempre

Rápidos (segundos), isolados, cobrem a lógica de negócio. São o coração do CI. Qualquer commit deve passar por eles.

Testes de Integração — rode no merge

Validam comunicação entre módulos, banco, APIs externas. Mais lentos — ideais para rodar em PRs antes do merge.

E2E — rode periodicamente

Simulam o usuário real. Muito lentos e frágeis para rodar a cada commit. Rodam em pipelines noturnos ou antes de releases.

Anatomia de um Pipeline de CI

Um pipeline é uma sequência de jobs que validam a saúde do código.

1
Checkout & Setup

Clona o repositório, instala dependências (npm install, pip install), configura variáveis de ambiente.

2
Lint & Build

Verifica estilo de código (ESLint, Prettier), erros de compilação, tipagem (TypeScript). Falha rápido antes dos testes.

3
Testes Unitários

Executa a suite de testes. Gera relatório de cobertura. Falha se cobertura cai abaixo do threshold.

4
Testes de Integração

Sobe serviços auxiliares (banco via Docker), executa testes que cruzam fronteiras de módulo ou sistema.

5
Segurança & Qualidade

Auditoria de dependências (npm audit), análise estática de segurança, varredura de vulnerabilidades.

6
Notificação

Resultado visível no PR. Verde = pode mergear. Vermelho = bloqueia merge até o time corrigir.

GitHub Actions

A plataforma de CI/CD nativa do GitHub — grátis para repositórios públicos.

Conceitos fundamentais
  • Workflow: arquivo YAML que define o pipeline (.github/workflows/)
  • Trigger (on): evento que dispara o workflow — push, pull_request, schedule...
  • Job: conjunto de steps que roda em uma máquina virtual isolada
  • Step: comando ou action individual dentro de um job
  • Action: unidade reutilizável de código (ex: actions/checkout@v4)
Runners disponíveis
  • ubuntu-latest — Linux (mais usado, mais rápido)
  • windows-latest — Windows Server
  • macos-latest — macOS (mais lento e caro)
  • Self-hosted — sua própria máquina/servidor

Cada job roda em uma VM zerada — o ambiente é limpo a cada execução, garantindo reproducibilidade.

Workflow básico — Node.js + Jest

# .github/workflows/ci.yml name: CI on: push: branches: ["main"] pull_request: branches: ["main"] jobs: test: runs-on: ubuntu-latest steps: - name: Checkout do código uses: actions/checkout@v4 - name: Configurar Node.js uses: actions/setup-node@v4 with: node-version: "20" cache: "npm" - name: Instalar dependências run: npm ci - name: Verificar lint run: npm run lint - name: Rodar testes com cobertura run: npm test -- --coverage

Testando em múltiplas versões — Matrix Strategy

jobs: test: runs-on: ubuntu-latest strategy: matrix: node-version: [18, 20, 22] # roda 3 jobs em paralelo steps: - uses: actions/checkout@v4 - name: Node ${{ matrix.node-version }} uses: actions/setup-node@v4 with: node-version: ${{ matrix.node-version }} - run: npm ci - run: npm test deploy: needs: test # só executa se "test" passou if: github.ref == 'refs/heads/main' runs-on: ubuntu-latest steps: - run: echo "Fazendo deploy!"

needs: cria dependência entre jobs. if: condiciona execução. matrix: paraleliza em múltiplos ambientes.

Boas práticas para testes em CI

Use npm ci em vez de npm install

Instalação determinística, respeita o lockfile, mais rápida em CI onde não há node_modules em cache.

Cache de dependências

Use cache: "npm" no setup-node para evitar baixar pacotes do zero a cada execução. Economiza minutos de build.

Falhe rápido (fail-fast)

Coloque lint e build antes dos testes. Se o código nem compila, não perca tempo rodando testes.

Nunca commite segredos no YAML

Use GitHub Secrets (secrets.MINHA_CHAVE) para tokens, senhas e chaves de API. Jamais no arquivo YAML.

Evite: testes que dependem de ordem

Cada teste deve ser independente. Testes acoplados causam falhas intermitentes em CI (flaky tests).

Evite: testes que acessam internet externa

APIs externas reais tornam o CI instável. Use mocks, fixtures ou serviços locais via Docker Compose.

Atividade Prática

Vamos criar um pipeline de CI real para um projeto Node.js.

Passo a passo
  1. Faça um fork do repositório-base disponibilizado pelo professor
  2. Crie a pasta .github/workflows/ na raiz do projeto
  3. Crie o arquivo ci.yml com: checkout, setup-node (v20), npm ci, npm test
  4. Faça um push e observe o GitHub executar o workflow na aba Actions
  5. Introduza um bug intencional em um teste e faça novo push — veja o CI falhar
  6. Corrija o bug, faça push e observe o CI ficar verde novamente
Desafio extra

Adicione uma matrix strategy testando nas versões Node 18 e 20. Configure o relatório de cobertura como artifact do workflow.

Entrega

Compartilhe o link do repositório com o workflow funcionando (aba Actions com execução verde).

Recapitulando

CI = Integração contínua

Commitar frequentemente com validação automática elimina a dor de integração tardia.

Pirâmide no pipeline

Unitários sempre, integração no PR, E2E periodicamente. Velocidade é essencial em CI.

GitHub Actions

YAML declarativo, triggers flexíveis, matrix para múltiplos ambientes, secrets para segurança.
