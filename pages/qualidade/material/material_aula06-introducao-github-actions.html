Aula 06 - Testes Automatizados em CI

Material de apoio sobre Continuous Integration, GitHub Actions e a construção de um ci.yml confiável.

Este pipeline será exigido na entrega do projeto final. O repositório precisa executar testes automaticamente e ficar verde na aba Actions.

Regra para a entrega final

O projeto final deve possuir workflow de CI versionado em .github/workflows/ci.yml.

  • O pipeline deve rodar a cada push e pull_request.
  • Os testes precisam executar sem intervenção manual.
  • A execução deve aparecer com sucesso na aba Actions do GitHub.
  • Entrega com workflow quebrado ou ausente não atende ao padrão esperado.

1. O que é CI

Continuous Integration é a prática de validar automaticamente o projeto sempre que código novo entra no repositório. Em vez de descobrir problemas só no dia da apresentação, a equipe recebe feedback rápido a cada alteração.

  • Garante que o projeto continua executando após cada mudança.
  • Reduz integração manual e surpresa entre branches.
  • Cria uma evidência objetiva de qualidade para o projeto.
  • Facilita correção rápida de erros antes da entrega final.

2. O que um bom CI precisa validar

Um pipeline bom não é o mais longo. É o que valida o essencial com velocidade e previsibilidade.

Validações mínimas

  • Instalação limpa de dependências.
  • Lint ou checagem de padrão, quando existir no projeto.
  • Execução dos testes automatizados.
  • Falha imediata se algum passo quebrar.

Características desejáveis

  • Tempo de execução curto.
  • Passos determinísticos e reprodutíveis.
  • Sem depender de máquina local do aluno.
  • Saída clara para diagnosticar falhas.

3. Anatomia de um bom ci.yml

No GitHub Actions, um workflow é composto por gatilhos, jobs e steps. O arquivo deve ficar em .github/workflows/ci.yml.

  1. name: nome legível do workflow.
  2. on: define quando o pipeline roda.
  3. jobs: separa a execução em blocos lógicos.
  4. runs-on: sistema operacional usado pelo runner.
  5. steps: sequência de ações do job.

4. Exemplo recomendado para projeto Node.js

Este é um ponto de partida sólido para a maior parte dos projetos da disciplina.

name: CI

on:
  push:
    branches: ["main", "develop"]
  pull_request:
    branches: ["main"]

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout do codigo
        uses: actions/checkout@v4

      - name: Configurar Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm

      - name: Instalar dependencias
        run: npm ci

      - name: Rodar lint
        run: npm run lint --if-present

      - name: Rodar testes
        run: npm test -- --runInBand

      - name: Gerar build
        run: npm run build --if-present

5. Por que esse exemplo é bom

  • actions/checkout@v4 baixa o repositório no runner.
  • actions/setup-node@v4 define a versão do Node de forma explícita.
  • npm ci instala dependências a partir do lockfile, com mais previsibilidade que npm install.
  • --if-present evita falhas em projetos que ainda não possuem script de lint ou build.
  • O job falha automaticamente se lint, teste ou build quebrarem.

6. Boas práticas para um CI realmente útil

Seja determinístico

Use versões explícitas, lockfile commitado e comandos reproduzíveis.

Falhe cedo

Lint e testes rápidos devem rodar cedo para economizar tempo.

Não dependa da sua máquina

Se algo só funciona localmente, o pipeline está revelando um problema real do projeto.

  • Mantenha o pipeline curto e focado no que protege a entrega.
  • Use nomes claros nos steps para facilitar leitura da aba Actions.
  • Evite segredos desnecessários em workflows de teste.
  • Separe testes lentos dos testes obrigatórios de cada push, se necessário.
  • Não esconda erro com comandos como || true.

7. Erros comuns em ci.yml

Erro Problema causado Como corrigir
Usar npm install sem necessidade Instalação menos previsível Preferir npm ci
Rodar apenas em main Erro só aparece tarde demais Rodar também em pull_request
Depender de banco externo manual Pipeline instável ou impossível de reproduzir Subir serviços no workflow ou usar estratégia de teste apropriada
Teste que depende de internet real Falhas intermitentes Isolar integração, usar VCR ou ambiente controlado
Não versionar lockfile Resultado diferente em cada execução Commitar package-lock.json

8. E quando o projeto usa banco, API ou containers?

Projeto real quase nunca é só uma função isolada. Se os testes dependem de infraestrutura, isso precisa estar explícito no pipeline.

  • Banco de dados: subir serviço com services: no workflow ou usar Testcontainers.
  • APIs externas: evitar chamadas reais e usar abordagem controlada, como VCR, fixtures ou ambiente local.
  • Docker: se a aplicação já sobe por container, o CI pode usar docker compose para validar integração.
  • Variáveis de ambiente: documentar no repositório e configurar secrets apenas quando forem realmente necessários.

9. Exemplo com serviço de banco no GitHub Actions

name: CI

on:
  push:
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest

    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_USER: app
          POSTGRES_PASSWORD: app
          POSTGRES_DB: app_test
        ports:
          - 5432:5432
        options: >-
          --health-cmd="pg_isready -U app -d app_test"
          --health-interval=10s
          --health-timeout=5s
          --health-retries=5

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm

      - run: npm ci

      - name: Rodar testes de integracao
        env:
          DATABASE_URL: postgres://app:app@localhost:5432/app_test
        run: npm test

10. Critérios mínimos para o projeto final

  • O repositório deve conter o arquivo .github/workflows/ci.yml.
  • O workflow deve executar automaticamente no GitHub.
  • O projeto precisa ter scripts funcionais no package.json ou equivalente.
  • O grupo deve conseguir mostrar uma execução verde recente na entrega.
  • Se houver testes de integração, a infraestrutura necessária deve subir no pipeline.

11. Checklist antes de entregar

  1. Fazer clone limpo do projeto e confirmar que ele não depende de arquivos locais escondidos.
  2. Revisar se o workflow está em .github/workflows/ci.yml.
  3. Conferir se os scripts usados no workflow existem de fato.
  4. Fazer um push pequeno e verificar o resultado na aba Actions.
  5. Corrigir qualquer falha antes da entrega, em vez de explicar verbalmente que "na sua máquina funciona".

12. Exercícios de fixação

  1. Explique por que npm ci é preferível a npm install em CI.
  2. Monte um ci.yml para o seu projeto atual e identifique quais scripts ele exige.
  3. Liste três motivos que fariam um workflow passar localmente e falhar no GitHub Actions.
  4. Adapte o pipeline para subir o banco que seu projeto usa.
  5. Defina o que seu grupo precisa mostrar no dia da entrega para comprovar que o CI está funcionando.
