Aula 08 — VCR, Chamadas de API Seguras e TestContainers

Testes automatizados que dependem de APIs externas são frágeis por natureza: a rede pode falhar, a API pode mudar, o rate limit pode estourar. Esta aula apresenta duas estratégias complementares — VCR para chamadas HTTP e TestContainers para serviços de infraestrutura — e explica como guardar credenciais em cada ambiente.

1. O problema dos testes dependentes de rede

Testes que chamam APIs reais são chamados de flaky quando falham por razões externas ao código: servidor fora do ar, latência alta, mudança não planejada no contrato da API. No CI, isso é ainda pior porque o runner pode não ter acesso à internet.

Regra prática: testes automatizados precisam ser determinísticos — a mesma entrada produz o mesmo resultado independentemente de horário, rede ou estado externo.

2. VCR — Video Cassette Recorder para HTTP

O padrão VCR, inspirado no videocassete, funciona em dois modos:

  • Record: o teste faz a chamada real uma vez e salva a resposta num arquivo chamado cassete (JSON ou YAML).
  • Replay: nas execuções seguintes, a biblioteca intercepta a chamada e devolve o cassete salvo sem tocar na rede.

O resultado é um teste rápido, offline e idêntico a cada execução.

2.1 WireMock — stub programático com JUnit 5

import com.github.tomakehurst.wiremock.junit5.WireMockTest;
import static com.github.tomakehurst.wiremock.client.WireMock.*;
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.*;

@WireMockTest(httpPort = 8089)
class WeatherClientTest {

    @Test
    void retornaTemperaturaDeSP() throws Exception {
        // "cassete" — define a resposta simulada
        stubFor(get("/current?city=SP")
            .willReturn(okJson(
                "{\"temp\": 28, \"desc\": \"Ensolarado\"}"
            )));

        WeatherClient client =
            new WeatherClient("http://localhost:8089");

        WeatherData data = client.fetchWeather("SP");
        assertEquals(28, data.getTemp());
    }
}

2.2 WireMock — stub declarativo (arquivo JSON)

// src/test/resources/mappings/weather-sp.json
// WireMock carrega automaticamente no @WireMockTest
{
  "request": {
    "method": "GET",
    "url": "/current?city=SP"
  },
  "response": {
    "status": 200,
    "headers": { "Content-Type": "application/json" },
    "bodyFileName": "weather-sp-response.json"
  }
}

// src/test/resources/__files/weather-sp-response.json
{ "temp": 28, "desc": "Ensolarado" }
WireMock é o padrão de mercado para interceptação HTTP em Java. Dependency Maven: com.github.tomakehurst:wiremock:3.x (scope test). Para Spring Boot, existe também o starter org.springframework.cloud:spring-cloud-contract-wiremock.

3. Sanitização do cassete — nunca exponha secrets

O cassete grava tudo que foi enviado na requisição, incluindo cabeçalhos de autenticação. Se você commitar esse arquivo, seu token vaza publicamente. 

// Mapping PERIGOSO — nunca commitar com token real
// mappings/get-user.json
{
  "request": {
    "method": "GET",
    "url": "/api/users/1",
    "headers": {
      "Authorization": {
        "equalTo": "Bearer sk-prod-SECRET123"  // PERIGO!
      }
    }
  }
}

// Mapping SEGURO — usa regex, sem valor real
{
  "request": {
    "method": "GET",
    "url": "/api/users/1",
    "headers": {
      "Authorization": {
        "matches": "Bearer .*"  // aceita qualquer token
      }
    }
  },
  "response": {
    "status": 200,
    "bodyFileName": "user-1-response.json"
  }
}
Boa prática: adicione src/test/resources/mappings/ ao .gitignore enquanto gravar respostas reais. Só commite após confirmar que nenhum header ou body contém credencial.

4. Onde guardar secrets em cada ambiente

Ambiente Onde guardar Como acessar no código
Desenvolvimento local .env (no .gitignore) process.env.API_KEY via dotenv
CI/CD (GitHub Actions) Settings → Secrets and Variables ${{ secrets.API_KEY }} no workflow
Produção AWS Secrets Manager / Azure Key Vault / Vault SDK específico ou variável de ambiente injetada 
# application.properties (local — NUNCA commitar, no .gitignore)
api.key=${API_KEY}
spring.datasource.url=${DB_URL:jdbc:postgresql://localhost:5432/dev}

// Spring Boot — injeta via @Value
@Value("${api.key}")
private String apiKey;

// Sem Spring — via System.getenv()
String apiKey = System.getenv("API_KEY");
HttpRequest request = HttpRequest.newBuilder()
    .uri(URI.create(url))
    .header("Authorization", "Bearer " + apiKey)
    .build();

5. TestContainers — serviço real, sem infraestrutura permanente

TestContainers é uma biblioteca que gerencia containers Docker durante a execução dos testes. Em vez de mockar o banco de dados, você sobe um Postgres real, roda as migrations, executa os testes e destrói o container ao final.

Por que isso importa?

  • Valida o comportamento real do driver de banco (tipos, constraints, índices).
  • Garante que as migrations funcionam na ordem correta.
  • Elimina a discrepância entre mock e produção (o mock passa, o prod falha).

5.1 Setup com JUnit 5 + @Testcontainers

import org.testcontainers.containers.PostgreSQLContainer;
import org.testcontainers.junit.jupiter.Container;
import org.testcontainers.junit.jupiter.Testcontainers;
import org.junit.jupiter.api.*;
import static org.junit.jupiter.api.Assertions.*;

@Testcontainers
class UserRepositoryTest {

    @Container
    static PostgreSQLContainer<?> db =
        new PostgreSQLContainer<>("postgres:16")
            .withDatabaseName("testdb")
            .withUsername("test")
            .withPassword("test");

    @BeforeAll
    static void setUp() {
        // roda Flyway ou Liquibase com a URL do container
        runMigrations(db.getJdbcUrl(),
            db.getUsername(), db.getPassword());
    }
}

5.2 Teste usando o banco real

@Test
void salvaEBuscaUsuario() {
    UserRepository repo = new UserRepository(
        db.getJdbcUrl(), db.getUsername(), db.getPassword());

    repo.save(new User("Ana", "ana@example.com"));

    User found = repo.findByEmail("ana@example.com");
    assertEquals("Ana", found.getName());
}
// @Container static → container sobe 1x por classe
// e é destruído automaticamente pelo JUnit ao final
Maven: org.testcontainers:postgresql:1.20.x + org.testcontainers:junit-jupiter:1.20.x (scope test). O runner ubuntu-latest do GitHub Actions já inclui Docker — nenhuma configuração extra necessária.

6. VCR vs TestContainers — quando usar cada um

Critério VCR / HTTP Mock TestContainers
Alvo APIs HTTP externas (REST, GraphQL) Banco, fila, cache (Postgres, Redis, Kafka…)
Velocidade Muito rápido — sem Docker Mais lento — pull + start do container
Fidelidade Alta para o payload HTTP Alta — serviço real rodando
Requer Docker Não Sim
Manutenção Re-gravar cassete ao mudar o contrato Baixa — imagem oficial segue a spec
Use VCR/msw na suite de testes de unidade (rápidos, rodados em todo PR). Use TestContainers na suite de integração (rodada pelo menos em merge para main).

7. Pipeline completa no GitHub Actions

## .github/workflows/quality.yml
jobs:
  unit:                         # rápido — sem Docker
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { java-version: '21', distribution: temurin, cache: maven }
      - run: mvn test -Dtest="**/*UnitTest"
      # WireMock intercepta as chamadas HTTP — sem rede real

  integration:                  # mais lento — com Docker
    runs-on: ubuntu-latest      # ubuntu-latest já tem Docker instalado
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { java-version: '21', distribution: temurin, cache: maven }
      - run: mvn test -Dtest="**/*IntegrationTest"
      # @Testcontainers sobe Postgres/Redis automaticamente

  sonar:
    needs: [unit, integration]
    steps:
      - uses: SonarSource/sonarcloud-github-action@v2

8. Anti-patterns para evitar

  • Cassete com secret: sempre sanitize antes de commitar.
  • Cassete eterno: se a API mudou o contrato, o teste passa e a prod falha. Programe re-gravações periódicas.
  • TestContainer em teste de unidade: Docker em unit test é desproporcional e torna o feedback lento.
  • Container compartilhado entre testes: estado residual causa flakiness. Limpe as tabelas no afterEach ou suba um container por suite.
  • Hard-code de credencial no código: mesmo em teste, use variáveis de ambiente.

9. Exercícios de fixação

  1. Adicione a dependência wiremock ao pom.xml. Crie um teste anotado com @WireMockTest que intercepta uma chamada HTTP externa feita pelo seu projeto e valide dois cenários (sucesso e erro 404).
  2. Identifique uma chamada HTTP no projeto que usa um token hard-coded. Mova-o para application.properties lendo de variável de ambiente e adapte o workflow do GitHub Actions para injetar o secret via secrets.API_KEY.
  3. Adicione org.testcontainers:postgresql ao pom.xml. Escreva um teste de integração anotado com @Testcontainers que insere e busca um registro no PostgreSQL real.
  4. Compare o tempo de execução dos testes unitários (WireMock) vs integração (TestContainers) no seu projeto e documente os resultados.
  5. Crie um mapping WireMock em JSON para um endpoint que requer Authorization. Use "matches": "Bearer .*" para não gravar o token real e explique por que essa abordagem é segura.
