1) Introdução aos Testes de Software

Testar software é validar se o sistema atende aos requisitos e se se comporta como esperado em diferentes cenários.

Na aula, usamos duas visões complementares:

  • Caixa Branca: observa lógica interna, métodos, condições e caminhos.
  • Caixa Preta: observa apenas entradas e saídas visíveis ao usuário.

Por que isso importa na prática?

Sem testes, o time descobre defeitos tarde demais: em homologação, produção ou com o cliente. Quanto mais tarde o defeito é encontrado, maior é o custo para corrigir.

Com testes bem planejados, você cria uma rede de segurança para evoluir o sistema sem medo de quebrar funcionalidades já prontas.

Resumo de estratégia: caixa branca garante a saúde da lógica interna; caixa preta garante que o usuário recebe o comportamento esperado.

2) Teste Caixa Branca (White-Box)

Ideia central: o testador conhece o código-fonte e usa esse conhecimento para escolher cenários de teste.

Objetivos principais

  • Verificar caminhos de execução (if/else, loops, branches).
  • Testar a lógica interna e estruturas de dados.
  • Aumentar cobertura de código com critério (não apenas porcentagem).
  • Detectar defeitos cedo, no nível de unidade e integração.

Como pensar ao criar um teste de caixa branca

  1. Mapeie a regra de negócio e os caminhos possíveis (sucesso, erro, borda).
  2. Escolha entradas que forcem cada caminho a ser executado.
  3. Valide o resultado e, quando fizer sentido, o efeito colateral (log, persistência, exceção).
  4. Mantenha o teste simples e com um único motivo de falha por cenário.

3) Exemplo 1: Teste de Unidade com JUnit

Trecho alinhado ao slide: validação do método somar(a, b).

@SpringBootTest
public class CalculadoraTest {

    @Autowired
    private Calculadora calculadora;

    @Test
    void testarSoma() {
        // Arrange - conhecemos a estrutura interna
        int a = 5, b = 3;

        // Act - executamos o método
        int resultado = calculadora.somar(a, b);

        // Assert - validamos o resultado esperado
        assertEquals(8, resultado);
    }
}

Explicação linha a linha

  1. @SpringBootTest: sobe o contexto do Spring para permitir injeção de dependências no teste.
  2. public class CalculadoraTest: classe que agrupa os testes da calculadora.
  3. @Autowired: injeta uma instância real de Calculadora.
  4. private Calculadora calculadora: objeto que será testado.
  5. @Test: marca o método como caso de teste executável pelo JUnit.
  6. void testarSoma(): nome do cenário; descreve o que está sendo validado.
  7. int a = 5, b = 3;: dados de entrada do cenário (fase Arrange).
  8. int resultado = calculadora.somar(a, b);: execução da regra de negócio (fase Act).
  9. assertEquals(8, resultado);: verificação do comportamento esperado (fase Assert).

Leitura didática do fluxo AAA (Arrange, Act, Assert)

  • Arrange: você prepara o estado inicial e as entradas do teste.
  • Act: executa apenas a ação principal que quer validar.
  • Assert: confirma se o resultado observado bate com o comportamento esperado.

4) Exemplo 2: Testes Paramétricos com @CsvSource

Aqui, o mesmo teste roda várias vezes mudando apenas os parâmetros de entrada.

@ParameterizedTest
@CsvSource({
    "2, 3, 5",
    "10, 20, 30",
    "-5, 5, 0",
    "0, 0, 0",
    "100, 200, 300"
})
void testarSomaComMultiplosValores(int a, int b, int esperado) {
    int resultado = calculadora.somar(a, b);
    assertEquals(esperado, resultado);
}

Explicação linha a linha

  1. @ParameterizedTest: indica que o método será executado múltiplas vezes.
  2. @CsvSource({...}): fornece conjuntos de dados no formato CSV.
  3. Cada string como "2, 3, 5" representa a, b e esperado.
  4. void testarSomaComMultiplosValores(...): assinatura compatível com os três campos do CSV.
  5. int resultado = calculadora.somar(a, b);: execução repetida para cada linha.
  6. assertEquals(esperado, resultado);: valida o resultado correspondente ao conjunto atual.

Vantagem prática: menos duplicação e mais cobertura em menos código.

Interpretação pedagógica: esse formato ajuda a ensinar o aluno a pensar em classes de equivalência e valores de fronteira sem copiar e colar vários métodos de teste.

5) Exemplo 3: @CsvSource para validação de usuário

Esse caso testa regras de negócio: formato de e-mail, senha e campos vazios.

@ParameterizedTest
@CsvSource({
    "usuario@email.com, Senha123!, true",
    "email-invalido, Senha123!, false",
    "usuario@email.com, 123, false",
    ", Senha123!, false",
    "usuario@email.com, , false"
})
void testarValidacaoUsuario(String email, String senha, boolean esperado) {
    boolean valido = validador.validarUsuario(email, senha);
    assertEquals(esperado, valido);
}

Explicação linha a linha

  1. Primeira linha CSV: cenário válido completo, retorno esperado true.
  2. Segunda linha: e-mail inválido deve reprovar (false).
  3. Terceira linha: senha fraca deve reprovar.
  4. Quarta linha: e-mail vazio deve reprovar.
  5. Quinta linha: senha vazia deve reprovar.
  6. validarUsuario(email, senha): executa a regra interna da aplicação.
  7. assertEquals(esperado, valido): compara o resultado obtido com o esperado para cada cenário.

Por que esse caso é valioso em avaliação

  • Demonstra domínio de regra de negócio, não apenas sintaxe de framework.
  • Mostra cobertura de cenários inválidos, que costumam ser os mais esquecidos.
  • Treina escrita de teste orientada a comportamento esperado.

6) Teste Caixa Preta (Black-Box)

Ideia central: validar comportamento externo sem depender de como o código foi implementado.

Objetivos principais

  • Verificar se requisitos funcionais foram atendidos.
  • Testar entradas e saídas com foco no valor para o usuário.
  • Cobrir cenários de uso real (fluxos felizes e erros).
  • Apoiar testes de sistema, aceitação e E2E.

Mentalidade de caixa preta

Aqui o teste não se preocupa se a implementação usa classe A ou B, nem qual algoritmo foi escolhido. O foco é: dado um input, o usuário recebeu o output correto?

Essa visão aproxima o teste dos requisitos do produto e da linguagem do negócio.

7) Exemplo funcional: fluxo de login

Visão do usuário (sem olhar código interno):

  1. Usuário informa e-mail e senha.
  2. Clica no botão Entrar.
  3. Sistema redireciona para dashboard, ou exibe erro/validação.

Critérios de aceite usados nos slides

  • Login válido -> dashboard.
  • Login inválido -> mensagem de erro.
  • Campos vazios -> mensagem de validação.

Como transformar isso em casos de teste

  1. Escreva pré-condição (usuário cadastrado, sistema no ar, rota disponível).
  2. Descreva passos de execução (preencher campos, clicar em entrar).
  3. Defina resultado esperado de forma objetiva (URL, mensagem, status visual).
  4. Documente dados de teste (credencial válida, inválida, vazia).

8) Exemplo 4: Teste E2E com Selenium

Teste de ponta a ponta simulando um usuário real no navegador.

@SpringBootTest(webEnvironment = WebEnvironment.RANDOM_PORT)
@ExtendWith(SeleniumExtension.class)
public class LoginE2ETest {

    @Autowired
    private WebDriver webDriver;

    @Test
    void testarFluxoLoginCompleto() {
        webDriver.get("/login");

        webDriver.findElement(By.id("email")).sendKeys("user@email.com");
        webDriver.findElement(By.id("senha")).sendKeys("Senha123!");
        webDriver.findElement(By.id("btn-login")).click();

        assertTrue(webDriver.getCurrentUrl().contains("/dashboard"));
    }
}

Explicação linha a linha

  1. @SpringBootTest(...RANDOM_PORT): sobe a aplicação para teste web real.
  2. @ExtendWith(SeleniumExtension.class): ativa suporte/configuração de Selenium.
  3. private WebDriver webDriver: driver que controla o navegador.
  4. webDriver.get("/login"): abre a tela de login.
  5. findElement(By.id("email"))...: preenche o campo de e-mail.
  6. findElement(By.id("senha"))...: preenche a senha.
  7. findElement(By.id("btn-login")).click(): executa a ação do usuário.
  8. assertTrue(...contains("/dashboard")): valida o resultado final visível.

Observações importantes para não gerar falso positivo

  • Espere elementos carregarem antes de interagir (wait explícito/implícito).
  • Evite validar só URL; valide também texto ou elemento da dashboard.
  • Use dados de teste controlados para o ambiente de aula/laboratório.

9) UML de Sequência: como interpretar os fluxos

Fluxo Caixa Branca: mostra chamadas internas entre componentes (Teste -> Calculadora -> Validador -> Repositório).

Esse fluxo ajuda a decidir onde criar testes de unidade e integração, além de visualizar dependências internas.

Fluxo Caixa Preta: mostra interação externa (Usuário -> Interface -> Sistema -> Banco) até o resultado final.

Esse fluxo orienta critérios de aceite e cenários E2E baseados em comportamento observável.

Como usar os diagramas para planejar testes

  • Cada seta pode virar um ponto de verificação de teste.
  • Mensagens de retorno indicam expectativas que podem ser assertadas.
  • Pontos de decisão (sucesso/erro) sugerem cenários alternativos.

10) Comparação final, pirâmide e boas práticas

Característica Caixa Branca Caixa Preta
Conhecimento do código Necessário Não necessário
Foco Estrutura e lógica interna Requisitos e comportamento
Níveis comuns Unidade e integração Sistema, aceitação e E2E
Exemplos da aula @ParameterizedTest / @CsvSource Selenium / Cypress

Pirâmide de testes (resumo da aula):

  • Base: muitos testes de unidade (rápidos e baratos).
  • Meio: quantidade moderada de integração.
  • Topo: poucos testes E2E (mais lentos e caros).

Boas práticas principais

  • Caixa branca: testes isolados, descritivos e com casos de exceção.
  • Caixa preta: cenários reais, requisitos claros e validação de feedback ao usuário.
  • Combine as duas abordagens: elas se complementam.
