Trabalho 2 · Sistema com banco, API e ViaCEP

O mesmo repositório do Trabalho 1 vira um sistema com PostgreSQL, API HTTP, endereço pela ViaCEP, cenários BDD e teste de carga.

IndividualPostgreSQL · Express · ViaCEPContinua o Trabalho 1Entrega na semana 17

Objetivo

Evoluir o núcleo de regras do Trabalho 1 para um sistema que grava dados num banco relacional, expõe uma API HTTP e cadastra alunos e professores com endereço completado pela ViaCEP. As regras do Trabalho 1 continuam valendo e os testes dele continuam passando.

O enunciado é publicado na semana 11, durante as provas orais do Trabalho 1. As Aulas 10, 11 e 12 trazem as técnicas na ordem em que o trabalho precisa delas.

Modelagem relacional

  • DER em docs/der.md (pode ser Mermaid) com aluno, professor, endereço, turma, matrícula, sala, material, reserva e reserva_material.
  • Modelo na terceira forma normal, com justificativa escrita de qualquer desnormalização.
  • Restrições no banco: chaves estrangeiras, unique em e-mail, check em término posterior ao início e capacidade positiva.
  • Esquema versionado em migrations/NNN_descricao.sql, aplicado por npm run db:migrar; o banco sobe do zero só com as migrações.
  • Opcional, vale bônus de 0,5: impedir sobreposição no próprio banco com EXCLUDE USING gist e tstzrange.

Comandos que precisam funcionar

npm ci
npm run lint
npm test           # unidade e API, sem internet e sem banco
npm run test:int   # integração com PostgreSQL via Testcontainers
npm run bdd        # cucumber-js
npm run carga      # k6 run carga/reservas.js (com a API rodando)

A prova oral confirma a autoria. A parte do trabalho que o aluno não consegue explicar ou modificar na hora não é considerada na nota.

  • Repositório privado, inexistente ou sem a tag trabalho-2 na data da entrega: trabalho não avaliado.
  • Teste da suíte padrão que chama a ViaCEP de verdade: a dimensão de dublês fica limitada à metade.
  • Segredo no histórico: desconto de 2 pontos, além de revogar a chave.

Entrega e prova oral

  • A entrega é feita no formulário de entrega (botão "Entregar" no card da semana 17, 26/04 a 30/04), com o nome completo e o link do repositório público organizacao-recursos.
  • Antes de enviar, crie a tag do commit entregue: git tag trabalho-2 && git push origin trabalho-2. A correção é feita sobre essa tag; commits posteriores não entram na nota do Trabalho 2.
  • O repositório precisa estar público na data da entrega. O formulário confere isso antes de registrar o envio.
  • A prova oral acontece nas semanas 18, 19 e 20 (03/05 a 21/05), individualmente, sobre o repositório entregue. As orientações estão na página Prova oral.
  • A correção chega como issues no seu repositório. Responda cada uma com um commit que cite a issue e tenha Closes #N no corpo.
