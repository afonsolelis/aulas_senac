O que é teste de unidade

A regra "no máximo 3 empréstimos ativos" mora numa função. Um teste de unidade chama essa função com dados montados na memória e confere o resultado, em milissegundos.

É teste de unidade

  • Chama emprestar(aluno, livro, hoje) com objetos literais.
  • Roda sem banco, sem rede, sem arquivo e sem depender do dia.
  • Falha por um único motivo, que o nome do teste anuncia.
  • Roda em qualquer ordem e quantas vezes for preciso, com o mesmo resultado.

Não é teste de unidade

  • Abre conexão com o PostgreSQL: teste de integração (Aula 10).
  • Chama a ViaCEP de verdade: depende da rede (Aula 11 usa dublês).
  • Sobe a API e faz requisição HTTP: teste de API, com supertest.
  • Usa new Date() sem argumento: passa hoje e falha daqui a um mês.

Conceito

O ciclo red, green e refactor

ObjetivoPedir ao opencode o primeiro teste com node:test e conferir o que ele gerou.
Faça1. "Preparar o ambiente".
2. "opencode: gerar o teste" e leia o arquivo criado.
3. "Conferir": git status e npm test.
4. "Ver uma falha", com o prazo trocado para 13 dias.
ObserveO rastro ▸ read, ▸ write, ▸ bash mostra o que o agente tocou, e ele pede permissão antes de rodar comando. Na falha, o Node mostra + actual, - expected e a linha.
ConclusãoO agente escreve; a etapa de qualidade é a sua revisão: ler o teste, ver que só ele mudou e provar que ele falha quando a regra quebra.

O que o node:test oferece

RecursoPara que serveExemplo
describe, it, testAgrupar e declarar testes (it e test são a mesma função)it('recusa livro reservado', () => {...})
assert.equalIgualdade estrita de valores primitivosassert.equal(multa, 450)
assert.deepEqualIgualdade estrutural de objetos e listasassert.deepEqual(ids, ['l1', 'l2'])
assert.throwsFunção síncrona que deve lançar erroassert.throws(() => emprestar(...), /multa/)
assert.rejectsPromessa que deve ser rejeitada (use com await)await assert.rejects(registrar(...))
before, beforeEachPreparar dados uma vez ou antes de cada testebeforeEach(() => { aluno = {...} })
it.skip, it.todoPular um teste ou registrar um que ainda falta escreverit.todo('renova uma vez')
--watchReexecutar a cada arquivo salvonode --test --watch
--test-name-patternRodar só os testes cujo nome casa com o padrãonode --test --test-name-pattern="reserva"

Importe sempre node:assert/strict: nele, equal compara com === e deepEqual também confere os tipos.

ObjetivoUsar as asserções e os hooks que o trabalho vai exigir.
Faça1. "opencode: gerar os testes" com o prompt que lista cada recurso.
2. Leia o arquivo: beforeEach, deepEqual, throws, rejects, skip, todo.
3. Rode a conferência, o filtro por nome e o modo watch.
ObserveO beforeEach recria o aluno e o livro antes de cada teste, então o teste da reserva não contamina o seguinte. skip e todo aparecem no resumo sem reprovar a execução.
ConclusãoNa revisão, procure o await antes de assert.rejects: sem ele o teste passa sempre. --test-name-pattern e --watch deixam a conferência rápida.
ObjetivoFazer um ciclo completo de TDD na regra da multa, com um commit por passo.
FaçaAlterne pedido e conferência, nesta ordem:
1. Pedir só o teste; 2. conferir o red e commitar.
3. Pedir o green; 4. conferir e commitar.
5. Pedir o refactor; 6. conferir, commitar e ver o git log.
ObserveQuem conduz o ciclo é você: cada prompt pede um passo e manda parar. No red, confira que a falha é 0 !== 450, uma asserção; no green, que o git diff não mexeu no teste.
ConclusãoA revisão entre um passo e outro é a etapa de qualidade. O commit test(...) guarda só o teste, o feat(...) só o código e o refactor(...) só a arrumação. O teto de 3000 centavos é o próximo ciclo.

Datas: o relógio entra como parâmetro

Um teste que lê o relógio do sistema muda de resultado conforme o dia em que roda. A regra de negócio recebe a data; só a borda do sistema lê o relógio.

1. hoje como parâmetro

export function estaAtrasado(emprestimo, hoje) {
  return hoje > emprestimo.previsto;
}

O teste passa a data que quiser: um dia antes, no dia, um dia depois. É a primeira opção, porque não exige ferramenta nenhuma.

2. mock.timers na borda

it('usa o relógio do sistema', (t) => {
  t.mock.timers.enable({
    apis: ['Date'],
    now: new Date('2027-03-10T12:00:00Z')
  });
  // new Date() devolve 10/03/2027 aqui dentro
});

Para o pedaço que precisa chamar new Date(). Com t.mock, o relógio volta ao normal quando o teste termina.

ObjetivoVer um teste que depende do dia falhar e corrigi-lo com relógio injetado.
Faça1. "Hoje, 22/02": passa.
2. "O mesmo teste em 10/03": falha sem ninguém mexer no código.
3. Peça a correção ao opencode e releia os dois arquivos.
4. Confira com grep e npm test, depois filtre pelo relógio.
ObserveestaAtrasado recebe hoje; só registrarAtraso lê o relógio, e o teste dela fixa a data com t.mock.timers.
ConclusãoO grep por new Date() nos testes é uma revisão que você faz em segundos e que pega o erro mais comum dos testes gerados.

Padrão AAA e nomes de teste

Arrange, Act, Assert

it('recusa quando o aluno tem multa pendente', () => {
  const aluno = { id: 'a1', ativos: [], multaPendente: 450 };

  const tentar = () => emprestar(aluno, livro, hoje);

  assert.throws(tentar, /multa pendente/);
});

Montar os dados, executar uma ação, conferir o resultado. Uma linha em branco separa os três blocos; um teste tem uma única ação.

Nome com condição e resultado

VagoDescreve a regra
teste 1recusa quando o aluno já tem 3 empréstimos ativos
multa oklimita a multa a 3000 centavos
reservaaceita livro reservado pelo próprio aluno

Quando o teste falha no CI, o nome é a primeira coisa que aparece. Ele precisa dizer qual regra quebrou sem que alguém abra o arquivo.

ObjetivoComparar a saída de testes com nomes vagos e com nomes que descrevem a regra, e separar unidade de integração.
Faça1. "Nomes vagos": tente dizer qual regra quebrou.
2. Peça a revisão ao opencode e leia a proposta antes de aceitar.
3. Confira o diff e rode os testes de unidade.
4. Rode "Teste que fala com o banco".
ObserveA mesma falha fica legível só na segunda saída. O teste da pasta integracao/ demora 1,5 s e cai com ECONNREFUSED: ele depende de um PostgreSQL rodando.
ConclusãoPedir a lista antes de gravar deixa a decisão com você; confira que nenhuma asserção mudou. O que precisa de banco fica em test/integracao/ e ganha Testcontainers na Aula 10.

TDD no seu organizacao-recursos

Como trabalhar com o agente

  1. Uma branch curta por regra: feat/intervalo, feat/reserva.
  2. O prompt manda o opencode parar ao fim de cada passo.
  3. Você lê a saída do npm test antes de commitar.
  4. Commit por passo: test(...), feat(...), refactor(...).

Regras do domínio

  • Dois intervalos que só se encostam não se sobrepõem.
  • Sala não aceita reserva com horário sobreposto.
  • Turma não passa da capacidade da sala.
  • Professor não está em duas aulas ao mesmo tempo.
  • Material indisponível ou já reservado não sai.
Se o agente escrever o teste e o código no mesmo passo, recuse e peça de novo só o teste. Sem ver o vermelho, não há como saber se o teste testa alguma coisa.
Prompt 1 de 330 min

node:test e a função de sobreposição

Estamos no repositório organizacao-recursos, em JavaScript puro com ES modules e sem TypeScript. Crie a branch feat/intervalo. Garanta que o package.json tenha "type": "module" e o script "test": "node --test", sem nenhuma dependência de teste: use só node:test e node:assert/strict. Vamos implementar em TDD a função sobrepoe(a, b) em src/intervalo.js, que recebe dois intervalos { inicio, fim } com objetos Date e responde true quando eles se sobrepõem; um intervalo que termina exatamente quando o outro começa não se sobrepõe. Trabalhe em ciclos e pare ao fim de cada passo: 1) escreva um único teste novo em test/unidade/intervalo.test.js, rode npm test e me mostre a falha; 2) escreva o código mínimo para passar, rode npm test e mostre a saída verde; 3) proponha uma refatoração, se houver, e rode npm test de novo. Use o padrão Arrange, Act, Assert e nomes de teste que digam a condição e o resultado esperado. Não escreva o próximo teste antes de eu pedir.

Antes de aceitar: o vermelho tem que ser um AssertionError, não um erro de import. Commit por passo: test(intervalo), feat(intervalo), refactor(intervalo).
Prompt 2 de 335 min

Regras de conflito da reserva em TDD

Na branch feat/reserva, crie em TDD a função reservar(reservas, pedido, recursos) em src/reserva.js. O pedido tem { salaId, professorId, materiais, inicio, fim, alunos }; recursos traz as salas com capacidade e os materiais com disponibilidade. Implemente as regras uma por ciclo, nesta ordem: 1) recusa se a sala já tem reserva com intervalo sobreposto; 2) recusa se o número de alunos passa da capacidade da sala; 3) recusa se o professor já está em outra aula no mesmo horário, em qualquer sala; 4) recusa se algum material pedido está indisponível ou já reservado no horário. Recusa é um erro lançado com mensagem que diga a regra violada; sucesso devolve a reserva criada. Reaproveite sobrepoe de src/intervalo.js. Para cada regra escreva primeiro o teste que falha, depois o código mínimo, depois refatore, e pare ao fim de cada passo para eu commitar. Inclua o caso de fronteira de cada regra, como uma reserva que começa exatamente quando a outra termina e uma turma com o número exato da capacidade. Use assert.throws com a mensagem esperada. Nada de banco, rede ou arquivo nos testes.

Antes de aceitar: cada regra tem um teste que recusa e um que aceita no limite. Se o agente juntou duas regras no mesmo passo, peça para separar.
Prompt 3 de 320 min

Relógio injetado e revisão dos testes

Na branch feat/reserva-passado, acrescente em src/reserva.js a regra de que não se reserva no passado. A função reservar passa a receber um quarto parâmetro, agora, do tipo Date, e recusa pedidos cujo inicio seja anterior a agora. Faça em TDD, com testes que passam uma data fixa e não dependem do dia em que rodam. Se algum código precisar ler o relógio do sistema, isole essa leitura numa função pequena e teste essa função com t.mock.timers.enable({ apis: ['Date'], now: new Date('2027-02-24T19:00:00Z') }). Depois revise todos os arquivos de teste: renomeie testes cujo nome não diga condição e resultado, separe Arrange, Act e Assert com uma linha em branco e aponte qualquer teste que dependa de banco, rede, arquivo ou da data atual. Mostre a lista de mudanças antes de aplicar.

Antes de aceitar: rode node --test --test-name-pattern="passado" e procure new Date() sem argumento dentro de test/.
Entregável da Aula 04

src/intervalo.js e src/reserva.js com testes em test/unidade/, construídos em TDD e integrados na main com --ff-only.

O que confiro na mesa

  • O git log --oneline mostra o trio test, feat, refactor em cada regra.
  • Abro um commit test(...) com git show e ele só tem teste.
  • npm test fica verde e nenhum teste usa new Date() sem argumento.
  • Leio os nomes na saída e entendo cada regra sem abrir o código.
