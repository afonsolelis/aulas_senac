Como a disciplina funciona

Tudo individual

Não há grupos. Cada aluno tem o próprio repositório, o próprio Codespace e responde pelo próprio código na prova oral.

Tudo no GitHub

A entrega é o link do repositório público. A correção e os feedbacks chegam como issues no seu repositório, e a resposta é um commit que cita a issue.

Sem pull request

Como o trabalho é individual, não há revisão por PR. Vale o histórico: branches curtas, commits pequenos e a main sempre verde.

O ambiente que cada aluno vai ter

Nada é instalado no computador do laboratório. O ambiente roda no navegador, dentro do GitHub, e é igual para todos.

Repositório

Público, com README. É onde o trabalho vive e onde a correção acontece.

Codespace

Máquina virtual com VS Code no navegador, Node 22 e Docker, descrita em .devcontainer/devcontainer.json.

opencode

Agente de código no terminal. Lê o repositório, propõe mudanças e roda comandos com a sua permissão.

OpenRouter

Uma chave dá acesso a vários modelos. A chave fica num secret do Codespaces e nunca entra no repositório.

Git com branches curtas (trunk-based)

A main é o tronco e precisa estar sempre funcionando. Cada mudança nasce numa branch que dura horas, não semanas, e volta para a main por merge local.

Regras da disciplina

  • Uma branch por mudança: feat/, test/, fix/, docs/, chore/.
  • A branch vive no máximo um dia e é apagada depois do merge.
  • Antes do merge: git pull --rebase e npm test verde.
  • Merge com git merge --ff-only, sem commit de merge.
  • Nada de git push --force na main.

Mensagens de commit

Padrão Conventional Commits: tipo(escopo): o que mudou, no imperativo e em português.

feat(reserva): impede reserva de sala ocupada
test(reserva): cobre sala ocupada no mesmo horário
fix(cep): trata CEP com hífen (#4)
docs: descreve requisitos de qualidade

O (#4) liga o commit à issue de feedback. Closes #4 no corpo fecha a issue quando o commit chega à main.

ObjetivoFazer uma mudança completa do jeito que será cobrado no semestre.
FaçaRode os quatro passos em sequência: abrir a branch, commitar, integrar na main e responder a uma issue de feedback.
ObserveO git log --oneline --graph fica linear: sem bolhas de merge, um commit por intenção.
ConclusãoO histórico vira evidência. Na prova oral eu abro o log e peço para você explicar um commit.

O que chamamos de qualidade de software

Conformidade

O software faz o que a especificação diz. Mede-se comparando o comportamento com requisitos escritos.

Adequação ao uso

O software resolve o problema de quem usa, no contexto em que usa. Uma especificação errada gera um produto conforme e inútil.

Qualidade do código

O software continua fácil de mudar. Testes, legibilidade e baixa complexidade reduzem o custo da próxima mudança.

VerificaçãoEstamos construindo o produto do jeito certo? Testes, revisão, análise estática.
ValidaçãoEstamos construindo o produto certo? Conversa com o usuário, critérios de aceite, protótipo.

ISO/IEC 25010:2023 · qualidade do produto

Nove características. Cada uma vira requisito quando ganha uma métrica e um jeito de testar.

Adequação funcionalCompletude, correção e pertinência das funções.
Eficiência de desempenhoTempo de resposta, uso de recursos, capacidade.
CompatibilidadeCoexistência e interoperabilidade com outros sistemas.
Capacidade de interaçãoAntiga usabilidade: aprendizado, operação, proteção contra erro do usuário.
ConfiabilidadeAusência de falhas, disponibilidade, tolerância a falhas, recuperação.
SegurançaConfidencialidade, integridade, autenticidade, responsabilização.
ManutenibilidadeModularidade, testabilidade, facilidade de análise e de modificação.
FlexibilidadeAntiga portabilidade: adaptação, instalação, escalabilidade.
Proteção (safety)Nova em 2023: evitar dano a pessoas, patrimônio e ambiente.

Prompt 1 de 325 min

Devcontainer e configuração do opencode

Você está num GitHub Codespace, na raiz do repositório organizacao-recursos, que hoje só tem o README. Crie .devcontainer/devcontainer.json usando a imagem mcr.microsoft.com/devcontainers/javascript-node:1-22-bookworm, a feature ghcr.io/devcontainers/features/docker-in-docker:2, a extensão dbaeumer.vscode-eslint, o secret recomendado OPENROUTER_API_KEY com descrição em português e um postCreateCommand que instale o opencode com curl -fsSL https://opencode.ai/install | bash. Crie opencode.json com o $schema https://opencode.ai/config.json, o provedor openrouter lendo a chave por {env:OPENROUTER_API_KEY} e o modelo padrão que eu informar. Crie .gitignore para Node (node_modules, coverage, .env). Crie AGENTS.md dizendo que o projeto é em JavaScript puro com ES modules, sem TypeScript, que os testes usam node:test e que todo commit segue Conventional Commits em português. Não escreva nenhuma chave em arquivo. Mostre o conteúdo de cada arquivo antes de gravar.

Antes de aceitar: procure "sk-or" no diff. Se aparecer, recuse a mudança. Depois rode Rebuild Container e confira opencode --version.
Prompt 2 de 325 min

O opencode monta o projeto Node

Leia o AGENTS.md e transforme este repositório num projeto Node 22 com ES modules, sem TypeScript. Crie package.json com "type": "module", engines node >= 22 e os scripts test (node --test), test:cov (node --test --experimental-test-coverage --test-coverage-include='src/**') e lint (eslint .). Configure o ESLint 9 em eslint.config.js no formato flat, com @eslint/js recommended, globals do Node e a regra complexity limitada a 8. Crie src/intervalo.js com a função sobrepoe(a, b), que diz se dois intervalos [inicio, fim) de datas se sobrepõem, e test/intervalo.test.js com dois testes em node:test: intervalos que se cruzam e um que começa exatamente quando o outro termina. Peça permissão antes de instalar dependências. No fim, rode npm run lint e npm test e mostre a saída. Não use jest, mocha nem vitest.

Antes de aceitar: leia o git diff inteiro, confira que o script test é node --test e rode npm run lint && npm test você mesmo.
Prompt 3 de 320 min

Requisitos de qualidade do seu projeto

Atue como analista de qualidade. O projeto deste repositório é um sistema de Organização de Recursos de uma universidade: reserva de salas, professores e materiais sem conflito de horário. Escreva docs/qualidade.md com uma tabela de colunas Característica ISO/IEC 25010:2023, Requisito, Métrica, Meta e Como será verificado. Cubra pelo menos adequação funcional, eficiência de desempenho, confiabilidade, segurança e manutenibilidade. Cada meta precisa de número e unidade. Na coluna Como será verificado use apenas técnicas da disciplina: teste de unidade, teste de integração com banco, dublê de teste, cenário BDD, teste de carga, cobertura e análise estática. Quando faltar informação para fixar uma meta, escreva a pergunta numa seção Perguntas em aberto em vez de inventar o número. Não crie código.

Antes de aceitar: toda linha tem número e técnica. Apague as linhas que você não saberia explicar na prova oral.
