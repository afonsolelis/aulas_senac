Projeto 1 · Individual

API da Biblioteca

Uma API simples que lê os livros de um arquivo JSON e responde a consultas, construída a partir de uma especificação.

Individual Dados em JSON · sem banco Java 21 · Spring Boot 3.x Entrega na semana 12

Objetivo

Construir, individualmente, uma API REST simples que responde a consultas sobre os livros de uma biblioteca. As informações ficam em um arquivo livros.json dentro do projeto: a API lê esse arquivo e devolve os dados pedidos. Não há banco de dados, cadastro nem empréstimo.

Com o domínio simples, o esforço vai para o que a disciplina avalia: o projeto nasce de uma especificação escrita antes do código, seguindo o Spec-Driven Development da Aula 02, e cada regra chega à entrega com testes que a verificam.

Escopo e restrições

Dentro do escopo

  • Arquivo livros.json com pelo menos 20 livros: id, título, autor, ano, gênero e exemplares disponíveis.
  • Somente requisições GET, com respostas em JSON.
  • Java 21, Spring Boot 3.x, Maven e JUnit 5.

Fora do escopo

  • Banco de dados de qualquer tipo.
  • Chamada a API externa.
  • Cadastro, alteração ou exclusão de livros, empréstimos e login.

Rotas obrigatórias

MétodoRotaResponde
GET/livrosTodos os livros do arquivo
GET/livros/{id}Um livro pelo id
GET/livros?autor=Livros de um autor
GET/livros?genero=Livros de um gênero
GET/livros/disponiveisLivros com pelo menos um exemplar disponível

Regras de negócio obrigatórias

  1. Livro encontrado responde 200 com os dados do livro.
  2. Id que não existe no arquivo responde 404.
  3. Id que não é número inteiro positivo responde 400.
  4. A busca por autor e por gênero ignora maiúsculas e minúsculas e aceita parte do nome: assis encontra Machado de Assis.
  5. Busca sem resultado responde 200 com lista vazia.
  6. Um livro está disponível quando tem um ou mais exemplares disponíveis.
  7. Todo erro responde no mesmo formato: {"status": 404, "mensagem": "Livro 99 não encontrado"}.

Fluxo de Spec-Driven Development

1. Especificação

spec.md com as rotas e regras acima escritas como requisitos verificáveis, cada um com identificador.

2. Plano

plan.md com as decisões de projeto: camadas, leitura do JSON e formato de erro.

3. Tarefas

tasks.md quebrando o plano em passos pequenos, cada um ligado a um requisito.

4. Implementação por TDD

Cada tarefa começa por um teste vermelho; o histórico de commits mostra o ciclo red, green e refactor.

5. Rastreabilidade

Cada requisito aponta para os testes que o verificam, e cada teste cita o requisito no nome.

6. Revisão da especificação

Quando o código revela uma regra mal escrita, a especificação é corrigida no mesmo commit.

Práticas de qualidade exigidas

Testes de unidade

JUnit 5 com testes parametrizados para os casos válidos, inválidos e de borda de cada regra.

Testes de API

Chamadas às rotas com MockMvc conferindo status e corpo da resposta.

Cobertura

Relatório do JaCoCo gerado no build.

Análise estática

Projeto no SonarCloud com quality gate aprovado.

Integração contínua

GitHub Actions rodando testes, cobertura e análise a cada push e pull request.

Documentação

README.md com como rodar, como testar e um exemplo de chamada para cada rota.
