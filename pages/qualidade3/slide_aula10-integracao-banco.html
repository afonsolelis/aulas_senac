Um teste de unidade com dublê no lugar do banco confere a chamada que você escreveu. Ele não confere se o PostgreSQL entende aquele SQL do jeito que você imaginou. O próximo laboratório mostra um caso assim.

A unidade passa e a integração reprova

ObjetivoVer um defeito que só aparece quando o SQL roda num PostgreSQL de verdade.
Faça1. Rode "opencode gera o repositório" e leia o resumo do agente.
2. Abra src/repositorios/emprestimos.js e leia a linha destacada.
3. Rode "Testes de unidade" e "Testes de integração".
4. Rode "Depois da correção".
Observedevolvido_em = NULL nunca é verdadeiro em SQL, então a contagem sempre dá zero. O fake em memória usa === null de JavaScript e passa.
ConclusãoO agente disse que os testes passavam, e passavam. Com a contagem zerada, o limite de 3 empréstimos nunca seria aplicado; só o teste contra o banco real mostrou isso.

Modelagem relacional até a 3FN

1FN

Cada coluna guarda um valor atômico e não há grupos repetidos.

Errado: livros_emprestados = '12,15,31' na tabela de alunos. Certo: uma linha por empréstimo em emprestimos.

2FN

Toda coluna depende da chave inteira, e não de parte dela.

Errado: titulo dentro de emprestimos, que depende só de livro_id. Certo: o título fica em livros.

3FN

Nenhuma coluna depende de outra coluna que não é chave.

Cidade e UF dependem do CEP, e o CEP depende do aluno. Por isso o endereço vai para a tabela ceps.

Na prática, cada forma normal remove uma chance de o mesmo fato aparecer em dois lugares com valores diferentes. Se o título do livro estiver em 40 empréstimos, uma correção de grafia precisa acertar 40 linhas.

Laboratório 2 de 7

Migrações versionadas

ObjetivoCriar o esquema por arquivos numerados que qualquer máquina aplica na mesma ordem.
Faça1. "Preparar o ambiente" sobe o PostgreSQL de desenvolvimento no Docker do Codespace.
2. Rode "opencode gera as migrações" e leia scripts/migrar.js.
3. Rode "Migrar", "Migrar de novo" e "Ver schema_migrations".
ObserveNa segunda execução nada é aplicado: o script compara a pasta com a tabela schema_migrations. Cada arquivo roda dentro de uma transação.
ConclusãoMigração aplicada não se edita. Mudança nova vira arquivo novo, com o próximo número.

Laboratório 3 de 7

Quebrando as regras no psql

ObjetivoVer o banco recusar dados que violam as regras do DER.
Faça1. Rode "Perguntar ao opencode": ele propõe os INSERTs que deveriam falhar.
2. Rode "Descrever emprestimos" e as quatro inserções inválidas.
3. Compare o nome da restrição em cada erro com 003_cria_emprestimos.sql.
ObserveCada erro traz o código (23505, 23503, 23514) e o nome da restrição. São esses dois campos que o teste de integração vai conferir.
ConclusãoDar nome às restrições deixa o erro legível e o teste preciso.

Laboratório 4 de 7

Repositório com pg e queries parametrizadas

ObjetivoEscrever o acesso a dados com pg.Pool e parâmetros $1, $2.
Faça1. Rode "opencode gera a busca" e depois "Procurar concatenação" no diff.
2. Rode "Versão concatenada" com a entrada maliciosa.
3. Rode "Versão parametrizada" e "Pedir a correção".
ObserveConcatenando, a aspa da entrada fecha a string do SQL e o OR '1'='1' devolve todos os alunos. Com parâmetro, o valor viaja separado do comando e vira só um texto.
ConclusãoNenhum valor vindo de fora entra no texto do SQL. O repositório recebe o pool por parâmetro, o que permite trocar por um client numa transação.

Por que um PostgreSQL de verdade no teste

SQLite no lugar

Outro dialeto: não tem EXCLUDE USING gist, timestamptz nem RESTART IDENTITY; foreign keys vêm desligadas por padrão; os códigos de erro são outros. O teste passa num banco que não vai para produção.

Mock do pg

Confere que query foi chamada com a string que você escreveu. Um = NULL no lugar de IS NULL passa, e uma restrição esquecida na migração também.

Testcontainers

O teste sobe postgres:16-alpine num container descartável, aplica as migrações e derruba tudo no fim. No Codespace, o Docker vem da feature docker-in-docker do devcontainer.

Dublês continuam valendo para o que está fora do seu controle, como a ViaCEP na próxima aula. O banco é parte do seu sistema: as migrações e o SQL são código seu e precisam de teste.

Laboratório 5 de 7

PostgreSQL no teste com Testcontainers

ObjetivoRodar a suíte de integração contra um PostgreSQL 16 que nasce e morre com o teste.
Faça1. "Preparar o ambiente" instala as dependências e confere o Docker.
2. Rode "opencode gera o helper" e leia helpers/banco.js.
3. Confira você mesmo com "test:int com logs" e "docker ps durante o teste".
ObserveO Ryuk sobe junto: é ele que remove o container mesmo se o teste quebrar no meio. Os testes conferem code e constraint do erro do pg.
ConclusãoCom DATABASE_URL_TESTE definida, o helper usa esse banco; sem ela, sobe o container. O mesmo arquivo serve ao Codespace e ao CI.

Laboratório 6 de 7

Isolamento entre testes

ObjetivoFazer cada teste começar com o banco no mesmo estado, em qualquer ordem.
Faça1. Rode "opencode gera mais testes" e, em seguida, "Sem isolamento".
2. Rode "Pedir o isolamento" e confira com "Com TRUNCATE".
3. Abra transacao.test.js e rode "Com ROLLBACK".
ObserveTRUNCATE ... RESTART IDENTITY CASCADE também zera os ids, então o primeiro aluno de cada teste é sempre o id 1.
ConclusãoROLLBACK é mais rápido, mas só funciona se todo o código testado usar o mesmo client. Na dúvida, TRUNCATE.

Laboratório 7 de 7

Duas suítes, dois jobs no CI

ObjetivoSeparar a suíte rápida da suíte com banco e rodar as duas no GitHub Actions.
Faça1. Rode "opencode gera o CI" e leia o ci.yml que ele editou.
2. Veja os scripts em package.json.

Prompt 1 de 330 min

DER na 3FN e migrações

Você está no repositório organizacao-recursos, em JavaScript puro com ES modules e testes em node:test. O sistema reserva salas, professores e materiais da universidade sem conflito de horário e agora passa a guardar os dados em PostgreSQL 16. Antes de escrever código, crie docs/der.md com um diagrama erDiagram em Mermaid e uma tabela por entidade (coluna, tipo, nulo, chave, restrição) para alunos, professores, salas, materiais, reservas e a tabela de ligação entre reservas e materiais. Para cada tabela, justifique em uma frase por que ela está na 1FN, na 2FN e na 3FN; trate logradouro, bairro, cidade e uf como dependentes do CEP, numa tabela própria de CEPs. Depois crie as migrações migrations/001_*.sql em diante, uma por assunto, com chave primária em toda tabela, foreign keys com ON DELETE RESTRICT, UNIQUE em e-mail e matrícula, CHECK do CEP com 8 dígitos, CHECK de fim maior que início e duas restrições EXCLUDE USING gist (extensão btree_gist) que impeçam reservas sobrepostas da mesma sala e do mesmo professor. Dê nome a todas as restrições. O conflito de materiais pode ficar no serviço; registre essa decisão no docs/der.md. Crie scripts/migrar.js exportando migrar(pool), que cria a tabela schema_migrations se não existir, aplica em ordem só os arquivos que ainda não estão nela, cada um dentro de uma transação, e pode ser executado direto com node scripts/migrar.js lendo DATABASE_URL. Mostre o SQL antes de gravar.

Antes de aceitar: rode node scripts/migrar.js duas vezes; a segunda não pode aplicar nada. No psql, \d reservas precisa listar as duas restrições de exclusão.
Prompt 2 de 335 min

Repositório e testes de integração

Instale pg como dependência e @testcontainers/postgresql como devDependency. Crie src/db.js exportando criarPool(), que lê DATABASE_URL e falha com mensagem clara se ela não existir. Crie src/repositorios/reservas.js exportando repositorioReservas(db), em que db é um pool ou um client, com as funções criar, listarPorSala e cancelar. Toda query usa parâmetros $1, $2; nenhuma monta SQL concatenando valores. Crie test/integracao/helpers/banco.js exportando iniciarBanco(): se DATABASE_URL_TESTE existir, usa esse banco; se não, sobe postgres:16-alpine com PostgreSqlContainer. Em seguida aplica migrar(pool) e devolve { pool, limpar, parar }, em que limpar() faz TRUNCATE de todas as tabelas com RESTART IDENTITY CASCADE. Em test/integracao/reservas.test.js, com node:test e node:assert/strict, chame limpar() no beforeEach e cubra: reserva válida gravada e lida de volta; reserva sobreposta da mesma sala rejeitada com code 23P01; reservas encostadas (uma termina às 10h, a outra começa às 10h) aceitas; professor inexistente rejeitado com code 23503; e-mail de aluno repetido rejeitado com code 23505. Confira também o nome da restrição no erro. Não use SQLite nem mock do pg nesses testes.

Antes de aceitar: comente a restrição EXCLUDE da sala, rode npm run test:int e confira que o teste de sobreposição fica vermelho. Desfaça com git restore. Procure + ou template string montando SQL no diff.
Prompt 3 de 320 min

Scripts separados e job de integração no CI

Mova os testes do Trabalho 1 para test/unidade sem alterar o conteúdo deles, corrigindo apenas os caminhos de import. No package.json, deixe "test": "node --test test/unidade", crie "test:int": "node --test test/integracao" e "migrar": "node scripts/migrar.js". Em .github/workflows/ci.yml, mantenha o job atual de lint, testes de unidade e cobertura com o nome unidade e acrescente o job integracao, com needs: unidade, Node 22, npm ci e npm run test:int, usando o serviço postgres:16-alpine com healthcheck pg_isready e a variável DATABASE_URL_TESTE apontando para ele. Crie .env.example com uma DATABASE_URL de desenvolvimento sem senha real e confirme que .env está no .gitignore. Atualize o README com os comandos para subir o banco de desenvolvimento com docker run, aplicar as migrações e rodar cada suíte.

Antes de aceitar: pare o container de desenvolvimento e rode npm test; ele precisa passar sem banco. Depois do push, os jobs unidade e integracao aparecem verdes na aba Actions.

O que confiro na mesa

  • npm run test:int no seu Codespace sobe o postgres e passa.
  • Você aponta uma restrição no DER e mostra o teste que a reprova.
  • Nenhum SQL em src/ é montado por concatenação.
  • O git log é linear, com commits feat(banco) e test(integracao).
