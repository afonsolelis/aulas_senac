O que a cobertura mede

Enquanto os testes rodam, o Node conta quais partes de src/ foram executadas. O relatório responde a uma pergunta: que código nenhum teste chegou a rodar?

Linhas

Fração das linhas executadas pelo menos uma vez. A coluna uncovered lines diz quais faltam, como 9-10 15-16.

Ramos

Fração dos caminhos de cada decisão (if, else, &&, ||, ?:) que algum teste percorreu. Um if testado só no caso verdadeiro deixa um ramo descoberto.

Funções

Fração das funções chamadas por algum teste. Uma função exportada e nunca chamada aparece aqui antes de aparecer em produção.

Ligação com a Aula 03Cobertura de ramos é a medida automática da caixa branca: cada ramo descoberto aponta um caso de teste que a análise de caminhos teria pedido.
ObjetivoGerar o relatório de cobertura nativo do Node e localizar os ramos que nenhum teste percorre.
Faça1. Rode a cobertura sem filtro e depois só de src/.
2. Peça ao agente a leitura do relatório.
3. Confira as linhas apontadas no próprio arquivo.
ObserveSem --test-coverage-include, os arquivos de teste entram na conta e inflam a média. As linhas 9-10 e 15-16 são as recusas por multa e por reserva.
ConclusãoO agente lê a tabela rápido, mas a conferência é sua: abra as linhas citadas e veja se a regra descrita é a que está lá.
ObjetivoTransformar a cobertura em meta que reprova a execução, e cobrir os ramos que faltam.
Faça1. Peça ao agente o script test:cov.
2. Confira o script e rode: a meta de ramos reprova.
3. Peça os testes que faltam, sem mexer em src/.
4. Confira o diff e rode de novo.
ObserveCom --test-coverage-branches=80, 71,43% de ramos encerra o comando com código 1, mesmo com todos os testes verdes.
ConclusãoA meta vira uma regra que o CI consegue aplicar. A revisão humana confere que os testes novos têm asserção e que o diff não tocou no código de produção.

Por que 100% não prova correção

Executar não é conferir

it('calcula multa com atraso', () => {
  const multa = calcularMulta(previsto, devolvido);
  assert.ok(multa > 0);
});

Esse teste roda todas as linhas de calcularMulta e passa com 450, com 3000 ou com 99999. A cobertura chega a 100% e a regra continua sem verificação.

O que a cobertura não enxerga

  • Fronteiras: > e >= dão a mesma cobertura; só um teste no limite separa os dois.
  • Regra esquecida: se a especificação pede o teto e o código não tem o teto, não há linha descoberta.
  • Asserção fraca: assert.ok no lugar do valor exato.

Use a cobertura como alarme de código que nenhum teste rodou, e a meta de 80% como piso, não como objetivo.

ObjetivoVer um bug sobreviver a 100% de cobertura e encontrá-lo com asserções exatas.
Faça1. Rode a cobertura: 100% e tudo verde.
2. Peça ao agente valores exatos nos testes.
3. Rode npm test: o bug aparece.
4. Peça a correção e confira com test:cov.
ObserveO código usa Math.max onde a regra pede Math.min: 3 dias de atraso custam 3000 centavos. O teste antigo, com assert.ok(multa > 0), não percebia.
ConclusãoA revisão que pegou o bug foi ler a asserção, não olhar o número da cobertura. É esse o trabalho que o agente não faz por você.

Análise estática com ESLint 9

eslint.config.js (flat config)

import js from '@eslint/js';
import globals from 'globals';

export default [
  { ignores: ['coverage/', 'node_modules/'] },
  js.configs.recommended,
  {
    languageOptions: {
      ecmaVersion: 2024, sourceType: 'module',
      globals: globals.node
    },
    rules: { complexity: ['error', 6] }
  }
];

Dependências de desenvolvimento: eslint, @eslint/js e globals. Script: "lint": "eslint .".

O que ela encontra sem rodar o código

  • recommended: variável sem uso, nome não declarado, código inalcançável, chave duplicada.
  • complexity: número de caminhos independentes da função. Cada if, &&, || e case soma 1.

Complexidade 7 pede pelo menos 7 testes para cobrir todos os ramos. O limite de 6 força a quebrar a função antes que ela fique difícil de testar.

ObjetivoConfigurar o ESLint 9 com o agente e corrigir o que ele aponta sem desligar regras.
Faça1. Peça ao agente a instalação e o eslint.config.js, e autorize o npm install.
2. Confira o diff e rode npm run lint.
3. Peça a correção.
4. Confira que não há eslint-disable e que os testes seguem verdes.
ObservesituacaoDoAluno tem complexidade 7 e dois imports sem uso. A correção extrai estaBloqueado e troca o aninhamento por retornos antecipados.
ConclusãoUm agente pressionado a zerar o lint pode inserir // eslint-disable. O git grep depois da correção é a revisão que impede isso.

Integração contínua

Do push ao badge verde

ObjetivoCriar o workflow com o agente, integrar na main e reagir a um CI vermelho.
Faça1. Peça o ci.yml e o badge.
2. Rode o gate local antes do merge.
3. Faça o merge --ff-only e o push.
4. Acompanhe com gh run watch: vermelho.
5. Peça o diagnóstico ao agente.
6. Confira e mande o commit fix.
ObserveLocalmente tudo passou, porque o node_modules já estava instalado. No CI, npm ci recusa um package-lock.json fora de sincronia: ele ficou fora do commit do ESLint.
ConclusãoCI vermelho na main vira commit fix imediato, antes de qualquer outra mudança. O diagnóstico do agente só vale depois de você conferir o git status.

Quality gate sem SonarCloud

Cada verificação do SonarCloud tem uma biblioteca Node equivalente. Todas rodam no GitHub Actions, sem conta nem token externo.

ObjetivoMontar no próprio CI um quality gate que faz o papel do SonarCloud.
Faça1. Rode "opencode: montar o quality gate" e leia eslint.config.js e ci.yml.
2. Rode "npm run qualidade" e veja o que reprova.
3. Peça a correção, confira o diff e rode o gate de novo.
4. Rode "gh run view" para ver o resumo do run.
ObserveCada passo do CI tem continue-on-error: todas as verificações rodam, o resumo mostra todas, e o último passo reprova se qualquer uma falhou.
ConclusãoO gate é código no repositório: versionado, revisado e igual na sua máquina e no CI.

Cobertura, lint e CI no seu repositório

Sequência

  1. test/cobertura: script test:cov e testes até 80% de linhas e ramos.
  2. chore/eslint: flat config, complexity e correções.
  3. chore/ci: workflow, badge e primeiro run verde.

Regra da main

  • Antes de cada merge: npm run lint && npm run test:cov verdes na sua máquina.
  • Merge local com git merge --ff-only, sem pull request.
  • CI vermelho depois do push: o próximo commit é o fix.
A meta de cobertura se alcança com testes que conferem valores. Excluir arquivo da cobertura ou escrever teste sem asserção para subir o número será cobrado na prova oral.
Prompt 1 de 430 min

Cobertura com meta

Na branch test/cobertura do repositório organizacao-recursos, adicione ao package.json o script "test:cov": "node --test --experimental-test-coverage --test-coverage-lines=80 --test-coverage-branches=80 --test-coverage-include='src/**'", sem nenhuma dependência nova. Rode npm run test:cov e me mostre a tabela. Liste, arquivo por arquivo, as linhas e os ramos não cobertos e diga qual regra do domínio cada um representa (sobreposição de intervalos, capacidade da sala, professor em duas aulas, material indisponível, reserva no passado). Depois, um teste por vez, escreva testes que cubram esses ramos com asserção de valor exato ou da mensagem de erro, sem alterar nada em src/ e sem excluir arquivos da cobertura. Pare depois de cada teste para eu rodar npm run test:cov e commitar como test(escopo): ....

Antes de aceitar: todo teste novo confere valor ou mensagem, nada de assert.ok genérico, e o git diff não toca em src/.
Prompt 2 de 420 min

ESLint no seu repositório

Na branch chore/eslint, instale como devDependencies eslint, @eslint/js e globals. Crie eslint.config.js no formato flat do ESLint 9, exportando um array com: ignores para coverage/ e node_modules/; js.configs.recommended; e um bloco com languageOptions { ecmaVersion: 2024, sourceType: 'module', globals: globals.node } e a regra complexity: ['error', 6]. Adicione o script "lint": "eslint .". Rode npm run lint e me mostre os problemas agrupados por regra. Corrija um arquivo por vez, sem usar comentários eslint-disable e sem desligar regras; para complexidade, extraia funções pequenas ou use retornos antecipados. Rode npm test depois de cada correção e pare para eu commitar.

Antes de aceitar: git grep eslint-disable vazio, package-lock.json no commit e npm test verde depois de cada refatoração.
Prompt 3 de 425 min

Workflow de CI e badge

Na branch chore/ci, crie .github/workflows/ci.yml com name CI, disparado em push e workflow_dispatch, com um job qualidade em ubuntu-latest e os passos: actions/checkout@v4; actions/setup-node@v4 com node-version 22 e cache npm; npm ci; npm run lint; npm run test:cov. Acrescente no topo do README.md o badge ![CI](https://github.com/MEU-USUARIO/organizacao-recursos/actions/workflows/ci.yml/badge.svg), perguntando antes qual é o meu usuário do GitHub. Não crie pull request nem outros workflows. Antes de terminar, rode npm ci, npm run lint e npm run test:cov localmente e me mostre o resultado de cada um.

Antes de aceitar: rode você mesmo npm run lint && npm run test:cov, faça o merge --ff-only, o push e acompanhe com gh run watch. Vermelho vira commit fix na hora.
Prompt 4 de 425 min

Quality gate no seu repositório

Na branch chore/quality-gate do repositório organizacao-recursos, monte um quality gate que substitua o SonarCloud. Instale como devDependencies eslint-plugin-sonarjs, eslint-plugin-security, jscpd, secretlint, @secretlint/secretlint-rule-preset-recommend e knip. No eslint.config.js, acrescente sonarjs.configs.recommended e pluginSecurity.configs.recommended, com a regra sonarjs/cognitive-complexity limitada a 15, mantendo complexity 8. Crie .jscpd.json com path ["src"], threshold 3 e reporters console e markdown, e .secretlintrc.json com o preset recomendado. Adicione ao package.json os scripts dup (jscpd), segredos (secretlint "**/*"), morto (knip), auditoria (npm audit --audit-level=high) e qualidade, que roda lint, dup, segredos, morto, auditoria e test:cov nessa ordem. No .github/workflows/ci.yml, transforme cada verificação num passo com id e continue-on-error: true, escreva em $GITHUB_STEP_SUMMARY uma tabela com o outcome de cada passo e termine com um passo que falha se algum outcome for failure. Rode npm run qualidade e corrija o que reprovar sem desligar regra, sem eslint-disable e sem subir o threshold. Mostre o diff antes de cada commit.

Antes de aceitar: git grep eslint-disable vazio, threshold do jscpd em 3 e o resumo do run mostrando as seis verificações.
