Testes de integração com banco de dados real

Objetivo da aula

Sair da aula com o organizacao-recursos guardando dados em PostgreSQL 16, com DER na 3FN, migrações versionadas, um repositório com queries parametrizadas e uma suíte de integração que roda contra um banco real no Codespace e no GitHub Actions.

O primeiro bloco é demonstração no repositório biblioteca-campus, em laboratórios simulados do VS Code: o opencode gera o código a partir de um prompt e o professor confere o resultado com testes, git diff e psql antes de qualquer commit. O segundo bloco é laboratório: cada aluno aplica os três prompts desta página no próprio repositório. Esta é a primeira aula do segundo bloco, depois das provas orais do Trabalho 1. O enunciado do Trabalho 2 foi aberto na semana 11 e a entrega é na semana 17.

1. Teste de unidade e teste de integração

Um teste de unidade exercita uma função ou um módulo sem rede, sem disco e sem banco. Ele roda em milissegundos e pega regra de negócio errada: calcularMulta(5) deveria devolver 750 centavos e devolveu outra coisa. Um teste de integração com banco exercita o seu código junto com o PostgreSQL. Ele leva segundos e pega o que a unidade não enxerga: SQL que o banco interpreta de outro jeito, coluna inexistente, restrição esquecida na migração, conversão de tipo.

UnidadeIntegração com banco
Pastatest/unidadetest/integracao
Comandonpm test (node --test test/unidade)npm run test:int (node --test test/integracao)
Dependênciasdublês e fakesPostgreSQL 16 num container
Quando rodaa cada mudançaantes do merge e no CI

O primeiro laboratório mostra por que as duas suítes são necessárias. O opencode gerou contarAtivos com WHERE devolvido_em = NULL e um teste de unidade com fake em memória, e informou que os testes passavam. Passavam mesmo: o fake compara com === null em JavaScript. Em SQL, porém, = NULL resulta em desconhecido, nenhuma linha entra na contagem e a função devolve sempre zero. Com isso, o limite de 3 empréstimos ativos nunca seria aplicado. Só o teste de integração reprovou o código (0 !== 1), e a correção foi IS NULL.

2. Modelagem relacional e DER na 3FN

As formas normais existem para que cada fato fique guardado num lugar só. Quando o título do livro aparece em 40 empréstimos, uma correção de grafia precisa acertar 40 linhas, e a primeira que ficar para trás contradiz as outras.

  • 1FN: cada coluna guarda um valor atômico, sem listas. livros_emprestados = '12,15,31' na tabela de alunos viola a 1FN; o certo é uma linha por empréstimo em emprestimos.
  • 2FN: toda coluna depende da chave inteira. titulo dentro de emprestimos depende só de livro_id, então pertence a livros.
  • 3FN: nenhuma coluna depende de outra que não é chave. Logradouro, bairro, cidade e UF dependem do CEP, e o CEP depende do aluno. Por isso o endereço vai para uma tabela ceps, e alunos guarda só o CEP e o número.

No biblioteca-campus, o DER tem quatro tabelas do domínio: alunos, livros, emprestimos (com aluno_id, livro_id, emprestado_em, devolucao_prevista e devolvido_em) e ceps. Aluno e livro têm relação 1:N com empréstimo. A ligação entre alunos.cep e ceps fica sem foreign key por decisão: na Aula 11, o aluno poderá ser cadastrado com a ViaCEP fora do ar, e o endereço pendente é justamente o CEP que ainda não tem linha em ceps. Uma quinta tabela, schema_migrations, controla as migrações e não faz parte do domínio.

No seu projeto, o DER cobre alunos, professores, salas, materiais, reservas e a tabela de ligação entre reservas e materiais. O arquivo docs/der.md traz o diagrama em Mermaid (erDiagram) e uma justificativa de 1FN, 2FN e 3FN por tabela. Na prova oral, essa justificativa será perguntada.

3. Restrições como regra de negócio

Uma regra garantida pelo banco vale para qualquer caminho de escrita: a API, um script de carga, alguém no psql ou um bug no serviço. Dê nome a todas as restrições; o nome aparece na mensagem de erro e o teste de integração confere esse nome junto com o código do erro.

RegraRestriçãoCódigo do erro
E-mail e matrícula não se repetemUNIQUE23505
CEP com 8 dígitos; exemplares maior que zero; prazo depois do empréstimoCHECK23514
Empréstimo aponta para aluno e livro existentesFOREIGN KEY ... ON DELETE RESTRICT23503
O mesmo aluno não fica com dois empréstimos ativos do mesmo livroUNIQUE INDEX ... WHERE devolvido_em IS NULL23505
Sala sem duas reservas no mesmo horário (seu projeto)EXCLUDE USING gist com btree_gist23P01

Regras que dependem de contar linhas, como o máximo de 3 empréstimos ativos, o prazo de 14 dias e a multa de 150 centavos por dia com teto de 3000, ficam no serviço e são testadas por unidade e por integração.

-- migrations/003_cria_emprestimos.sql
CREATE TABLE emprestimos (
  id                  integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  aluno_id            integer NOT NULL REFERENCES alunos (id) ON DELETE RESTRICT,
  livro_id            integer NOT NULL REFERENCES livros (id) ON DELETE RESTRICT,
  emprestado_em       date NOT NULL DEFAULT current_date,
  devolucao_prevista  date NOT NULL,
  devolvido_em        date,
  CONSTRAINT prazo_valido CHECK (devolucao_prevista > emprestado_em),
  CONSTRAINT devolucao_valida CHECK (devolvido_em IS NULL OR devolvido_em >= emprestado_em)
);

CREATE UNIQUE INDEX emprestimos_ativo_unico
  ON emprestimos (aluno_id, livro_id)
  WHERE devolvido_em IS NULL;

4. Migrações versionadas

O esquema nasce de arquivos SQL numerados em migrations/, aplicados em ordem por scripts/migrar.js. O script cria a tabela schema_migrations se ela não existir, compara a pasta com o que já foi aplicado e roda só o que falta, cada arquivo dentro de uma transação. Se um arquivo falhar, o ROLLBACK desfaz a mudança parcial e o arquivo não entra em schema_migrations. Migração aplicada não se edita: mudança nova vira arquivo novo com o próximo número.

migrations/
  001_cria_alunos.sql
  002_cria_livros.sql
  003_cria_emprestimos.sql
  004_cria_ceps.sql
scripts/
  migrar.js
export async function migrar(pool, { log = console.log } = {}) {
  await pool.query(
    'CREATE TABLE IF NOT EXISTS schema_migrations (' +
    ' versao text PRIMARY KEY, aplicada_em timestamptz NOT NULL DEFAULT now())'
  );
  const { rows } = await pool.query('SELECT versao FROM schema_migrations');
  const aplicadas = new Set(rows.map((r) => r.versao));
  const arquivos = (await readdir(PASTA)).filter((f) => f.endsWith('.sql')).sort();

  for (const arquivo of arquivos) {
    if (aplicadas.has(arquivo)) continue;
    const sql = await readFile(join(PASTA, arquivo), 'utf8');
    const client = await pool.connect();
    try {
      await client.query('BEGIN');
      await client.query(sql);
      await client.query('INSERT INTO schema_migrations (versao) VALUES ($1)', [arquivo]);
      await client.query('COMMIT');
      log('aplicada ' + arquivo);
    } catch (erro) {
      await client.query('ROLLBACK');
      throw new Error('falha em ' + arquivo + ': ' + erro.message, { cause: erro });
    } finally {
      client.release();
    }
  }
}

Para desenvolver, suba um PostgreSQL no Docker do Codespace e coloque a URL no .env, que está no .gitignore. No repositório entra só o .env.example.

docker run -d --name pg-dev -p 5432:5432 \
  -e POSTGRES_USER=biblioteca -e POSTGRES_PASSWORD=dev-local -e POSTGRES_DB=biblioteca \
  postgres:16-alpine
cp .env.example .env
export $(grep -v '^#' .env | xargs)
npm run migrar          # aplica 001 a 004
npm run migrar          # segunda vez: nada pendente
docker exec pg-dev psql -U biblioteca -c '\dt' -c 'SELECT * FROM schema_migrations'

5. Repositório com pg e queries parametrizadas

O acesso a dados fica em src/repositorios/. Cada repositório recebe por parâmetro um pg.Pool ou um client, o que permite usar o mesmo código dentro de uma transação. Todo valor vindo de fora viaja como parâmetro ($1, $2), separado do texto do SQL.

// src/db.js
import pg from 'pg';
pg.types.setTypeParser(1082, (valor) => valor);   // date volta como 'AAAA-MM-DD'

export function criarPool(url = process.env.DATABASE_URL) {
  if (!url) throw new Error('DATABASE_URL não definida (veja .env.example)');
  return new pg.Pool({ connectionString: url, max: 10 });
}

// src/repositorios/alunos.js
export function repositorioAlunos(db) {
  return {
    async buscarPorNome(nome) {
      const { rows } = await db.query('SELECT id, nome, email FROM alunos WHERE nome = $1', [nome]);
      return rows;
    }
  };
}

No laboratório, a primeira proposta do agente montou o WHERE concatenando o nome, mesmo com o AGENTS.md pedindo parâmetros. A busca por x' OR '1'='1 devolveu todos os alunos: a aspa da entrada fechou a string do SQL e o OR virou parte do comando. Com $1, a mesma entrada é só um texto e não encontra ninguém. A revisão pegou o problema com um grep no diff, antes do commit:

git diff --stat
grep -rnE "query\((\"|').*(\+|\$\{)" src/

6. PostgreSQL de verdade no teste com Testcontainers

Trocar o banco por SQLite ou por um mock do pg deixa o teste mais rápido e menos útil. O SQLite tem outro dialeto: não conhece EXCLUDE USING gist, timestamptz nem RESTART IDENTITY, vem com foreign keys desligadas por padrão e devolve outros códigos de erro. Um mock do pg confere que query foi chamada com a string que você escreveu, e por isso aceita o = NULL da seção 1 e qualquer restrição esquecida. O banco é parte do seu sistema; dublês ficam para o que está fora do seu controle, como a ViaCEP na Aula 11.

O pacote @testcontainers/postgresql sobe postgres:16-alpine num container descartável, devolve a URL de conexão e derruba o container no fim. Junto sobe o Ryuk, que remove o container mesmo se o teste quebrar no meio. No Codespace, o Docker vem da feature ghcr.io/devcontainers/features/docker-in-docker:2 do devcontainer, configurada na Aula 01.

npm install pg
npm install -D @testcontainers/postgresql
docker info --format "{{.ServerVersion}}"
// test/integracao/helpers/banco.js
import pg from 'pg';
import { PostgreSqlContainer } from '@testcontainers/postgresql';
import { migrar } from '../../../scripts/migrar.js';

// DATABASE_URL_TESTE (CI com services) ou um container descartável.
// Nunca usa DATABASE_URL: o TRUNCATE apagaria o banco de desenvolvimento.
export async function iniciarBanco() {
  let container = null;
  let url = process.env.DATABASE_URL_TESTE;
  if (!url) {
    container = await new PostgreSqlContainer('postgres:16-alpine').start();
    url = container.getConnectionUri();
  }
  const pool = new pg.Pool({ connectionString: url });
  await migrar(pool, { log: () => {} });
  return {
    pool,
    async limpar() {
      await pool.query('TRUNCATE emprestimos, livros, alunos, ceps RESTART IDENTITY CASCADE');
    },
    async parar() {
      await pool.end();
      if (container) await container.stop();
    }
  };
}
// trecho de test/integracao/emprestimos.test.js
it('rejeita aluno inexistente pela foreign key', async () => {

});

7. Isolamento entre testes

Cada teste precisa começar com o banco no mesmo estado, senão o resultado passa a depender da ordem. No laboratório, o agente acrescentou um beforeEach que inseria a mesma aluna sem limpar o banco; a partir do segundo teste, a inserção falhou com 23505 em alunos_matricula_unica. Há duas formas de isolar:

  • TRUNCATE ... RESTART IDENTITY CASCADE no beforeEach: apaga as linhas e zera os ids, então o primeiro aluno de cada teste é sempre o id 1. Funciona com qualquer código, inclusive o que abre a própria transação.
  • Transação com ROLLBACK: o beforeEach abre um client, roda BEGIN e entrega esse client ao repositório; o afterEach roda ROLLBACK. É mais rápido, mas só funciona se todo o código testado usar o mesmo client.
beforeEach(async () => {
  client = await banco.pool.connect();
  await client.query('BEGIN');
  repo = repositorioEmprestimos(client);
});
afterEach(async () => {
  await client.query('ROLLBACK');
  client.release();
});

8. Duas suítes e o job de integração no CI

Os testes do Trabalho 1 passam para test/unidade sem mudar de conteúdo. npm test precisa terminar sem Docker; se ele depender do banco, a suíte rápida deixou de ser rápida.

"scripts": {
  "test": "node --test test/unidade",
  "test:int": "node --test test/integracao",
  "test:cov": "node --test --experimental-test-coverage test/unidade",
  "lint": "eslint .",
  "migrar": "node scripts/migrar.js"
}

No GitHub Actions, o job integracao só começa se unidade passar. Ele usa o serviço postgres:16-alpine com healthcheck e entrega a URL em DATABASE_URL_TESTE. A senha teste vale só para esse container descartável do runner e não é segredo. Sem o bloco services e sem a variável, o mesmo job funciona com Testcontainers, porque o runner ubuntu-latest já tem Docker.

  integracao:
    needs: unidade
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:16-alpine
        env:
          POSTGRES_USER: teste
          POSTGRES_PASSWORD: teste
          POSTGRES_DB: biblioteca
        ports: ['5432:5432']
        options: >-
          --health-cmd "pg_isready -U teste"
          --health-interval 5s --health-timeout 5s --health-retries 10
    env:
      DATABASE_URL_TESTE: postgres://teste:teste@localhost:5432/biblioteca
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: npm }
      - run: npm ci
      - run: npm run test:int

9. Como revisar o que o agente gerou

Nos sete laboratórios, o código veio do opencode e a verificação veio do professor. O agente acertou a maior parte e errou em três pontos que só a conferência mostrou: o = NULL que zerava a contagem, o SQL concatenado e o beforeEach sem limpeza. Antes de cada commit, confira:

  • npm test e npm run test:int rodados por você, e não só o resumo do agente.
  • git diff lido arquivo por arquivo, com o grep de concatenação em src/.
  • No psql, \d tabela mostrando as restrições com os nomes que o DER promete.
  • Pedidos de permissão do agente lidos antes de aceitar; comando que você não entende é recusado.

10. Prompt 1 · DER na 3FN e migrações

30 min

Você está no repositório organizacao-recursos, em JavaScript puro com ES modules e testes em node:test. O sistema reserva salas, professores e materiais da universidade sem conflito de horário e agora passa a guardar os dados em PostgreSQL 16. Antes de escrever código, crie docs/der.md com um diagrama erDiagram em Mermaid e uma tabela por entidade (coluna, tipo, nulo, chave, restrição) para alunos, professores, salas, materiais, reservas e a tabela de ligação entre reservas e materiais. Para cada tabela, justifique em uma frase por que ela está na 1FN, na 2FN e na 3FN; trate logradouro, bairro, cidade e uf como dependentes do CEP, numa tabela própria de CEPs. Depois crie as migrações migrations/001_*.sql em diante, uma por assunto, com chave primária em toda tabela, foreign keys com ON DELETE RESTRICT, UNIQUE em e-mail e matrícula, CHECK do CEP com 8 dígitos, CHECK de fim maior que início e duas restrições EXCLUDE USING gist (extensão btree_gist) que impeçam reservas sobrepostas da mesma sala e do mesmo professor. Dê nome a todas as restrições. O conflito de materiais pode ficar no serviço; registre essa decisão no docs/der.md. Crie scripts/migrar.js exportando migrar(pool), que cria a tabela schema_migrations se não existir, aplica em ordem só os arquivos que ainda não estão nela, cada um dentro de uma transação, e pode ser executado direto com node scripts/migrar.js lendo DATABASE_URL. Mostre o SQL antes de gravar.
Antes de aceitar: rode node scripts/migrar.js duas vezes; a segunda não pode aplicar nada. No psql, \d reservas precisa listar as duas restrições de exclusão.

11. Prompt 2 · repositório e testes de integração

35 min

Instale pg como dependência e @testcontainers/postgresql como devDependency. Crie src/db.js exportando criarPool(), que lê DATABASE_URL e falha com mensagem clara se ela não existir. Crie src/repositorios/reservas.js exportando repositorioReservas(db), em que db é um pool ou um client, com as funções criar, listarPorSala e cancelar. Toda query usa parâmetros $1, $2; nenhuma monta SQL concatenando valores. Crie test/integracao/helpers/banco.js exportando iniciarBanco(): se DATABASE_URL_TESTE existir, usa esse banco; se não, sobe postgres:16-alpine com PostgreSqlContainer. Em seguida aplica migrar(pool) e devolve { pool, limpar, parar }, em que limpar() faz TRUNCATE de todas as tabelas com RESTART IDENTITY CASCADE. Em test/integracao/reservas.test.js, com node:test e node:assert/strict, chame limpar() no beforeEach e cubra: reserva válida gravada e lida de volta; reserva sobreposta da mesma sala rejeitada com code 23P01; reservas encostadas (uma termina às 10h, a outra começa às 10h) aceitas; professor inexistente rejeitado com code 23503; e-mail de aluno repetido rejeitado com code 23505. Confira também o nome da restrição no erro. Não use SQLite nem mock do pg nesses testes.
Antes de aceitar: comente a restrição EXCLUDE da sala, rode npm run test:int e confira que o teste de sobreposição fica vermelho. Desfaça com git restore. Procure + ou template string montando SQL no diff.

12. Prompt 3 · scripts separados e job de integração no CI

20 min

Mova os testes do Trabalho 1 para test/unidade sem alterar o conteúdo deles, corrigindo apenas os caminhos de import. No package.json, deixe "test": "node --test test/unidade", crie "test:int": "node --test test/integracao" e "migrar": "node scripts/migrar.js". Em .github/workflows/ci.yml, mantenha o job atual de lint, testes de unidade e cobertura com o nome unidade e acrescente o job integracao, com needs: unidade, Node 22, npm ci e npm run test:int, usando o serviço postgres:16-alpine com healthcheck pg_isready e a variável DATABASE_URL_TESTE apontando para ele. Crie .env.example com uma DATABASE_URL de desenvolvimento sem senha real e confirme que .env está no .gitignore. Atualize o README com os comandos para subir o banco de desenvolvimento com docker run, aplicar as migrações e rodar cada suíte.
Antes de aceitar: pare o container de desenvolvimento e rode npm test; ele precisa passar sem banco. Depois do push, os jobs unidade e integracao aparecem verdes na aba Actions.

13. Entregável e checagem

No organizacao-recursos: docs/der.md, migrações com scripts/migrar.js, repositório de reservas com queries parametrizadas e test/integracao rodando contra PostgreSQL real, com os dois jobs do CI verdes na main. Cada prompt vai numa branch curta (feat/banco-esquema, test/integracao-reservas, chore/ci-integracao) que volta para a main com git merge --ff-only.

O que o professor confere na mesa

  • npm run test:int no seu Codespace sobe o postgres e passa.
  • Você aponta uma restrição no DER e mostra o teste que a reprova.
  • Nenhum SQL em src/ é montado por concatenação.
  • O git log é linear, com commits feat(banco) e test(integracao).
