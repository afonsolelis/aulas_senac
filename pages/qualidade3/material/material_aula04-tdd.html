TDD: ciclo red, green e refactor

Objetivo da aula

Sair da aula com as primeiras regras do organizacao-recursos construídas em TDD, com node:test, um commit por passo do ciclo e testes que dão o mesmo resultado em qualquer dia.

Na disciplina, o código e os testes são gerados pelo opencode a partir de prompts. A etapa de qualidade é a sua revisão: pedir um passo por vez, ler o que o agente escreveu, conferir com git diff e npm test e só então commitar. No primeiro bloco o professor mostra isso no repositório biblioteca-campus; no segundo, cada aluno aplica no próprio repositório com os três prompts desta página.

1. O que é teste de unidade e o que não é

A regra "no máximo 3 empréstimos ativos por aluno" mora na função emprestar(aluno, livro, hoje). Um teste de unidade chama essa função com objetos montados na memória e confere o resultado. Ele roda em milissegundos, não depende de banco, rede, arquivo nem do dia em que é executado, e falha por um único motivo, que o nome do teste anuncia.

O teste...ClassificaçãoOnde aparece na disciplina

Um repositório falso em memória, como { buscar: async (id) => ... }, mantém o teste na categoria de unidade: nada sai do processo do Node.

2. Configurar o node:test

O Node 22 traz o executor de testes (node:test) e as asserções (node:assert/strict). Não há biblioteca de teste para instalar. O package.json precisa de "type": "module", para os import, e do script de teste:

{
  "name": "organizacao-recursos",
  "version": "1.0.0",
  "type": "module",
  "scripts": {
    "test": "node --test"
  }
}

Sem argumentos, node --test procura os arquivos *.test.js e os arquivos dentro de pastas test/. Os scripts test:cov e lint entram na Aula 05.

No laboratório do professor, o primeiro teste foi pedido assim ao agente:

opencode run "Crie test/emprestimo.test.js com node:test e node:assert/strict. Teste que emprestar define a devolução prevista 14 dias depois da retirada, com data fixa 2027-02-22T12:00:00Z e padrão AAA. Não altere src/."

O agente lê os arquivos, escreve o teste e pede permissão antes de rodar npm test. O resultado foi este arquivo:

import { describe, it } from 'node:test';
import assert from 'node:assert/strict';
import { emprestar } from '../src/emprestimo.js';

const hoje = new Date('2027-02-22T12:00:00Z');

describe('emprestar', () => {
  it('define a devolução prevista para 14 dias depois da retirada', () => {
    const aluno = { id: 'a1', ativos: [], multaPendente: 0 };
    const livro = { id: 'l1', reservadoPor: null };

    const emprestimo = emprestar(aluno, livro, hoje);

    assert.equal(emprestimo.previsto.toISOString(), '2027-03-08T12:00:00.000Z');
  });
});

A conferência do aluno vem antes do commit: git status --short deve listar só o arquivo de teste, e npm test deve passar. Para saber se o teste confere alguma coisa, mude a regra de propósito (o prazo para 13 dias) e veja o teste falhar:

▶ emprestar
  ✖ define a devolução prevista para 14 dias depois da retirada (1.02ms)
✖ emprestar (2.66ms)
ℹ tests 1
ℹ pass 0
ℹ fail 1

  AssertionError [ERR_ASSERTION]: Expected values to be strictly equal:
  + actual - expected

  + '2027-03-07T12:00:00.000Z'
  - '2027-03-08T12:00:00.000Z'

Um teste gerado que continua verde depois dessa mudança não verifica a regra, mesmo que execute a função.

3. Asserções, hooks e opções de execução

RecursoUso
describe, it, testAgrupar e declarar testes; it e test são a mesma função.
assert.equal(a, b)Igualdade estrita (===) de valores primitivos.
assert.deepEqual(a, b)Igualdade estrutural de objetos e listas, conferindo tipos.
assert.throws(fn, /msg/)Função síncrona que deve lançar erro com a mensagem esperada.
await assert.rejects(promessa, { message })Promessa que deve ser rejeitada. Sem await, o teste termina antes e passa sempre.
before, beforeEachPreparar dados uma vez ou antes de cada teste; beforeEach impede que um teste contamine o seguinte.
it.skip, it.todoPular um teste ou registrar um que falta escrever. Aparecem no resumo como # SKIP e # TODO, sem reprovar.
node --test --watchReexecuta a cada arquivo salvo.
node --test --test-name-pattern="reserva"Roda só os testes cujo nome casa com o padrão.
beforeEach(() => {
  aluno = { id: 'a1', ativos: [], multaPendente: 0 };
  livro = { id: 'l1', reservadoPor: null };
});

it('recusa livro reservado por outro aluno', () => {
  livro.reservadoPor = 'a2';

  const tentar = () => emprestar(aluno, livro, hoje);

  assert.throws(tentar, /reservado por outro aluno/);
});

it('rejeita empréstimo inexistente', async () => {
  await assert.rejects(registrarDevolucao(repo, 'e9', hoje), { message: 'empréstimo e9 não encontrado' });
});

it.skip('aceita professor sem limite de empréstimos', () => {});
it.todo('renova o empréstimo uma única vez');

Ao revisar testes gerados, procure dois erros frequentes: assert.rejects sem await e assert.ok(resultado) no lugar de um valor exato.

4. O ciclo red, green e refactor com o agente

TDD inverte a ordem habitual: o teste vem antes do código. Cada volta do ciclo tem três passos, e cada passo vira um commit.

  1. Red: um único teste novo, para o próximo comportamento, que falha por uma asserção. Commit test(escopo): ....
  2. Green: o menor código que faz esse teste passar, sem antecipar regras. Commit feat(escopo): ....
  3. Refactor: com tudo verde, melhorar nomes e estrutura sem mudar o resultado. Commit refactor(escopo): ....

Com o opencode, quem conduz o ciclo é o aluno. Se o prompt pedir "implemente a multa com testes", o agente escreve teste e código juntos, e não há como saber se o teste teria falhado sem o código. Por isso cada prompt pede um passo e manda parar:

opencode run "Passo red. Acrescente em test/multa.test.js um único teste: 3 dias de atraso custam 450 centavos. Não altere nada em src/. Rode npm test e pare."
git diff --stat && npm test          # só o teste mudou? falhou com 0 !== 450?
git add test/multa.test.js && git commit -m "test(multa): cobra 150 centavos por dia de atraso"

opencode run "Passo green. Escreva o mínimo em calcularMulta para o teste novo passar. Não mexa nos testes e não implemente o teto ainda."
git diff --stat && npm test          # só src/ mudou? tudo verde?
git commit -am "feat(multa): calcula 150 centavos por dia de atraso"

opencode run "Passo refactor. Melhore calcularMulta sem mudar comportamento: use DIA_MS e uma constante exportada MULTA_POR_DIA. Rode npm test depois."
npm test
git commit -am "refactor(multa): dá nome ao dia e ao valor por dia"

A conferência do red tem dois pontos. A falha precisa ser uma asserção (0 !== 450); um SyntaxError ou um erro de import significa que o teste quebrou por outro motivo. E o diff precisa mostrar só o arquivo de teste. Na conferência do green, o diff precisa mostrar só src/: um agente que altera o teste para fazê-lo passar desfaz o ciclo.

$ git log --oneline -4
c81f3b0 (HEAD -> feat/multa) refactor(multa): dá nome ao dia e ao valor por dia
9a7e254 feat(multa): calcula 150 centavos por dia de atraso
4d2e9a1 test(multa): cobra 150 centavos por dia de atraso
2f60c3e (origin/main, main) feat(multa): devolve 0 quando o livro volta no prazo

O commit vermelho fica na branch; a branch só entra na main com git merge --ff-only depois do último passo verde. Na prova oral, git show de um commit test(...) deve mostrar apenas teste. O teto de 3000 centavos da multa é a próxima volta do ciclo.

5. Datas: relógio injetado e mock.timers

Um teste que lê o relógio do sistema muda de resultado conforme o dia. No laboratório, este teste passou em 22/02 e falhou em 10/03 sem nenhuma mudança no código:

export function estaAtrasado(emprestimo) {
  return new Date() > emprestimo.previsto;
}

A correção tem duas partes. A regra de negócio recebe a data como parâmetro, e o teste passa a data que quiser:

export function estaAtrasado(emprestimo, hoje) {
  return hoje > emprestimo.previsto;
}

it('retorna true um dia depois da data prevista', () => {
  assert.equal(estaAtrasado(emprestimo, new Date('2027-03-09T12:00:00Z')), true);
});

A leitura do relógio fica concentrada numa função pequena, na borda do sistema. Para testá-la, t.mock.timers fixa a data só dentro do teste e restaura o relógio no fim:

export function registrarAtraso(emprestimo) {
  const agora = new Date();
  return { ...emprestimo, atrasado: estaAtrasado(emprestimo, agora), conferidoEm: agora };
}

it('usa o relógio do sistema quando ninguém informa a data', (t) => {
  t.mock.timers.enable({ apis: ['Date'], now: new Date('2027-03-10T12:00:00Z') });

  const registro = registrarAtraso(emprestimo);

  assert.equal(registro.atrasado, true);
  assert.equal(registro.conferidoEm.toISOString(), '2027-03-10T12:00:00.000Z');
});

Revisão rápida depois de qualquer teste gerado: grep -rn "new Date()" test/ não deve encontrar nada.

6. Padrão AAA e nomes de teste

Arrange, Act, Assert: montar os dados, executar uma única ação e conferir o resultado. Uma linha em branco separa os três blocos.

it('recusa quando o aluno já tem 3 empréstimos ativos', () => {
  const aluno = { id: 'a1', ativos: ['l7', 'l8', 'l9'], multaPendente: 0 };

  const tentar = () => emprestar(aluno, livroLivre, hoje);

  assert.throws(tentar, /limite de 3 empréstimos ativos/);
});

O nome do teste diz a condição e o resultado esperado. Quando um teste falha no CI, o nome é a primeira linha que aparece: ✖ teste 3 obriga a abrir o arquivo, enquanto ✖ recusa quando o aluno tem multa pendente já diz qual regra quebrou.

VagoCom condição e resultado

teste 2aceita o empréstimo quando o aluno tem 2 ativos
multa oklimita a multa a 3000 centavos
caso reservaaceita livro reservado pelo próprio aluno

7. Prompt 1 · node:test e a função de sobreposição

30 min

Estamos no repositório organizacao-recursos, em JavaScript puro com ES modules e sem TypeScript. Crie a branch feat/intervalo. Garanta que o package.json tenha "type": "module" e o script "test": "node --test", sem nenhuma dependência de teste: use só node:test e node:assert/strict. Vamos implementar em TDD a função sobrepoe(a, b) em src/intervalo.js, que recebe dois intervalos { inicio, fim } com objetos Date e responde true quando eles se sobrepõem; um intervalo que termina exatamente quando o outro começa não se sobrepõe. Trabalhe em ciclos e pare ao fim de cada passo: 1) escreva um único teste novo em test/unidade/intervalo.test.js, rode npm test e me mostre a falha; 2) escreva o código mínimo para passar, rode npm test e mostre a saída verde; 3) proponha uma refatoração, se houver, e rode npm test de novo. Use o padrão Arrange, Act, Assert e nomes de teste que digam a condição e o resultado esperado. Não escreva o próximo teste antes de eu pedir.
Antes de aceitar: o vermelho tem que ser um AssertionError, não um erro de import. Commit por passo: test(intervalo), feat(intervalo), refactor(intervalo).

8. Prompt 2 · regras de conflito da reserva em TDD

35 min

Na branch feat/reserva, crie em TDD a função reservar(reservas, pedido, recursos) em src/reserva.js. O pedido tem { salaId, professorId, materiais, inicio, fim, alunos }; recursos traz as salas com capacidade e os materiais com disponibilidade. Implemente as regras uma por ciclo, nesta ordem: 1) recusa se a sala já tem reserva com intervalo sobreposto; 2) recusa se o número de alunos passa da capacidade da sala; 3) recusa se o professor já está em outra aula no mesmo horário, em qualquer sala; 4) recusa se algum material pedido está indisponível ou já reservado no horário. Recusa é um erro lançado com mensagem que diga a regra violada; sucesso devolve a reserva criada. Reaproveite sobrepoe de src/intervalo.js. Para cada regra escreva primeiro o teste que falha, depois o código mínimo, depois refatore, e pare ao fim de cada passo para eu commitar. Inclua o caso de fronteira de cada regra, como uma reserva que começa exatamente quando a outra termina e uma turma com o número exato da capacidade. Use assert.throws com a mensagem esperada. Nada de banco, rede ou arquivo nos testes.
Antes de aceitar: cada regra tem um teste que recusa e um que aceita no limite. Se o agente juntou duas regras no mesmo passo, peça para separar.

9. Prompt 3 · relógio injetado e revisão dos testes

20 min

Na branch feat/reserva-passado, acrescente em src/reserva.js a regra de que não se reserva no passado. A função reservar passa a receber um quarto parâmetro, agora, do tipo Date, e recusa pedidos cujo inicio seja anterior a agora. Faça em TDD, com testes que passam uma data fixa e não dependem do dia em que rodam. Se algum código precisar ler o relógio do sistema, isole essa leitura numa função pequena e teste essa função com t.mock.timers.enable({ apis: ['Date'], now: new Date('2027-02-24T19:00:00Z') }). Depois revise todos os arquivos de teste: renomeie testes cujo nome não diga condição e resultado, separe Arrange, Act e Assert com uma linha em branco e aponte qualquer teste que dependa de banco, rede, arquivo ou da data atual. Mostre a lista de mudanças antes de aplicar.
Antes de aceitar: rode node --test --test-name-pattern="passado" e procure new Date() sem argumento dentro de test/.

10. Entregável e checagem

src/intervalo.js e src/reserva.js com testes em test/unidade/, construídos em TDD e integrados na main com git merge --ff-only.

O que o professor confere na mesa

  • O git log --oneline mostra o trio test, feat, refactor em cada regra.
  • Um commit test(...) aberto com git show contém só teste.
  • npm test fica verde e nenhum teste usa new Date() sem argumento.
  • Os nomes na saída do npm test explicam cada regra sem abrir o código.
