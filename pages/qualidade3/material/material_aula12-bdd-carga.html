BDD e testes de carga

Objetivo da aula

Sair da aula com cenários BDD em português, nascidos dos critérios de aceite da sua spec e executados pela API com cucumber-js, e com um teste de carga no k6 que reprova quando a meta de desempenho do docs/qualidade.md não é cumprida.

É a última aula de conteúdo antes da entrega do Trabalho 2, na semana 17. Como nas aulas anteriores, o código das demonstrações é gerado pelo agente a partir de um prompt, e cada laboratório mostra o que o aluno confere antes de aceitar: o diff, a execução dos cenários e o resumo do k6. O professor demonstra no repositório biblioteca-campus; você aplica no seu organizacao-recursos.

Os prompts desta página servem para o chat do GitHub Copilot no modo Agent, o agente padrão da disciplina, e também para o opencode (opencode run "..."). Os comandos opencode run que aparecem nos exemplos equivalem a colar o mesmo pedido no chat do Copilot.

1. Exemplo como especificação

Um critério de aceite como "com 3 empréstimos ativos, o pedido é recusado" ainda deixa perguntas: recusado com qual mensagem? E com 2 empréstimos? Behavior-Driven Development (BDD) responde reescrevendo cada critério como um exemplo concreto, com nomes e números, numa linguagem que quem escreveu a spec consegue ler e que uma ferramenta consegue executar.

## Critérios de aceite (specs/emprestimo.md)
- CA-01 Com menos de 3 empréstimos ativos, o aluno
  pega o livro e a devolução prevista é hoje + 14 dias.
- CA-02 Com 3 empréstimos ativos, o pedido é recusado.
- CA-03 Livro reservado por outro aluno não sai.
- CA-04 Aluno com multa pendente não pega livro.
# CA-02
Cenário: Quarto empréstimo é recusado
  Dado que "Ana" tem 3 empréstimos ativos
  Quando "Ana" pede o livro "Clean Code"
  Então o empréstimo é recusado com a mensagem
        "limite de 3 empréstimos ativos"

O mesmo arquivo cumpre três papéis. Na conversa, o exemplo tira a ambiguidade antes do código existir. Como documentação, ele descreve o comportamento e falha quando deixa de ser verdade. Como teste de aceitação, ele roda pela API, do jeito que um cliente usa o sistema, acima dos testes de unidade da Aula 04. Os cenários não substituem as técnicas de caixa preta da Aula 03: são elas que escolhem quais exemplos valem a pena.

As frases ficam no ponto de vista de quem usa. Na demonstração, o agente gera este arquivo a partir de specs/emprestimo.md, e o aluno confere com grep -c '# CA-' que cada critério tem cenário.

3. Configurar o cucumber-js

O @cucumber/cucumber e o supertest são dependências de teste e entram em devDependencies. Na demonstração, o agente os instalou em dependencies e anunciou que estava tudo pronto; só o git diff package.json mostrou o erro. A configuração fica em cucumber.js, na raiz. Num projeto com "type": "module", os arquivos de passos são carregados pela chave import.

npm install --save-dev @cucumber/cucumber supertest

const comum = {
  paths: ['features/**/*.feature'],
  import: ['features/support/**/*.js', 'features/step_definitions/**/*.js'],
};

// perfil padrão: tudo o que está pronto, com relatório HTML

  ...comum,

4. World e step definitions com supertest

O cucumber-js cria um objeto World novo para cada cenário, e ele é o this de todos os passos daquele cenário. Por isso o estado não vaza: o empréstimo criado num cenário não existe no seguinte. O World da demonstração monta o app Express com o repositório em memória e um relógio fixo, injetados como os dublês da Aula 11, e o supertest faz a requisição direto no app, sem abrir porta.

// features/support/world.js
import { setWorldConstructor, World } from '@cucumber/cucumber';
import request from 'supertest';
import { criarApp } from '../../src/app.js';
import { criarRepoMemoria } from '../../src/repo-memoria.js';

class MundoBiblioteca extends World {
  constructor(options) {
    super(options);
    this.repo = criarRepoMemoria();
    this.hoje = new Date('2027-01-01');
    this.app = criarApp({ repo: this.repo, relogio: () => this.hoje });
    this.resposta = null;
  }

  api() {
    return request(this.app);
  }
}

setWorldConstructor(MundoBiblioteca);

Cada step definition casa com uma frase por uma expressão do Cucumber: {string} captura um texto entre aspas e {int} um número inteiro.

// features/step_definitions/emprestimo.steps.js (trecho)
import { Given, When, Then } from '@cucumber/cucumber';
import assert from 'node:assert/strict';

Given('que {string} tem {int} empréstimos ativos', async function (aluno, n) {
  for (let i = 1; i <= n; i++) {
    await this.repo.salvarEmprestimo({ aluno, livro: 'Livro ' + i, devolvido: null });
  }
});

When('{string} pede o livro {string}', async function (aluno, livro) {
  this.resposta = await this.api().post('/emprestimos').send({ aluno, livro });
});

Then('o empréstimo é recusado com a mensagem {string}', function (mensagem) {
  assert.equal(this.resposta.status, 422);
  assert.equal(this.resposta.body.erro, mensagem);
});

Na saída do formato progress, cada passo vira um símbolo: . passou, F falhou, U indefinido, - pulado. Um passo sem step definition aparece com ? e com o snippet pronto para implementar:

5. Esquema do Cenário e Exemplos

Quando a mesma regra precisa de vários valores, o Esquema do Cenário evita copiar cenários. As linhas da tabela vêm da análise de valor-limite: no dia, um dia antes, um dia depois, exatamente no teto (20 dias de atraso, 3000 centavos), um dia depois do teto e muito depois.

# language: pt
@multa
Funcionalidade: Multa por atraso
  Regra da spec: 150 centavos por dia de atraso, com teto de 3000 centavos.

  Esquema do Cenário: Multa calculada na devolução
    Dado um empréstimo com devolução prevista para "<previsto>"
    Quando o livro é devolvido em "<devolvido>"
    Então a multa é de <multa> centavos

    Exemplos:
      | previsto   | devolvido  | multa |
      | 2027-05-04 | 2027-05-04 | 0     |
      | 2027-05-04 | 2027-05-03 | 0     |
      | 2027-05-04 | 2027-05-05 | 150   |
      | 2027-05-04 | 2027-05-24 | 3000  |
      | 2027-05-04 | 2027-05-25 | 3000  |
      | 2027-05-04 | 2027-06-30 | 3000  |

Nem todo cenário precisa passar pela API. A multa é uma função pura, então os passos chamam calcularMulta direto. Na demonstração, a linha da devolução antecipada falhou com -150 !== 0, e o agente ofereceu trocar a multa esperada para -150. Aceitar faria o teste passar e o arquivo passaria a contradizer a spec. A resposta foi não, e a correção foi no código:

export function calcularMulta(previsto, devolvido) {
  const dias = Math.ceil((new Date(devolvido) - new Date(previsto)) / 86_400_000);
  if (dias <= 0) return 0;
  return Math.min(dias * 150, 3000);
}

6. Tags, perfis e relatório

Uma funcionalidade ainda sem passos recebe @wip (work in progress). O perfil padrão do cucumber.js usa tags: 'not @wip', então npm run bdd continua verde na main. O perfil wip roda só o que está em construção. Por padrão o cucumber-js trata passo indefinido como falha: o comando sai com código 1, e por isso um cenário incompleto sem a tag quebra o CI.

npm run bdd                              # perfil padrão: not @wip, gera relatorios/cucumber.html
npx cucumber-js -p wip                   # só @wip
npx cucumber-js --tags "@multa"          # só a multa
npx cucumber-js --tags "@emprestimo and not @lento"
npx cucumber-js --dry-run                # confere frases e passos sem executar

O formato html:relatorios/cucumber.html grava um relatório navegável com cada passo e o erro de cada falha. Ponha relatorios/ no .gitignore: o relatório é gerado, não versionado.

7. Tipos de teste de carga

Teste de carga mede a eficiência de desempenho da ISO/IEC 25010 com usuários virtuais (VUs) fazendo requisições ao mesmo tempo. O script pode ser o mesmo; o que muda é o perfil de VUs ao longo do tempo e a pergunta respondida.

TipoPerfilPergunta
Smoke1 VU por 30 sO script e a API funcionam? Erro aqui é de script ou de API, não de carga.
Cargasobe até a carga esperada, mantém, desceA meta vale no uso normal?
Estressedegraus acima do esperadoOnde o sistema degrada e como ele falha?
Picosalto súbito de usuáriosAguenta a abertura do semestre e se recupera depois?
Resistência (soak)carga normal por horasHá vazamento de memória, de conexões ou de disco?

Estresse e pico costumam reprovar os thresholds, e isso é esperado: o resultado útil é saber a partir de quantos usuários a vazão para de crescer e qual erro aparece. Na demonstração, acima de cerca de 200 VUs, o pool do PostgreSQL recusou conexões.

8. Métricas

  • Vazão: http_reqs por segundo. Para de subir quando o sistema satura.
  • p95: percentil 95 de http_req_duration. 95% das requisições terminaram até esse tempo; uma em cada 20 demorou mais.
  • p99: percentil 99, a cauda que um em cada 100 usuários sente. O k6 só mostra se você pedir em summaryTrendStats.
  • Taxa de erro: http_req_failed, fração de respostas fora de 200 a 399 ou sem resposta.

A média esconde a cauda. Com 100 requisições, 95 em 50 ms e 5 em 2000 ms, a média dá 147,5 ms e parece confortável diante de uma meta de 300 ms. O p95 é 50 ms e o p99 é 2000 ms: cinco usuários em cada cem esperaram dois segundos. Por isso os requisitos da Aula 01 usam percentil.

9. k6: script, checks e thresholds

O k6 roda scripts em JavaScript, mas não é Node: ele tem módulos próprios (k6/http, k6) e lê variáveis de ambiente por __ENV. Ele já vem instalado no Codespace da disciplina; confira com k6 version.

// carga/busca.js
import http from 'k6/http';
import { check, sleep } from 'k6';

const BASE = __ENV.BASE_URL || 'http://localhost:3000';

export const options = {
  stages: [
    { duration: '30s', target: 50 }, // subida
    { duration: '1m', target: 50 },  // patamar: a carga do requisito
    { duration: '15s', target: 0 },  // descida
  ],
  thresholds: {
    http_req_duration: ['p(95)<300'], // meta do docs/qualidade.md
    http_req_failed: ['rate<0.01'],
    checks: ['rate>0.99'],
  },
  summaryTrendStats: ['avg', 'med', 'p(90)', 'p(95)', 'p(99)', 'max'],
};

const TERMOS = ['clean', 'teste', 'banco', 'redes', 'algoritmos'];

export default function () {
  const termo = TERMOS[Math.floor(Math.random() * TERMOS.length)];
  const res = http.get(BASE + '/livros?busca=' + termo, { tags: { name: 'GET /livros' } });
  check(res, {
    'status 200': (r) => r.status === 200,
    'corpo é uma lista': (r) => Array.isArray(r.json()),
  });
  sleep(1);
}
  • stages descreve o perfil: cada estágio leva o número de VUs até target em duration. Para smoke, use vus: 1 e duration: '30s'.
  • check registra acertos e erros, mas sozinho não reprova nada. Quem reprova é um threshold sobre checks.
  • thresholds são os critérios de aprovação. Se algum cruzar, o k6 marca ✗ e sai com código 99, o que derruba um script ou um job de CI.
  • Um único script pode guardar vários perfis num objeto e escolher por variável: k6 run -e PERFIL=pico carga/perfis.js chega ao script como __ENV.PERFIL.

Na demonstração, o agente escreveu p(95)<500 com o comentário "meta do docs/qualidade.md", mas a meta é 300 ms. O grep nos dois arquivos mostrou a diferença. Com 500, a execução sem o índice da busca teria passado.

11. Prompt 1 · cenários a partir dos critérios de aceite

25 min

Leia a especificação em specs/ deste repositório organizacao-recursos, em especial os critérios de aceite da reserva de salas, professores e materiais. Crie features/reserva.feature começando com # language: pt, com uma Funcionalidade que diga quem usa e para quê, um Contexto com os dados comuns a todos os cenários e um Cenário por critério de aceite, cada um precedido de um comentário com o identificador do critério (por exemplo # CA-03). Inclua um Esquema do Cenário com Exemplos para os limites de horário: reserva que termina exatamente quando a outra começa, sobreposição de um minuto e reserva dentro de outra. Escreva as frases do ponto de vista de quem usa o sistema, sem rotas, SQL ou nomes de função, e use um único Quando por cenário. Não crie step definitions nem altere código em src/.
Antes de aceitar: todo critério de aceite da spec tem pelo menos um cenário, e nenhum cenário cita rota, tabela ou função.

12. Prompt 2 · cucumber.js, World e step definitions

30 min

Instale @cucumber/cucumber e supertest como devDependencies. Crie cucumber.js como ES module, com export default contendo paths ['features/**/*.feature'], import ['features/support/**/*.js', 'features/step_definitions/**/*.js'], format ['progress', 'html:relatorios/cucumber.html'] e tags 'not @wip', e um perfil exportado wip com tags '@wip'. Adicione o script "bdd": "cucumber-js" ao package.json e relatorios/ ao .gitignore. Crie features/support/world.js com uma classe que estende World e monta o app Express de src/app.js com repositório em memória e relógio fixo, para cada cenário começar com estado limpo. Crie as step definitions em features/step_definitions/, chamando a API com supertest sem subir servidor e verificando com node:assert/strict. Não altere as frases dos arquivos .feature para facilitar os passos. Rode npm run bdd e mostre a saída completa.
Antes de aceitar: rode npm run bdd duas vezes e compare. Depois quebre uma regra em src/ e confira que um cenário falha.

13. Prompt 3 · teste de carga com a meta do docs/qualidade.md

25 min

Leia docs/qualidade.md e encontre o requisito de eficiência de desempenho. Crie carga/busca.js para o k6, em JavaScript, que exercite a consulta de disponibilidade de salas da API deste repositório. Use BASE_URL vindo de __ENV com padrão http://localhost:3000, options.stages com subida, patamar e descida até o número de usuários do requisito, thresholds http_req_duration com p(95) igual à meta do docs/qualidade.md e http_req_failed com rate<0.01, e checks de status 200 e de corpo em JSON. Comente cada estágio dizendo por que ele existe. Adicione o script "carga": "k6 run carga/busca.js" ao package.json. Se a meta ou o número de usuários não estiver no docs/qualidade.md, pare e me pergunte em vez de inventar.
Antes de aceitar: o número do threshold é o mesmo do docs/qualidade.md e a URL aponta para localhost. Anote o p(95) obtido no corpo do commit.
