Cobertura, CI e análise estática

Objetivo da aula

Sair da aula com cobertura medida e com meta, ESLint configurado e um workflow do GitHub Actions que roda lint e testes a cada push na main do organizacao-recursos.

É a última aula de conteúdo antes da entrega do Trabalho 1, na semana 10. Como nas aulas anteriores, o agente gera a configuração e o código a partir de prompts, e a etapa de qualidade é a revisão de quem pediu: ler o diff, rodar os comandos e só então commitar. A seção 11 traz o checklist da entrega.

Os prompts desta página servem para o chat do GitHub Copilot no modo Agent, o agente padrão da disciplina, e também para o opencode (opencode run "..."). Os comandos opencode run que aparecem nos exemplos equivalem a colar o mesmo pedido no chat do Copilot.

1. O que a cobertura mede

Enquanto os testes rodam, o Node registra que partes do código foram executadas. O relatório responde a uma pergunta: que código nenhum teste chegou a rodar?

  • Linhas: fração das linhas executadas pelo menos uma vez.
  • Ramos: fração dos caminhos de cada decisão (if, else, &&, ||, ?:) que algum teste percorreu. Um if testado só no caso verdadeiro deixa um ramo descoberto.
  • Funções: fração das funções chamadas por algum teste.

A cobertura de ramos é a medida automática da caixa branca da Aula 03: cada ramo descoberto corresponde a um caso de teste que a análise de caminhos teria pedido.

2. Cobertura nativa do Node e metas

O Node 22 mede cobertura sem dependência extra, com --experimental-test-coverage. Sem filtro, os próprios arquivos de teste entram na conta e puxam a média para cima, por isso a disciplina usa --test-coverage-include='src/**'. As opções --test-coverage-lines e --test-coverage-branches transformam a medida em meta: abaixo do valor, o comando termina com código 1, mesmo que todos os testes passem.

"scripts": {
  "test": "node --test",
  "test:cov": "node --test --experimental-test-coverage --test-coverage-lines=80 --test-coverage-branches=80 --test-coverage-include='src/**'",
  "lint": "eslint ."
}

No laboratório, o script foi pedido assim, e a conferência veio antes do commit:

opencode run "Adicione ao package.json o script test:cov com cobertura nativa do Node, meta de 80% de linhas e de ramos e só src/ na conta. Nenhuma dependência nova."

3. Ler o relatório e achar os ramos descobertos

A coluna uncovered lines aponta as linhas que nenhum teste executou. Em src/emprestimo.js, as linhas 9-10 e 15-16 são as duas recusas que os testes nunca provocam:

 8  if (aluno.multaPendente > 0) {
 9    throw new Error('aluno com multa pendente');
10  }
11  if (aluno.ativos.length >= LIMITE_ATIVOS) {
12    throw new Error('limite de 3 empréstimos ativos');
13  }
14  if (livro.reservadoPor && livro.reservadoPor !== aluno.id) {
15    throw new Error('livro reservado por outro aluno');
16  }

Há também um ramo que não aparece como linha: o lado direito do && da linha 14 nunca é avaliado, porque nenhum teste usa livro reservado. Ele só aparece na porcentagem de ramos. O agente pode ler o relatório e listar as regras correspondentes; a conferência é abrir as linhas citadas (por exemplo, sed -n '8,16p' src/emprestimo.js) e ver se a regra descrita é a que está lá.

Os testes que fecham esses ramos precisam conferir a mensagem do erro ou o valor retornado, e o git diff deles não pode tocar em src/. Com eles, a tabela foi a 100% de linhas, ramos e funções e o comando terminou com código 0.

4. Por que 100% de cobertura não prova correção

A cobertura mede o que foi executado, não o que foi conferido. No laboratório, src/multa.js estava com 100% de linhas, ramos e funções e mesmo assim errado:

return Math.max(atraso * MULTA_POR_DIA, TETO_MULTA);   // a regra pede Math.min

it('calcula multa com atraso', () => {
  const multa = calcularMulta(previsto, new Date('2027-03-11T12:00:00Z'));
  assert.ok(multa > 0);
});

Com 3 dias de atraso a função devolvia 3000 centavos em vez de 450, e o teste passava, já que só exigia um valor positivo. A troca por valores exatos (0 no prazo, 450 com 3 dias, 3000 com 20 dias, 3000 com 25 dias) fez o teste falhar com 3000 !== 450; a correção para Math.min o deixou verde.

  • Fronteiras: > e >= produzem a mesma cobertura. Só um teste exatamente no limite distingue os dois.
  • Regra esquecida: se a especificação pede um teto e o código não tem teto, não existe linha descoberta para avisar.
  • Asserção fraca: assert.ok no lugar do valor exato executa o código sem verificar o resultado.

Por isso a meta de 80% é um piso. A cobertura serve de alarme para código que nenhum teste rodou; a verificação da regra depende da asserção, e lê-la é trabalho de revisão, inclusive nos testes gerados pelo agente.

5. Análise estática com ESLint 9

Análise estática examina o código sem executá-lo. O ESLint 9 usa o formato flat: um arquivo eslint.config.js que exporta um array de configurações. As dependências de desenvolvimento são eslint, @eslint/js e globals.

npm install -D eslint @eslint/js globals
import js from '@eslint/js';
import globals from 'globals';

export default [
  { ignores: ['coverage/', 'node_modules/'] },
  js.configs.recommended,
  {
    languageOptions: {
      ecmaVersion: 2024,
      sourceType: 'module',
      globals: globals.node
    },
    rules: {
      complexity: ['error', 6]
    }
  }
];

O conjunto recommended aponta variável sem uso, nome não declarado, código inalcançável e chave duplicada. A regra complexity conta os caminhos independentes de cada função: cada if, &&, || e case soma 1. Uma função de complexidade 7 exige pelo menos 7 testes para cobrir todos os ramos; o limite de 6 obriga a quebrá-la antes.

/workspaces/biblioteca-campus/src/situacao-aluno.js
  1:10  error  'calcularMulta' is defined but never used  no-unused-vars
  1:25  error  'PRAZO_DIAS' is defined but never used     no-unused-vars
  3:8   error  Function 'situacaoDoAluno' has a complexity of 7. Maximum allowed is 6  complexity

✖ 3 problems (3 errors, 0 warnings)

A correção pedida ao agente tirou os imports sem uso, extraiu estaBloqueado e trocou o aninhamento por retornos antecipados:

function estaBloqueado(aluno) {
  return aluno.bloqueado || aluno.multaPendente >= TETO_MULTA;
}

export function situacaoDoAluno(aluno, hoje) {
  if (estaBloqueado(aluno)) return 'bloqueado';
  if (aluno.multaPendente > 0) return 'com multa';
  if (aluno.ativos.length >= LIMITE_ATIVOS) return 'no limite';
  if (aluno.ativos.some((e) => e.previsto < hoje)) return 'com atraso';
  if (aluno.ativos.length === 0) return 'sem empréstimos';
  return 'regular';
}

Um agente pressionado a zerar o lint pode resolver com um comentário // eslint-disable. A revisão é git grep -n "eslint-disable", que precisa voltar vazio, seguida de npm run lint && npm test.

6. GitHub Actions no seu repositório

Integração contínua roda as verificações numa máquina limpa a cada push. O workflow fica em .github/workflows/ci.yml, no repositório de cada aluno:

name: CI

on:
  push:
  workflow_dispatch:

jobs:
  qualidade:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm
      - run: npm ci
      - run: npm run lint
      - run: npm run test:cov

npm ci instala exatamente as versões do package-lock.json e falha se ele não estiver em sincronia com o package.json. Qualquer passo que termine com código diferente de 0 encerra o job em vermelho. workflow_dispatch permite rodar o workflow pelo botão Run workflow da aba Actions.

O badge no topo do README mostra o estado do último run:

![CI](https://github.com/MEU-USUARIO/organizacao-recursos/actions/workflows/ci.yml/badge.svg)

No terminal do Codespace, gh run watch acompanha o run do último push e gh run view --log-failed mostra só o log dos passos que falharam.

7. A regra da main e o CI vermelho

  • A main só recebe merge local, com git merge --ff-only, depois de npm run lint && npm run test:cov verdes na branch.
  • Não há pull request: o CI roda no push da main e verifica o que já foi integrado.
  • Um push que deixa o CI vermelho vira um commit fix imediato, antes de qualquer outra mudança.

No laboratório, o gate local passou e o CI falhou no npm ci: o commit do ESLint levou o package.json, mas o package-lock.json atualizado ficou só no Codespace. Localmente o node_modules já existia; na máquina limpa do GitHub, não.

npm error `npm ci` can only install packages when your package.json and package-lock.json are in sync.
npm error Missing: eslint@9.17.0 from lock file

O agente diagnosticou a causa a partir do log. A conferência foi git status --short, que mostrou o lock modificado, e npm ci && npm run lint && npm run test:cov antes do commit:

git switch -c fix/lock
git commit -am "fix(ci): versiona package-lock.json com o eslint"
git switch main
git merge --ff-only fix/lock
git push
gh run watch

Na correção de trabalhos, o professor clona a main. Um badge vermelho na entrega significa que o que está lá não passa nas próprias verificações do aluno.

8. Quality gate sem SonarCloud

O SonarCloud junta várias análises num painel e reprova o código que não atinge as metas. A disciplina monta o mesmo gate com bibliotecas Node, que rodam na sua máquina e no GitHub Actions, sem conta nem token externo. O gate fica versionado no repositório, então qualquer mudança nele aparece no histórico.

npm install -D eslint-plugin-sonarjs eslint-plugin-security jscpd secretlint \
  @secretlint/secretlint-rule-preset-recommend knip
// eslint.config.js
import js from '@eslint/js';
import globals from 'globals';
import sonarjs from 'eslint-plugin-sonarjs';
import pluginSecurity from 'eslint-plugin-security';

export default [
  { ignores: ['coverage/', 'node_modules/'] },
  js.configs.recommended,
  sonarjs.configs.recommended,
  pluginSecurity.configs.recommended,
  {
    languageOptions: { ecmaVersion: 2024, sourceType: 'module', globals: globals.node },
    rules: { complexity: ['error', 8], 'sonarjs/cognitive-complexity': ['error', 15] }
  }
];
// package.json (scripts)
"lint": "eslint .",
"dup": "jscpd",
"segredos": "secretlint \"**/*\"",
"morto": "knip",
"auditoria": "npm audit --audit-level=high",
"qualidade": "npm run lint && npm run dup && npm run segredos && npm run morto && npm run auditoria && npm run test:cov"

O .jscpd.json define "path": ["src"] e "threshold": 3; o .secretlintrc.json ativa o preset @secretlint/secretlint-rule-preset-recommend.

No CI, cada verificação vira um passo com id e continue-on-error: true. Assim todas rodam mesmo quando a primeira falha, o resumo mostra todas, e o último passo reprova o run se alguma falhou:

      - { id: lint,      run: npm run lint,      continue-on-error: true }
      - { id: dup,       run: npm run dup,       continue-on-error: true }
      - { id: segredos,  run: npm run segredos,  continue-on-error: true }
      - { id: morto,     run: npm run morto,     continue-on-error: true }
      - { id: auditoria, run: npm run auditoria, continue-on-error: true }
      - { id: cobertura, run: npm run test:cov,  continue-on-error: true }
      - name: Resumo do quality gate
        if: always()
        run: |
          {
            echo "## Quality gate"
            echo "| Verificação | Resultado |"
            echo "|---|---|"
            echo "| ESLint, sonarjs e security | ${{ steps.lint.outcome }} |"
            echo "| Duplicação (jscpd, 3%) | ${{ steps.dup.outcome }} |"
            echo "| Segredos (secretlint) | ${{ steps.segredos.outcome }} |"
            echo "| Código morto (knip) | ${{ steps.morto.outcome }} |"
            echo "| Dependências (npm audit) | ${{ steps.auditoria.outcome }} |"
            echo "| Cobertura 80% | ${{ steps.cobertura.outcome }} |"
          } >> "$GITHUB_STEP_SUMMARY"
      - name: Reprovar se alguma verificação falhou
        if: contains(join(steps.*.outcome, ','), 'failure')
        run: exit 1

9. Prompt 1 · cobertura com meta

30 min

Na branch test/cobertura do repositório organizacao-recursos, adicione ao package.json o script "test:cov": "node --test --experimental-test-coverage --test-coverage-lines=80 --test-coverage-branches=80 --test-coverage-include='src/**'", sem nenhuma dependência nova. Rode npm run test:cov e me mostre a tabela. Liste, arquivo por arquivo, as linhas e os ramos não cobertos e diga qual regra do domínio cada um representa (sobreposição de intervalos, capacidade da sala, professor em duas aulas, material indisponível, reserva no passado). Depois, um teste por vez, escreva testes que cubram esses ramos com asserção de valor exato ou da mensagem de erro, sem alterar nada em src/ e sem excluir arquivos da cobertura. Pare depois de cada teste para eu rodar npm run test:cov e commitar como test(escopo): ....
Antes de aceitar: todo teste novo confere valor ou mensagem, nada de assert.ok genérico, e o git diff não toca em src/.

10. Prompt 2 · ESLint no seu repositório

20 min

Na branch chore/eslint, instale como devDependencies eslint, @eslint/js e globals. Crie eslint.config.js no formato flat do ESLint 9, exportando um array com: ignores para coverage/ e node_modules/; js.configs.recommended; e um bloco com languageOptions { ecmaVersion: 2024, sourceType: 'module', globals: globals.node } e a regra complexity: ['error', 6]. Adicione o script "lint": "eslint .". Rode npm run lint e me mostre os problemas agrupados por regra. Corrija um arquivo por vez, sem usar comentários eslint-disable e sem desligar regras; para complexidade, extraia funções pequenas ou use retornos antecipados. Rode npm test depois de cada correção e pare para eu commitar.
Antes de aceitar: git grep eslint-disable vazio, package-lock.json no commit e npm test verde depois de cada refatoração.

11. Prompt 3 · workflow de CI e badge

25 min

Na branch chore/ci, crie .github/workflows/ci.yml com name CI, disparado em push e workflow_dispatch, com um job qualidade em ubuntu-latest e os passos: actions/checkout@v4; actions/setup-node@v4 com node-version 22 e cache npm; npm ci; npm run lint; npm run test:cov. Acrescente no topo do README.md o badge ![CI](https://github.com/MEU-USUARIO/organizacao-recursos/actions/workflows/ci.yml/badge.svg), perguntando antes qual é o meu usuário do GitHub. Não crie pull request nem outros workflows. Antes de terminar, rode npm ci, npm run lint e npm run test:cov localmente e me mostre o resultado de cada um.
Antes de aceitar: rode você mesmo npm run lint && npm run test:cov, faça o merge --ff-only, o push e acompanhe com gh run watch. Vermelho vira commit fix na hora.

12. Prompt 4 · quality gate no seu repositório

25 min

Na branch chore/quality-gate do repositório organizacao-recursos, monte um quality gate que substitua o SonarCloud. Instale como devDependencies eslint-plugin-sonarjs, eslint-plugin-security, jscpd, secretlint, @secretlint/secretlint-rule-preset-recommend e knip. No eslint.config.js, acrescente sonarjs.configs.recommended e pluginSecurity.configs.recommended, com a regra sonarjs/cognitive-complexity limitada a 15, mantendo complexity 8. Crie .jscpd.json com path ["src"], threshold 3 e reporters console e markdown, e .secretlintrc.json com o preset recomendado. Adicione ao package.json os scripts dup (jscpd), segredos (secretlint "**/*"), morto (knip), auditoria (npm audit --audit-level=high) e qualidade, que roda lint, dup, segredos, morto, auditoria e test:cov nessa ordem. No .github/workflows/ci.yml, transforme cada verificação num passo com id e continue-on-error: true, escreva em $GITHUB_STEP_SUMMARY uma tabela com o outcome de cada passo e termine com um passo que falha se algum outcome for failure. Rode npm run qualidade e corrija o que reprovar sem desligar regra, sem eslint-disable e sem subir o threshold. Mostre o diff antes de cada commit.
Antes de aceitar: git grep eslint-disable vazio, threshold do jscpd em 3 e o resumo do run mostrando as seis verificações.

13. Checklist do Trabalho 1

A entrega é na semana 10, pelo link do repositório público, e a prova oral acontece nas semanas 11, 12 e 13. O trabalho é individual. Antes de entregar, confira:

Conteúdo do repositório

  • docs/qualidade.md com requisitos mensuráveis (Aula 01).
  • Especificação e critérios de aceite (Aula 02).
  • Casos de teste de caixa preta e de caixa branca (Aula 03).
  • Regras de reserva feitas em TDD, com o trio test, feat, refactor no histórico (Aula 04).
  • npm run test:cov com pelo menos 80% de linhas e de ramos em src/.
  • npm run lint sem erros e sem eslint-disable.
  • npm run qualidade verde e o resumo do quality gate no run do CI.

Estado no GitHub

  • Repositório público organizacao-recursos, com README e badge do CI.
  • Último run da main verde na aba Actions.
  • Histórico linear, Conventional Commits em português e branches curtas apagadas.
  • Issues de feedback respondidas com fix(...): ... (#N) e Closes #N.
  • Qualquer commit pode ser explicado na prova oral, inclusive os gerados com o agente.
