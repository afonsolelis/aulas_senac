Ambiente no Codespaces e introdução à qualidade

Objetivo da aula

Sair da aula com um repositório público, um Codespace funcionando, o opencode respondendo por um modelo da OpenRouter e um primeiro documento de requisitos de qualidade integrado na main.

O primeiro bloco é demonstração: o professor mostra cada passo em simulações do GitHub e do VS Code. O segundo bloco é laboratório: cada aluno repete os passos no próprio repositório, com os dois prompts desta página.

1. Como a disciplina funciona

  • Todo o trabalho é individual. Não há grupos em nenhuma etapa.
  • Há dois trabalhos. Cada um é entregue pelo link do repositório público no GitHub, com nome completo, no formulário de entrega da home. Depois da entrega vêm três dias de prova oral, em que o aluno explica o próprio código e o próprio histórico de commits.
  • Correção e feedback acontecem no GitHub: o professor abre issues no seu repositório. A resposta é um commit que cita a issue, por exemplo fix(cep): trata CEP com hífen (#4), com Closes #4 no corpo da mensagem para fechá-la quando chegar à main.
  • Não usamos pull request, já que ninguém revisa o código de outra pessoa. O que vale é o histórico da main.

2. GitHub Codespaces

Um Codespace é uma máquina virtual do GitHub com o VS Code aberto no navegador. A configuração fica no próprio repositório, em .devcontainer/devcontainer.json, então qualquer pessoa que abrir um Codespace recebe o mesmo Node, as mesmas extensões e as mesmas ferramentas. A conta gratuita do GitHub tem uma cota mensal de horas; pare o Codespace quando terminar (menu Codespaces › Stop) para não gastá-la à toa.

Passo a passo

  1. Em github.com/new, crie o repositório organizacao-recursos, público, com README.
  2. No repositório, clique em <> Code, aba Codespaces, Create codespace on main.
  3. Quando o VS Code abrir, use Ctrl + ` para abrir o terminal e confira node --version.
  4. Instale o opencode: curl -fsSL https://opencode.ai/install | bash. Depois do prompt 1, o devcontainer passa a instalar sozinho a cada Codespace novo.
{
  "name": "organizacao-recursos",
  "image": "mcr.microsoft.com/devcontainers/javascript-node:1-22-bookworm",
  "features": { "ghcr.io/devcontainers/features/docker-in-docker:2": {} },
  "postCreateCommand": "curl -fsSL https://opencode.ai/install | bash",
  "secrets": {
    "OPENROUTER_API_KEY": { "description": "Chave da OpenRouter usada pelo opencode" }
  },
  "customizations": { "vscode": { "extensions": ["dbaeumer.vscode-eslint"] } }
}

A feature docker-in-docker será usada na Aula 10, quando os testes de integração subirem um PostgreSQL de verdade dentro do Codespace.

3. opencode com OpenRouter

O opencode é um agente de código que roda no terminal. Ele lê os arquivos do repositório, propõe mudanças e executa comandos, sempre pedindo permissão. A OpenRouter é um intermediário que dá acesso a modelos de vários fornecedores com uma única chave e um único saldo.

  1. Em openrouter.ai/settings/keys, crie uma chave chamada codespaces-qualidade-2027 com limite de crédito. Copie a chave na hora: ela não aparece de novo.
  2. No GitHub, em Settings › Codespaces › Secrets, crie o secret OPENROUTER_API_KEY com a chave como valor e libere o acesso só para organizacao-recursos.
  3. Volte ao Codespace e aceite o aviso "Reload to apply". Confira com echo ${OPENROUTER_API_KEY:0:8}: deve aparecer sk-or-v1.
  4. Rode opencode auth login, escolha OpenRouter e confirme. Depois, opencode abre o agente; opencode run "pergunta" responde sem abrir a interface.
{
  "$schema": "https://opencode.ai/config.json",
  "model": "openrouter/qwen/qwen3-coder",
  "provider": {
    "openrouter": {
      "options": { "apiKey": "{env:OPENROUTER_API_KEY}" }
    }
  }
}

O opencode.json vai para o repositório porque não contém segredo: {env:OPENROUTER_API_KEY} manda o opencode ler a variável de ambiente que o secret do Codespaces criou. Para ver os modelos disponíveis, use opencode models openrouter; a OpenRouter também oferece modelos gratuitos, marcados com :free no nome, com limite de uso diário.

A chave nunca vai para arquivo, print, issue ou prompt. Se ela aparecer em qualquer commit, revogue-a na OpenRouter na mesma hora e crie outra: apagar o commit não basta, porque o histórico público já foi copiado.

4. Alternativa local: OpenLLM

Quem tem computador com GPU pode servir um modelo aberto localmente com o OpenLLM e ligar o opencode a ele, sem chave e sem custo por token. O OpenLLM expõe uma API compatível com a da OpenAI em http://localhost:3000/v1, e o opencode conversa com ela pelo pacote @ai-sdk/openai-compatible. O Codespace gratuito não tem GPU, por isso em sala usamos a OpenRouter.

pip install openllm
openllm serve qwen2.5:7b
"provider": {
  "openrouter": { "options": { "apiKey": "{env:OPENROUTER_API_KEY}" } },
  "openllm": {
    "npm": "@ai-sdk/openai-compatible",
    "name": "OpenLLM (local)",
    "options": { "baseURL": "http://localhost:3000/v1" },
    "models": { "qwen2.5:7b": { "name": "Qwen 2.5 7B" } }
  }
}

Com os dois provedores no arquivo, escolha o modelo na hora: opencode run -m openllm/qwen2.5:7b "..." usa o local; sem -m, vale o model padrão.

5. O projeto Node criado pelo agente

Na disciplina, o código e a configuração são gerados por LLM. O aluno escreve o pedido, acompanha as ferramentas que o agente usa e revisa o resultado antes de commitar. A demonstração mostra o opencode criando o projeto Node do zero: package.json com ES modules e os scripts test, test:cov e lint, o ESLint 9 em flat config, uma função e dois testes em node:test.

  1. Abra uma branch curta: git switch -c chore/projeto-node.
  2. Rode o prompt 2 desta página no opencode. O agente lê o AGENTS.md, escreve os arquivos e pede permissão antes do npm install.
  3. Leia o resultado com git status e git diff. Na demonstração, o agente trocou o script de teste por jest, contrariando o AGENTS.md; a correção foi pedida a ele mesmo, num segundo prompt.
  4. Rode npm run lint && npm test você mesmo. Só então faça o commit e integre na main.
{
  "name": "organizacao-recursos",
  "type": "module",
  "scripts": {
    "test": "node --test",
    "test:cov": "node --test --experimental-test-coverage --test-coverage-include='src/**'",
    "lint": "eslint ."
  },
  "engines": { "node": ">=22" }
}

6. Git com branches curtas

Usamos desenvolvimento baseado em tronco (trunk-based development). A main é o tronco e precisa estar sempre funcionando. Cada mudança nasce numa branch curta, que dura no máximo um dia, e volta para a main por merge local, sem pull request.

  • Prefixos de branch: feat/, test/, fix/, docs/, refactor/, chore/.
  • Commits pequenos, um por intenção, no padrão Conventional Commits: tipo(escopo): o que mudou, no imperativo e em português.
  • Antes do merge: git pull --rebase na main e npm test passando.
  • Merge sempre com --ff-only, para o histórico ficar linear. Nunca use git push --force na main.
git switch -c docs/requisitos-qualidade
# edita, testa
git add docs/qualidade.md
git commit -m "docs: descreve requisitos de qualidade"
git switch main
git pull --rebase
git merge --ff-only docs/requisitos-qualidade
git push
git branch -d docs/requisitos-qualidade
git log --oneline --graph -5

7. O que é qualidade de software

Qualidade tem pelo menos três leituras. Conformidade: o software faz o que a especificação diz. Adequação ao uso: o software resolve o problema de quem usa; uma especificação errada produz um sistema conforme e inútil. Qualidade do código: o software continua barato de mudar, o que depende de testes, legibilidade e baixa complexidade.

Duas perguntas organizam as atividades. Verificação pergunta se o produto está sendo construído do jeito certo, e responde com testes, revisão e análise estática. Validação pergunta se o produto certo está sendo construído, e responde com critérios de aceite, protótipos e conversa com o usuário.

Os eixos da ISO/IEC 25010:2023

A norma descreve a qualidade do produto em nove características, os eixos que organizam toda a disciplina, e cada uma se divide em subcaracterísticas. Os requisitos de qualidade dos dois trabalhos partem desta tabela. A versão de 2023 renomeou usabilidade para capacidade de interação, portabilidade para flexibilidade, e acrescentou proteção (safety).

Uma característica só vira requisito quando ganha métrica, meta numérica e uma técnica que consiga reprová-la. "O sistema deve ser rápido" não reprova nada. "O p95 do tempo de resposta da busca fica abaixo de 300 ms com 50 usuários simultâneos" vira um teste de carga na Aula 12.

8. Prompt 1 · devcontainer e configuração do opencode

25 min

Você está num GitHub Codespace, na raiz do repositório organizacao-recursos, que hoje só tem o README. Crie .devcontainer/devcontainer.json usando a imagem mcr.microsoft.com/devcontainers/javascript-node:1-22-bookworm, a feature ghcr.io/devcontainers/features/docker-in-docker:2, a extensão dbaeumer.vscode-eslint, o secret recomendado OPENROUTER_API_KEY com descrição em português e um postCreateCommand que instale o opencode com curl -fsSL https://opencode.ai/install | bash. Crie opencode.json com o $schema https://opencode.ai/config.json, o provedor openrouter lendo a chave por {env:OPENROUTER_API_KEY} e o modelo padrão que eu informar. Crie .gitignore para Node (node_modules, coverage, .env). Crie AGENTS.md dizendo que o projeto é em JavaScript puro com ES modules, sem TypeScript, que os testes usam node:test e que todo commit segue Conventional Commits em português. Não escreva nenhuma chave em arquivo. Mostre o conteúdo de cada arquivo antes de gravar.
Antes de aceitar: procure "sk-or" no diff. Se aparecer, recuse a mudança. Depois rode Rebuild Container e confira opencode --version.

9. Prompt 2 · o opencode monta o projeto Node

25 min

Leia o AGENTS.md e transforme este repositório num projeto Node 22 com ES modules, sem TypeScript. Crie package.json com "type": "module", engines node >= 22 e os scripts test (node --test), test:cov (node --test --experimental-test-coverage --test-coverage-include='src/**') e lint (eslint .). Configure o ESLint 9 em eslint.config.js no formato flat, com @eslint/js recommended, globals do Node e a regra complexity limitada a 8. Crie src/intervalo.js com a função sobrepoe(a, b), que diz se dois intervalos [inicio, fim) de datas se sobrepõem, e test/intervalo.test.js com dois testes em node:test: intervalos que se cruzam e um que começa exatamente quando o outro termina. Peça permissão antes de instalar dependências. No fim, rode npm run lint e npm test e mostre a saída. Não use jest, mocha nem vitest.
Antes de aceitar: leia o git diff inteiro, confira que o script test é node --test e rode npm run lint && npm test você mesmo.

10. Prompt 3 · requisitos de qualidade do seu projeto

20 min

Atue como analista de qualidade. O projeto deste repositório é um sistema de Organização de Recursos de uma universidade: reserva de salas, professores e materiais sem conflito de horário. Escreva docs/qualidade.md com uma tabela de colunas Característica ISO/IEC 25010:2023, Requisito, Métrica, Meta e Como será verificado. Cubra pelo menos adequação funcional, eficiência de desempenho, confiabilidade, segurança e manutenibilidade. Cada meta precisa de número e unidade. Na coluna Como será verificado use apenas técnicas da disciplina: teste de unidade, teste de integração com banco, dublê de teste, cenário BDD, teste de carga, cobertura e análise estática. Quando faltar informação para fixar uma meta, escreva a pergunta numa seção Perguntas em aberto em vez de inventar o número. Não crie código.
Antes de aceitar: toda linha tem número e técnica. Apague as linhas que você não saberia explicar na prova oral.
