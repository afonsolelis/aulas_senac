2. Como revisar o que o agente produz

Durante o semestre, o código foi gerado pelo opencode. A responsabilidade pelo que entra na main continua sendo do aluno, e a prova oral cobra a explicação de cada arquivo. A revisão acontece em três momentos.

  • Antes do prompt: diga quais arquivos o agente pode alterar e quais não pode, aponte a fonte da verdade (spec, docs/qualidade.md, AGENTS.md) e peça que ele pare e pergunte quando faltar informação.
  • Durante a execução: leia o rastro (▸ read, ▸ write, ▸ edit, ▸ bash). Negue permissão para git push, para apagar arquivos e para qualquer mudança fora do escopo. Recuse ofertas de alterar o teste ou o exemplo para que ele passe.
  • Depois: git status e git diff para achar arquivo inesperado, teste ou .feature alterado e dependência no lugar errado; rode você mesmo npm test, npm run lint, npm run bdd e npm run carga; compare números (metas, thresholds) com a fonte. O commit e a mensagem são seus.

3. Qualidade e ISO/IEC 25010

Qualidade tem três leituras: conformidade com a especificação, adequação ao uso e facilidade de mudar o código. Verificação pergunta se o produto foi construído do jeito certo (testes, revisão, análise estática); validação pergunta se é o produto certo (critérios de aceite discutidos, protótipo, conversa com quem usa). A ISO/IEC 25010:2023 organiza a qualidade do produto em nove características: adequação funcional, eficiência de desempenho, compatibilidade, capacidade de interação, confiabilidade, segurança, manutenibilidade, flexibilidade e proteção (safety).

Uma característica vira requisito quando ganha métrica, meta numérica e a técnica que vai medi-la. No laboratório, o opencode apontou a linha de confiabilidade sem métrica e propôs uma meta de 99,5%; o grep '| ? |' confirmou a linha. O número proposto pelo agente é uma sugestão e precisa de confirmação.

| Eficiência de desempenho | Consulta de acervo responde sob carga | p95 com 50 usuários | < 300 ms | teste de carga (k6) |
| Confiabilidade | O sistema não pode cair | ? | ? | ? |      <- não reprova nada

4. Spec-Driven Development

A especificação vem antes do código e é o que o agente segue. Um arquivo specs/<funcionalidade>.md tem contexto, regras, critérios de aceite numerados e o que fica fora de escopo. Com o identificador do critério no nome do teste ou no comentário do cenário, a rastreabilidade vira um grep.

grep -rn "CA-03" test/ features/
features/emprestimo.feature:26:  # CA-03

No laboratório, o CA-03 (livro reservado por outro aluno) tinha cenário BDD, mas nenhum teste de unidade. Os erros mais comuns: critério que não se verifica ("deve ser fácil de usar") e spec escrita depois do código, só para descrevê-lo.

5. Caixa preta

As técnicas de caixa preta escolhem os casos olhando só a especificação. Partição de equivalência divide as entradas em classes que o sistema trata do mesmo jeito. Análise de valor-limite testa as fronteiras entre as classes, onde moram os erros de comparação. Tabela de decisão combina condições e define a ação de cada regra.

RegraMulta pendente3 ativosReservado por outroResultado
R1Squalquerqualquerrecusa: multa pendente
R2NSqualquerrecusa: limite de 3 empréstimos ativos
R3NNSrecusa: livro reservado por outro aluno
R4NNNaceita, devolução em 14 dias
describe('emprestar: valor-limite de empréstimos ativos', () => {
  it('0 ativos: aceita', () => assert.equal(emprestar(aluno({ ativos: 0 }), livro(), hoje).ok, true));
  it('2 ativos: aceita', () => assert.equal(emprestar(aluno({ ativos: 2 }), livro(), hoje).ok, true));
  it('3 ativos: recusa', () => assert.equal(emprestar(aluno({ ativos: 3 }), livro(), hoje).ok, false));
});

No laboratório, trocar >= por > em src/emprestimo.js derrubou dois testes: "3 ativos: recusa" e a regra R2. O teste de 0 ativos continuou verde, o que mostra por que valores do meio da partição não bastam.

6. Caixa branca

As técnicas de caixa branca olham o código. Cobertura de comandos pede que cada linha rode; cobertura de ramos pede que cada decisão seja exercitada como verdadeira e como falsa; cobertura de caminhos pede os caminhos independentes do grafo de fluxo. A complexidade ciclomática conta esses caminhos: V(G) = número de decisões + 1, ou arestas − nós + 2.

export function emprestar(aluno, livro, hoje) {
  if (aluno.multaPendente > 0) { ... }                               // decisão 1
  if (aluno.ativos >= LIMITE_ATIVOS) { ... }                         // decisão 2
  if (livro.reservadoPara && livro.reservadoPara !== aluno.id) { ... } // decisões 3 e 4
  ...
}
// V(G) = 4 + 1 = 5

7. TDD com node:test

O ciclo é vermelho, verde, refatoração. O teste é escrito antes do código e precisa falhar pelo motivo certo; o código mínimo o faz passar; a refatoração melhora o código com os testes verdes. Cada passo vira um commit, e o histórico prova que o ciclo aconteceu.

Com agente, TDD se faz dividindo o pedido. No laboratório, o primeiro prompt pediu só o teste do teto e proibiu mexer em src/; o aluno viu 3150 !== 3000 e commitou o vermelho. O segundo prompt pediu o mínimo para passar e proibiu mexer nos testes.

7b0d3f5 feat(multa): limita a multa a 3000 centavos
e19c6a8 test(multa): cobre o teto de 3000 centavos com 21 dias de atraso

8. Cobertura, ESLint e CI

A cobertura nativa do Node mede linhas, ramos e funções. Com as opções de meta, o próprio comando falha quando a cobertura cai:

"test:cov": "node --test --experimental-test-coverage --test-coverage-include='src/**' --test-coverage-lines=90 --test-coverage-branches=90"

ℹ Error: 87.50% branch coverage does not meet threshold of 90%.

O ESLint 9 usa flat config em eslint.config.js, com @eslint/js recommended, globals do Node e a regra complexity. O GitHub Actions roda, a cada push na main, npm ci, npm run lint e npm run test:cov.

name: CI
on:
  push:
    branches: [main]
jobs:
  testes:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
      - run: npm ci
      - run: npm run lint
      - run: npm run test:cov

Cobertura mostra o que não foi executado; ela não diz se o que foi executado está certo. Um teste sem asserção cobre a linha e não verifica nada.

9. Integração com banco real e migrações

O teste de integração roda contra um PostgreSQL 16 de verdade, num container criado pelo @testcontainers/postgresql. Ele pega o que um mock do pg aceitaria: SQL inválido, tipo errado, chave estrangeira, índice único, migração que não aplica. O esquema evolui por migrações numeradas em migrations/, aplicadas em ordem; uma migração já aplicada não se edita, cria-se a seguinte.

-- migrations/001_cria_tabelas.sql (trecho)
CREATE UNIQUE INDEX emprestimo_ativo_por_livro
  ON emprestimos (livro_id) WHERE devolvido IS NULL;
before(async () => {
  container = await new PostgreSqlContainer('postgres:16-alpine').start();
  pool = new pg.Pool({ connectionString: container.getConnectionUri() });
  await migrar(pool);
});

test('o banco recusa dois empréstimos ativos do mesmo livro', async () => {
  const sql = 'INSERT INTO emprestimos (aluno_id, livro_id, previsto) VALUES ($1, 1, $2)';
  await pool.query(sql, [1, '2027-06-07']);
  await assert.rejects(pool.query(sql, [2, '2027-06-07']), { code: '23505' });
});

10. Dublês e ViaCEP

Dublês substituem dependências nos testes. Dummy preenche um parâmetro que não é usado; stub devolve uma resposta pronta; spy registra as chamadas; mock já traz a expectativa de como será chamado; fake é uma implementação simplificada que funciona, como o repositório em memória. Para trocar a ViaCEP por um dublê, o fetch entra por injeção de dependência.

export async function buscarEndereco(cep, { fetch = globalThis.fetch } = {}) { ... }

test('ViaCEP fora do ar deixa o endereço pendente', async (t) => {
  const fetch = t.mock.fn(async () => { throw new TypeError('fetch failed'); });
  assert.deepEqual(await buscarEndereco('01310-100', { fetch }), { status: 'pendente' });
});

11. BDD e testes de carga

No BDD, cada critério de aceite vira um cenário em Gherkin com # language: pt. O cucumber-js lê cucumber.js, cria um World por cenário e executa as step definitions, que chamam a API pelo supertest. Esquema do Cenário com Exemplos cobre valores-limite; @wip fica fora do perfil padrão.

No k6, o mesmo script atende smoke, carga, estresse, pico e resistência, mudando o perfil de usuários. As métricas centrais são vazão, p95, p99 e taxa de erro, e os thresholds transformam a meta em critério: cruzou, o k6 marca ✗ e sai com código 99.

npm run bdd      # 10 scenarios (10 passed)
npm run carga    # ✓ 'p(95)<300' p(95)=131.8ms

No laboratório, o agente resumiu o p95 como "cerca de 130 ms". Na prova, cite o número do resumo do k6, que é a evidência.

12. Git trunk-based

A main é o tronco e está sempre verde. Cada mudança nasce numa branch que dura no máximo um dia, é testada e volta por merge local com --ff-only, sem pull request. Feedback do professor chega como issue e é respondido por commit.

git switch -c fix/cep-espacos
# teste que reproduz a issue, correção, npm test
git commit -am "fix(cep): normaliza o CEP antes de validar no cadastro (#7)" -m "Closes #7"
git switch main
git pull --rebase
git merge --ff-only fix/cep-espacos
git push
git branch -d fix/cep-espacos

13. Questões de revisão com respostas esperadas

Responda em voz alta antes de abrir a resposta. Na prova, troque os exemplos do biblioteca-campus pelos do seu organizacao-recursos.

1. Qual a diferença entre verificação e validação? Dê um exemplo de cada no seu projeto.

Resposta esperada

Verificação confere se o produto está de acordo com o que foi especificado (o produto foi construído do jeito certo?) e usa testes, revisão e análise estática; exemplo: o teste de unidade que recusa duas reservas da mesma sala no mesmo horário. Validação confere se a especificação resolve o problema de quem usa (é o produto certo?) e usa critérios de aceite discutidos, protótipo e conversa; exemplo: confirmar com a secretaria se reservas podem atravessar o intervalo entre os blocos de aula.

2. Por que "o sistema deve ser rápido" não serve como requisito? Reescreva-o.

Resposta esperada

Não tem métrica, meta nem técnica de verificação, então nenhum resultado consegue reprová-lo. Reescrita: "o p95 do tempo de resposta da consulta de disponibilidade de salas fica abaixo de 300 ms com 50 usuários simultâneos, verificado por teste de carga com k6". O número da meta deve vir de quem define o requisito ou ficar em Perguntas em aberto.

3. O que torna um critério de aceite verificável? Mostre um da sua spec e o teste que o cobre.

Resposta esperada

Uma condição observável e um resultado esperado sem ambiguidade, de preferência com valores concretos, e um identificador que permita rastreá-lo. Exemplo: "CA-02 Com 3 empréstimos ativos, o pedido é recusado", coberto pelo teste "3 ativos: recusa" e pelo cenário "Quarto empréstimo é recusado", ambos citando CA-02.

4. Para "no máximo 3 empréstimos ativos", quais partições e valores-limite você testaria, e por quê?

Resposta esperada

Partição válida {0, 1, 2 ativos}, que aceita, e partição inválida {3 ou mais}, que recusa. Os valores-limite são 2 (último aceito) e 3 (primeiro recusado); 0 pode entrar como extremo inferior. A fronteira é onde um > no lugar de >= aparece, como o laboratório mostrou.

5. Monte a tabela de decisão de emprestar. Quantas regras ela tem?

Resposta esperada

Condições: multa pendente, 3 ativos e livro reservado por outro aluno. Três condições binárias dão 8 combinações, mas como a primeira condição verdadeira (na ordem multa, limite, reserva) decide o resultado, elas se reduzem a 4 regras: R1 multa, R2 limite, R3 reserva por outro, R4 aceita. A reserva pelo próprio aluno cai em R4 e merece um teste próprio, porque exercita o segundo lado do &&.

6. Qual é a complexidade ciclomática de emprestar e o que esse número diz?

Resposta esperada

V(G) = 5: três if e um && somam 4 decisões, mais 1. Há 5 caminhos independentes, então são necessários pelo menos 5 casos para percorrê-los. O número também indica o custo de entender e testar a função; a regra complexity do ESLint impõe um teto.

7. 100% de cobertura de linhas garante 100% de ramos? Dê um contraexemplo.

Resposta esperada

Não. Em let r = 0; if (a) r = 1; return r;, um único teste com a verdadeiro executa todas as linhas, mas o ramo em que a é falso nunca roda. Por isso a meta da disciplina é de cobertura de ramos.

8. Mostre um ciclo de TDD no seu histórico. O que prova que o teste falhou antes?

Resposta esperada

Um commit test(...) anterior ao feat(...) da mesma funcionalidade. Fazendo git switch --detach <hash-do-test> e rodando npm test, o teste falha com a mensagem esperada (por exemplo 3150 !== 3000). Depois vem o commit que o faz passar e, se houver, um refactor(...) com os testes verdes.

9. Por que o teste de integração usa PostgreSQL em container e não um mock do pg?

Resposta esperada

O mock aceita qualquer SQL e devolve o que foi programado. O banco real pega erro de sintaxe, tipo, chave estrangeira, índice único (o 23505 do laboratório) e migração que não aplica. O container dá um banco limpo e igual no Codespace e no CI, sem instalar nada na máquina.

10. Diferencie stub, spy e mock no teste da ViaCEP. O que acontece com ela fora do ar?

Resposta esperada

Stub: o fetch falso que devolve o endereço pronto. Spy: o registro das chamadas, conferido com fetch.mock.callCount() e com a URL usada. Mock: um dublê com a expectativa embutida, que falha se não for chamado como previsto. Com a ViaCEP fora do ar, o fetch lança erro, buscarEndereco devolve { status: 'pendente' } e o cadastro segue; o teste simula isso com um fetch que lança TypeError, sem rede.

11. Em que um cenário BDD difere de um teste de unidade? Por que o .feature não cita rotas?

Resposta esperada

O cenário descreve um comportamento observável por quem usa, na linguagem da spec, e é executado pela API (supertest), atravessando rota, regra e repositório. O teste de unidade exercita uma função isolada. O .feature descreve o que acontece, e as step definitions guardam como; se ele citasse rotas, quebraria a cada mudança de API sem que o comportamento tivesse mudado.

12. O que significa p(95)<300? Por que percentil e não média?

Resposta esperada

Que 95% das requisições terminam em menos de 300 ms. A média esconde a cauda: com 95 requisições em 50 ms e 5 em 2000 ms, a média é 147,5 ms, mas cinco usuários em cem esperaram dois segundos. Se o threshold cruzar, o k6 marca ✗ e sai com código 99, o que derruba o script ou o CI.

13. Por que --ff-only? Como você responde a uma issue de feedback?

Resposta esperada

O --ff-only só integra se a main puder avançar sem commit de merge. O histórico fica linear e o merge exige git pull --rebase antes, então o que chega à main foi testado sobre a main atual. Para a issue: branch curta fix/..., teste que reproduz, correção, npm test, commit fix(escopo): ... (#N) com Closes #N no corpo, merge --ff-only e push; a issue fecha sozinha.

14. O agente disse que os testes passam. O que você confere antes de commitar?

Resposta esperada

git status e git diff (arquivos inesperados, testes ou .feature alterados, dependências no lugar errado), a execução dos comandos por você mesmo (npm test, lint, bdd, carga), os números comparados com a fonte (metas e thresholds) e o rastro do agente, procurando comandos que você não pediu. O resumo do agente não é evidência; a saída do terminal é.
