Caixa branca e caixa preta

Objetivo da aula

Sair da aula com docs/casos-de-teste.md no seu organizacao-recursos: partições, valores-limite e tabela de decisão derivados da spec, grafo de fluxo e complexidade ciclomática da função de conflito, e os testes node:test que saem de cada técnica, com cobertura medida.

No primeiro bloco, o professor aplica cada técnica no biblioteca-campus: o agente gera tabelas e testes, e o professor confere o resultado contra a spec. No segundo bloco, cada aluno faz o mesmo no próprio repositório com os três prompts desta página.

Os prompts desta página servem para o chat do GitHub Copilot no modo Agent, o agente padrão da disciplina, e também para o opencode (opencode run "..."). Os comandos opencode run que aparecem nos exemplos equivalem a colar o mesmo pedido no chat do Copilot.

1. Caixa preta e caixa branca

Testar todas as entradas possíveis é inviável: calcularMulta(previsto, devolvido) aceita qualquer par de datas. As técnicas de projeto de casos de teste escolhem poucos casos com mais chance de encontrar defeito, e dizem por que aqueles casos e não outros.

  • Caixa preta (funcional): os casos saem da especificação, sem olhar o código. Dá para escrevê-los antes de o código existir. Técnicas: partição de equivalência, análise de valor-limite e tabela de decisão.
  • Caixa branca (estrutural): os casos saem da estrutura do código, isto é, das decisões, ramos e caminhos que a execução pode seguir. Técnicas: grafo de fluxo de controle, complexidade ciclomática, caminhos básicos e critérios de cobertura.

O agente gera tabelas e testes em segundos. A técnica é o que permite a você conferir se ele escolheu os casos certos: sem ela, não há critério para aceitar ou recusar o que foi gerado.

2. Partição de equivalência

Divide-se o domínio de uma entrada em classes que o programa deveria tratar do mesmo jeito. Escolhe-se um representante por classe, supondo que, se ele passa, os outros valores da classe também passam. As classes inválidas, de entradas que o sistema deve recusar, entram na lista tanto quanto as válidas.

ClasseFaixa (dias de atraso)TipoRepresentanteEsperado (centavos)
P1dias ≤ 0válidadevolve 2 dias antes0
P21 ≤ dias ≤ 19válida5 dias de atraso750
P3dias ≥ 20válida30 dias de atraso3000 (teto)
P4data inválidainválidadevolvido = 'ontem'TypeError

As classes nascem nos pontos em que a regra muda de comportamento. Em RN05 eles são dois: o primeiro dia de atraso e o vigésimo, porque 20 × 150 = 3000 e a partir daí vale o teto. Cada classe vira um teste, com o nome começando pela classe:

import { test } from 'node:test';
import assert from 'node:assert/strict';
import { calcularMulta } from '../src/multa.js';

const DIA = 86_400_000;
const previsto = new Date('2027-03-15');
const atraso = (dias) => new Date(previsto.getTime() + dias * DIA);

test('P1 devolução 2 dias antes do prazo: multa 0', () => {
  assert.equal(calcularMulta(previsto, atraso(-2)), 0);
});
test('P2 5 dias de atraso: 750 centavos', () => {
  assert.equal(calcularMulta(previsto, atraso(5)), 750);
});
test('P3 30 dias de atraso: teto de 3000 centavos', () => {
  assert.equal(calcularMulta(previsto, atraso(30)), 3000);
});
test('P4 data de devolução inválida lança TypeError', () => {
  assert.throws(() => calcularMulta(previsto, 'ontem'), TypeError);
});

Na demonstração, P4 falhou: a função devolvia NaN em silêncio, porque NaN <= 0 é falso e Math.min(NaN, 3000) é NaN. O agente parou e avisou que a spec não dizia o que fazer com data inválida. A decisão (lançar TypeError) foi do professor, registrada como RN07 na spec antes de virar código.

3. Análise de valor-limite

Os defeitos se concentram nas fronteiras entre classes: um > que devia ser >=, um < que devia ser <=. Por isso testa-se cada fronteira, e não o meio da classe. Na análise de dois valores, testam-se o último valor de uma classe e o primeiro da seguinte; na de três valores, o limite, o valor logo abaixo e o logo acima.

RegraFronteiraValores (três valores)Esperado
RN013 empréstimos ativos2, 3, 4empresta, LIMITE_ATINGIDO, LIMITE_ATINGIDO
RN05início da multa-1, 0, 1 dia0, 0, 150
RN05teto19, 20, 21 dias2850, 3000, 3000

Em node:test, valores-limite ficam bem num array de casos percorrido com for: cada linha vira um teste com nome próprio, e acrescentar um caso é acrescentar uma linha.

const limitesDeAtivos = [
  [2, 'empresta'],          // abaixo do limite
  [3, 'LIMITE_ATINGIDO'],   // no limite
  [4, 'LIMITE_ATINGIDO'],   // acima do limite
];
for (const [ativos, esperado] of limitesDeAtivos) {
  test(`RN01 ${ativos} ativos -> ${esperado}`, () => {
    const aluno = { id: 'A1', ativos, multaPendente: 0 };
    if (esperado === 'empresta') {
      assert.equal(emprestar(aluno, livre, hoje).livroId, 'L1');
    } else {
      assert.throws(() => emprestar(aluno, livre, hoje), { codigo: esperado });
    }
  });
}

Na demonstração, o código tinha if (aluno.ativos > LIMITE_ATIVOS). Os casos com 2 e com 4 ativos passaram mesmo com o defeito; só o caso de exatamente 3 reprovou, com Missing expected exception. Um teste com um valor do meio da classe, como 5 ativos, nunca teria encontrado o erro.

No seu projeto, a regra de sobreposição tem uma fronteira explícita no enunciado: uma reserva das 19h às 21h e outra que começa às 21h não conflitam. Os três valores são 20h59 (conflita), 21h00 e 21h01 (não conflitam). O mesmo raciocínio vale para 07h e 23h, para a duração de exatamente 4 horas e para a turma com o mesmo número de alunos que a capacidade da sala.

4. Tabela de decisão

Quando o resultado depende da combinação de várias condições, cada combinação vira uma regra (uma coluna da tabela). Com três condições de sim ou não, a tabela completa tem 2³ = 8 regras. A spec costuma permitir reduzir: quando uma condição deixa de importar, marca-se com - (indiferente).

emprestarR1R2R3R4
C1 multa pendente (RN04)SNNN
C2 3 ou mais ativos (RN01)-SNN
C3 reservado por outro (RN03)--SN
MULTA_PENDENTEX
LIMITE_ATINGIDOX
LIVRO_RESERVADOX
emprestaX

A redução de 8 para 4 regras se apoia em RN06: vale o primeiro impedimento na ordem RN04, RN01, RN03. Na hora de testar, o representante do - deve ser S: um aluno com multa, 3 ativos e livro reservado por outro prova que a multa prevalece. Com N no lugar do -, a ordem dos motivos nunca seria exercitada.

const regras = [
  // regra, multaPendente, ativos, reservadoPor, esperado
  ['R1', 300, 3, 'ana', 'MULTA_PENDENTE'],
  ['R2', 0, 3, 'ana', 'LIMITE_ATINGIDO'],
  ['R3', 0, 1, 'ana', 'LIVRO_RESERVADO'],
  ['R4', 0, 1, null, 'empresta'],
];

Na demonstração, R2 falhou: o código verificava a reserva antes do limite e respondia LIVRO_RESERVADO. Antes de pedir a correção, o professor conferiu RN06 na spec para decidir de que lado estava o erro. Quando a spec não define a ordem, a tabela de decisão é o lugar onde essa lacuna aparece; registre-a em Perguntas em aberto em vez de deixar o agente escolher.

5. Grafo de fluxo de controle

Na caixa branca, o código vira um grafo: cada comando ou decisão é um nó, e cada desvio possível da execução é uma aresta. Uma decisão tem duas arestas de saída, S e N. Condições compostas com && ou || devem ser separadas em decisões simples, porque o curto-circuito cria caminhos próprios.

export function emprestar(aluno, livro, hoje) {                       // n1 (linha 12)
  if (aluno.multaPendente > 0) {                                        // d1 (linha 13)
    throw new RegraDeEmprestimo('MULTA_PENDENTE', ...);                 // e1
  }
  if (aluno.ativos >= LIMITE_ATIVOS) {                                  // d2 (linha 16)
    throw new RegraDeEmprestimo('LIMITE_ATINGIDO', ...);                // e2
  }
  if (livro.reservadoPor && livro.reservadoPor !== aluno.id) {          // d3 e d4 (linha 19)
    throw new RegraDeEmprestimo('LIVRO_RESERVADO', ...);                // e3
  }
  const previsto = new Date(hoje.getTime() + PRAZO_DIAS * DIA_MS);      // ok
  return { alunoId: aluno.id, livroId: livro.id, inicio: hoje, previsto };
}                                                                       // fim

Nós (N = 10): n1, d1, d2, d3, d4, e1, e2, e3, ok, fim
Arestas (E = 13):
  n1-d1   d1-e1 (S)  d1-d2 (N)   d2-e2 (S)  d2-d3 (N)
  d3-d4 (S)  d3-ok (N)   d4-e3 (S)  d4-ok (N)
  e1-fim  e2-fim  e3-fim  ok-fim

A linha 19 parece uma decisão só, mas tem duas: reservadoPor existe? E, se existe, é de outro aluno? Lida como uma decisão, ela esconde o caso de Ana retirar o livro que ela mesma reservou.

6. Complexidade ciclomática e caminhos básicos

A complexidade ciclomática V(G) é o número de caminhos independentes do grafo, isto é, o mínimo de testes necessário para cobrir todos os ramos passando por caminhos básicos. Há três jeitos de calculá-la, que devem dar o mesmo número:

  • V(G) = E - N + 2 = 13 - 10 + 2 = 5
  • V(G) = decisões simples + 1 = 4 + 1 = 5
  • V(G) = regiões fechadas do grafo desenhado no plano + 1 = 5
CaminhoDecisõesEntradaResultado
C1d1 Smulta 300MULTA_PENDENTE
C2d1 N, d2 Ssem multa, 3 ativosLIMITE_ATINGIDO
C3d1 N, d2 N, d3 Nsem multa, 1 ativo, sem reservaempresta
C4d3 S, d4 Sreservado por Ana, quem pede é BrunoLIVRO_RESERVADO
C5d3 S, d4 Nreservado por Ana, quem pede é Anaempresta

Cada caminho básico vira um teste com nome C1 a C5. Para conferir o V(G) que o agente calculou, o ESLint mede a complexidade de cada função. O limite 1 na linha de comando é um truque para que ele imprima o número de todas as funções:

npx eslint src/ --rule '{"complexity": ["warn", 1]}'

src/emprestimo.js
  12:8  warning  Function 'emprestar' has a complexity of 5. Maximum allowed is 1  complexity
  26:8  warning  Function 'calcularMulta' has a complexity of 2. Maximum allowed is 1  complexity
src/relatorio.js
   1:8  warning  Function 'situacaoDoAluno' has a complexity of 9. Maximum allowed is 1  complexity

Até 10 costuma ser tratável; acima disso, a função pede refatoração. No Trabalho 1, o eslint.config.js usa complexity: ['error', 8], e situacaoDoAluno, com 9 (1 de base, mais o for, três if de retorno, o if do laço, dois && e um ||), reprova no npm run lint.

7. Cobertura de comandos, ramos e caminhos com node:test

CritérioO que exigeComo medir
Comandos (linhas)Cada linha executada ao menos uma vezline %
Ramos (decisões)Cada decisão avaliada como verdadeira e como falsabranch %
Caminhos básicosV(G) caminhos independentesgrafo e ESLint
Todos os caminhosToda combinação de ramosinviável: cresce de forma exponencial e, com laços, pode ser infinita

O Node 22 mede cobertura sem dependência nenhuma. O script fica no package.json, com a meta no próprio comando: se a cobertura ficar abaixo, o comando sai com erro, no Codespace e no CI.

"test:cov": "node --test --experimental-test-coverage --test-coverage-lines=80 --test-coverage-branches=80 --test-coverage-include='src/**'"

A biblioteca usa 90% de ramos, a meta registrada em docs/qualidade.md na Aula 01; o seu trabalho usa 80%. Na primeira execução da demonstração:

ℹ file              | line % | branch % | funcs % | uncovered lines
ℹ src/emprestimo.js |  96.67 |    75.00 |  100.00 | 20
ℹ Error: 75.00% branch coverage does not meet threshold of 90%.

A linha 20 (livro reservado) nunca rodou. Além disso, if (dias <= 0) return 0; está numa linha só: o teste com 3 dias de atraso executa a linha e a conta como coberta, mas o ramo verdadeiro nunca rodou. Depois que o agente acrescentou testes para esses dois ramos, a tabela marcou 100% de linhas e 91,67% de ramos. A meta passou, e mesmo assim o caso de Ana retirar o próprio livro (C5) continuava sem teste, escondido dentro de uma linha já coberta. Bater a meta não dispensa ler o que ficou de fora.

8. Revisando o que o agente gerou

Em todas as demonstrações, o agente produziu as tabelas e os testes, e a qualidade veio da conferência. Antes de cada commit, verifique:

  • Cada classe de equivalência tem representante e teste, incluindo pelo menos uma classe inválida por regra.
  • Cada fronteira tem os três valores, e o resultado esperado de cada um está escrito na spec.
  • A tabela de decisão completa tem 2ⁿ regras, e cada redução cita a regra da spec que a permite.
  • O V(G) do agente bate com a sua contagem de decisões e com o número do ESLint.
  • Teste vermelho foi investigado: o defeito está no código ou na spec? Só depois peça a correção.
  • O agente não alterou src/ para fazer a cobertura subir.

9. Prompt 1 · partições e valores-limite

30 min · branch test/particoes

Leia docs/spec.md. Para três regras do meu projeto, sobreposição de reservas da mesma sala (RF02), capacidade da sala (RF04) e validação do intervalo (RF07: término posterior ao início, duração máxima de 4 horas, entre 07h e 23h), escreva em docs/casos-de-teste.md, para cada uma: a variável de entrada analisada; as classes de equivalência válidas e inválidas, numeradas P1, P2..., com um representante concreto de cada; os valores-limite de cada fronteira pela análise de três valores (o limite, logo abaixo e logo acima), com o resultado esperado segundo a spec. Use horários concretos, como 19:00–21:00 contra 20:59, 21:00 e 21:01. Depois crie test/particoes.test.js com node:test e node:assert/strict: um test por classe, com o nome começando pela classe, e os valores-limite em formato de tabela, num array de casos percorrido com for. Se o resultado esperado de algum caso não estiver na spec, não invente: registre em Perguntas em aberto. Não altere src/. Rode npm test e mostre a saída.
Antes de aceitar: o caso 21:00 está lá e espera "não conflita"? Existe pelo menos uma classe inválida por regra? Teste vermelho é informação; confira na spec se o erro é do código.

10. Prompt 2 · tabela de decisão da reserva

25 min · branch test/decisao

Monte uma tabela de decisão para a criação de reserva do meu projeto. Condições, cada uma de sim ou não: sala livre no intervalo (RF02), professor livre no intervalo (RF03), capacidade da sala suficiente para a turma (RF04), sala fora de manutenção no intervalo (RF06). Ações: criar a reserva ou recusar com o código de motivo definido na spec. Escreva em docs/casos-de-teste.md a tabela completa com as 16 regras e depois a versão reduzida, usando - para condição indiferente e explicando qual regra da spec permite cada redução. Se a spec não disser qual motivo prevalece quando há mais de um impedimento, pare e escreva a pergunta em Perguntas em aberto, sem escolher uma ordem. Crie test/decisao.test.js com um teste por regra da tabela reduzida, usando S (condição verdadeira) como representante do -, rode npm test e mostre a saída. Não altere src/.
Antes de aceitar: conte as colunas da tabela completa (16) e confira que cada redução cita uma regra da spec. Se o agente escolheu uma ordem de motivos que você nunca decidiu, recuse.

11. Prompt 3 · caixa branca e cobertura

35 min · branch test/caminhos

Agora caixa branca. Abra a função de src/ que verifica conflito de reserva (a T01 da aula passada). 1. Desenhe em docs/casos-de-teste.md o grafo de fluxo de controle em texto: numere os nós, liste as arestas e separe condições compostas com && e || em decisões simples. 2. Calcule a complexidade ciclomática de dois jeitos, E - N + 2 e decisões + 1, e confira se batem. 3. Liste os caminhos básicos independentes e, para cada um, os dados de entrada que o percorrem. 4. Crie test/caminhos.test.js com um teste por caminho, nomes começando por C1, C2... 5. No package.json, crie o script test:cov valendo node --test --experimental-test-coverage --test-coverage-lines=80 --test-coverage-branches=80 --test-coverage-include='src/**', rode npm run test:cov e mostre a tabela. Não altere src/ para aumentar a cobertura.
Antes de aceitar: conte as decisões da função você mesmo e compare com o V(G) do agente. Rode npx eslint src/ --rule '{"complexity": ["warn", 1]}' para conferir o número.

12. Entregável e checagem

docs/casos-de-teste.md com partições, limites, tabela de decisão, grafo e V(G); test/particoes.test.js, test/decisao.test.js, test/caminhos.test.js e o script test:cov, tudo integrado na main por branches curtas.
