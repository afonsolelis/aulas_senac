Parte 1 · Teoria

Com que olhos você olha o software

Toda técnica de teste responde a uma pergunta anterior: você pode ver o código? A resposta muda o que você consegue enxergar — e o que continua invisível.

Caixa preta

A base do teste é a especificação. Você conhece entradas, saídas e regras de negócio; o código é opaco por escolha. É o olhar de quem usa o sistema — e também de quem ataca.

  • Acha bem: requisito mal implementado, regra de negócio errada, validação ausente, funcionalidade que simplesmente falta.
  • Não acha: o caminho de código que nunca foi executado por nenhum teste.

Caixa branca

A base do teste é o código. Você olha o fluxo de controle e pergunta por quais ramos ainda não passou. É o olhar de quem escreve — e por isso o mais fácil de se enganar: você tende a testar o que implementou, não o que foi pedido.

  • Acha bem: ramo nunca executado, código morto, condição impossível, erro fino de lógica.
  • Não acha: o requisito que ninguém escreveu — não existe linha para cobrir.

Caixa cinza

É o que se pratica em teste de API: você chama pelo contrato, como um cliente externo, mas escolhe os casos sabendo o que existe atrás. É o modo em que o Foot Fanatics será testado na maior parte do semestre.

Critérios de cobertura

O mesmo trecho de código, medido por três réguas diferentes:

if (token != null && !token.expirado()) { liberarAcesso(); }
Critério Exige Testes mínimos
Comando (linha) Cada linha executada ao menos uma vez 1 — só o caminho feliz
Ramo (decisão) A decisão avaliada como verdadeira e como falsa 2 — inclui o caso que nega acesso
Condição Cada operando avaliado V e F isoladamente 3 — token nulo e token expirado são bugs distintos
Cobertura mede o que foi executado, não o que foi verificado. Um teste sem asserção soma cobertura e não protege nada. Use cobertura para descobrir o que falta testar — nunca como nota.

Técnicas de projeto de teste em caixa preta

  • Partição de equivalência — entradas tratadas do mesmo jeito formam uma classe; teste uma por classe. Ex.: plano free, premium, inválido.
  • Análise de valor limite — o defeito mora na fronteira; teste no limite, logo antes e logo depois. Ex.: sessão de 30 min em 29:59, 30:00 e 30:01.
  • Tabela de decisão — quando condições se combinam, monte a tabela e cubra cada regra. Ex.: logado? × assinante? × conteúdo pago?.

acesso.py — a regra sob teste

from dataclasses import dataclass

PLANOS = ("free", "premium")
LIMITE_SESSAO_S = 1800  # 30 minutos

@dataclass
class Sessao:
    plano: str
    idade_s: int
    renovacoes: int = 0

@dataclass
class Conteudo:
    premium: bool

def pode_assistir(sessao, conteudo):
    if sessao is None or sessao.idade_s > LIMITE_SESSAO_S:
        return "SESSAO_INVALIDA"
    if sessao.plano not in PLANOS:
        return "PLANO_INVALIDO"
    if conteudo.premium and sessao.plano != "premium":
        return "ASSINATURA_NECESSARIA"
    if sessao.renovacoes > 3:
        return "SESSAO_INVALIDA"
    return "LIBERADO"

Repare no último if: ele não está em nenhum requisito. Nenhum teste de caixa preta chega até ele — só o relatório de cobertura denuncia sua existência. Achar código assim é exatamente o que a caixa branca faz bem.

test_acesso.py — as três técnicas

import pytest
from acesso import Sessao, Conteudo, pode_assistir

def sessao(plano="premium", idade_s=10, renovacoes=0):
    return Sessao(plano=plano, idade_s=idade_s, renovacoes=renovacoes)

# --- 1. Particao de equivalencia -------------------------------------
@pytest.mark.parametrize("plano, esperado", [
    ("free",    "ASSINATURA_NECESSARIA"),   # classe: sem direito
    ("premium", "LIBERADO"),                # classe: com direito
    ("pirata",  "PLANO_INVALIDO"),          # classe: entrada invalida
])
def test_plano_decide_acesso_a_conteudo_premium(plano, esperado):
    assert pode_assistir(sessao(plano=plano), Conteudo(premium=True)) == esperado

# --- 2. Analise de valor limite --------------------------------------
@pytest.mark.parametrize("idade_s, esperado", [
    (1799, "LIBERADO"),           # logo antes do limite
    (1800, "LIBERADO"),           # NO limite: ainda vale
    (1801, "SESSAO_INVALIDA"),    # logo depois
])
def test_fronteira_de_expiracao_da_sessao(idade_s, esperado):
    assert pode_assistir(sessao(idade_s=idade_s), Conteudo(premium=False)) == esperado

# --- 3. Tabela de decisao --------------------------------------------
REGRAS = [
    # logado, assinante, premium, esperado
    (False, False, False, "SESSAO_INVALIDA"),
    (True,  False, False, "LIBERADO"),
    (True,  False, True,  "ASSINATURA_NECESSARIA"),
    (True,  True,  True,  "LIBERADO"),
]

@pytest.mark.parametrize("logado, assinante, premium, esperado", REGRAS)
def test_matriz_de_acesso(logado, assinante, premium, esperado):
    s = sessao(plano="premium" if assinante else "free") if logado else None
    assert pode_assistir(s, Conteudo(premium=premium)) == esperado

Medir

pytest --cov=acesso --cov-branch --cov-report=term-missing
CritérioComo pedirO que ainda escapa
Comando (linha)--covo ramo que nega o acesso
Ramo (decisão)--cov-branchqual dos dois operandos causou o desvio
Condiçãonenhuma ferramenta padrão dá de graçaé decisão sua de projeto de teste

O term-missing lista linha e ramo não executados. Rode a suíte completa e confira: a linha de renovacoes aparece como missing.

Provar que o teste protege — mutação na unha

Cobertura alta não significa proteção. Faça o experimento, um de cada vez, e volte atrás depois:

  1. Troque > LIMITE_SESSAO_S por >= LIMITE_SESSAO_S. Deve falhar apenas o caso 1800 — é a análise de valor limite fazendo o trabalho dela.
  2. Troque a condição de conteúdo premium por if False:. Deve falhar o caso free + premium.
  3. Escreva um teste que chama pode_assistir e não tem nenhum assert. Ele passa, soma cobertura e não falha em nenhuma das mutações acima. É o defeito mais comum em projeto com meta de cobertura.
Regra da casa para o semestre: apague a regra, rode a suíte. Se não ficar vermelha, aquele teste não está protegendo nada.
Parte 2 · Mão na massa

Foot Fanatics: o case do semestre

Uma API REST de conteúdo esportivo com a mesma espinha dorsal do remo-api — clubes, jogos, resultados, matérias — com uma diferença que muda tudo para a disciplina de qualidade: ela tem assinatura. Isso significa conta, controle de acesso e gestão de sessão.

Por que assinatura? Porque introduz tempo (token expira, plano vence), risco (falha de autorização é vazamento, não desconforto), ramificação (logado × assinante × conteúdo pago) e estado compartilhado (sessão sob concorrência). Cada tema das próximas semanas ganha um alvo concreto.

Escopos iniciais

Escopo Nome Do que trata
E1 Identidade & Conta Cadastro, credencial, perfil, recuperação de acesso.
E2 Sessão & Acesso Login, emissão de token, expiração, renovação, logout.
E3 Assinatura Planos free e premium, vigência, upgrade, cancelamento.
E4 Conteúdo Clubes, jogos e matérias; parte pública, parte exclusiva de assinante.

Fora do escopo: integração de pagamento real, aplicativo mobile, notificação push e painel administrativo.
