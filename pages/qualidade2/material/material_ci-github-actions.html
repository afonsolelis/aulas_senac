Testes Automatizados em CI (GitHub Actions)

Objetivos

  • Explicar CI como prática de integração frequente, não sinônimo de ferramenta.
  • Modelar eventos, jobs e steps de um workflow.
  • Executar a suíte Maven em Java 21 com cache e artifacts diagnósticos.
  • Aplicar permissões mínimas e tornar o check obrigatório antes do merge.
A aula abre com um quiz. Oito questões de 90 segundos sobre a Aula 05 — erro, defeito, falha e incidente, bug report reproduzível, severidade × prioridade, triagem, causa raiz e teste de regressão. Vale revisar o material da Aula 05 antes de entrar no quiz ao vivo. Não vale nota; vale saber onde você está.

1. O que é integração contínua?

CI combina mudanças pequenas e frequentes na linha principal com uma verificação automática confiável. O objetivo é reduzir o intervalo entre introduzir um problema e descobri-lo. Quanto menor esse intervalo, menor o contexto necessário para corrigir.

Comportamentos da equipe

  • Branches curtas e pull requests pequenos.
  • Build e testes executados localmente antes do push.
  • Main permanece executável e vermelho recebe atenção imediata.
  • Falha não é contornada com reruns sucessivos ou checks opcionais.
Ter um arquivo YAML não produz CI se a equipe integra raramente, aceita pipeline vermelho ou ignora o check para fazer merge.

2. Modelo do GitHub Actions

ElementoResponsabilidade
WorkflowProcesso versionado em .github/workflows/*.yml
EventoDisparo, como pull_request ou push em main
JobConjunto de passos em um runner; por padrão jobs são paralelos
StepAction reutilizável ou comando de shell
RunnerMáquina limpa que executa o job
ArtifactArquivo preservado após o job, como relatório de teste

Jobs não compartilham filesystem. Use artifacts para evidência e needs para dependência explícita.

3. Workflow mínimo e atual

Para o projeto Java 21, use releases estáveis das actions, distribuição Temurin e cache Maven incorporado ao setup do Java.

name: qualidade

on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

jobs:
  test:
    name: test
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - name: Obter código
        uses: actions/checkout@v6
      - name: Configurar Java
        uses: actions/setup-java@v5
        with:
          distribution: temurin
          java-version: '21'
          cache: maven
      - name: Verificar
        run: ./mvnw -B verify

As versões do exemplo foram verificadas nas páginas oficiais das actions para o semestre. Ao atualizar o material, revise changelog e requisitos do runner.

4. Por que o comando é verify?

O Maven possui ciclo de vida. test executa a fase de testes unitários; verify avança o ciclo e permite executar testes de integração e verificações como cobertura. Assim o gate cresce nas próximas aulas sem trocar o contrato principal.

  • ./mvnw fixa a versão do Maven usada pelo projeto.
  • -B executa em modo batch, apropriado à automação.
  • O mesmo comando deve estar no README e funcionar localmente.
  • Não use -DskipTests no job que decide a qualidade.

5. Cache, concorrência e tempo de feedback

Cache de dependências reduz download; não deve reaproveitar saída compilada de forma a esconder problemas. A chave do cache do setup-java considera arquivos de dependência. concurrency cancela execuções antigas da mesma referência, liberando runners.

Acelerar: testes determinísticos, cache de dependências, jobs independentes e mudanças menores.
Não mascarar: continue-on-error, retry indiscriminado, exclusão silenciosa e workspace persistente.

6. Preservar relatórios

- name: Publicar relatórios de teste
  if: always()
  uses: actions/upload-artifact@v4
  with:
    name: relatorios-${{ github.run_number }}
    path: |
      target/surefire-reports/
      target/failsafe-reports/
    if-no-files-found: warn
    retention-days: 7

O passo roda mesmo após falha e preserva resultado daquela execução. Retenção curta reduz armazenamento; relatórios não devem conter tokens, payloads pessoais ou credenciais.

Diagnóstico: nome do teste, stack trace, versão do commit e logs concisos devem permitir localizar a regressão sem repetir manualmente o cenário.

7. Segurança do workflow

  • Permissões mínimas: comece com contents: read; conceda escrita ao job específico.
  • Segredos: use armazenamento de secrets, mas lembre que código não confiável pode tentar exfiltrá-los.
  • Contribuições externas: evite executar código de fork com contexto privilegiado.
  • Actions: use releases estáveis e revise mudanças; em contexto profissional, fixe SHA conforme política.
  • Logs: não imprima contexto completo, variáveis ou tokens para “depurar”.
Atenção a pull_request_target: o evento roda no contexto da base e pode ter acesso privilegiado. Não faça checkout e execução ingênua de código não confiável.

8. Branch protection e contrato de merge

  1. Abra um pull request que execute o workflow.
  2. Confirme o nome estável do check: qualidade / test.
  3. Nas regras da branch, exija o check e revisão por par.
  4. Se desejado, exija branch atualizada com a base.
  5. Não permita merge administrativo como rotina; exceções devem ser auditáveis.

O pipeline deixa de ser relatório e se torna controle preventivo. Se estiver lento ou instável, corrija o pipeline; não enfraqueça a regra.

9. Diagnóstico operacional

SintomaInvestigação
Passa local, falha na CICompare Java, comando, timezone, locale, filesystem e estado implícito.
IntermitenteProcure concorrência, relógio, ordem, portas, limites e dependência externa.
Não disparaValide YAML, evento, branch e filtros de paths.
Cache não ajudaConfira pom.xml, hit/miss e tempo real de download.
Artifact vazioConfirme fase Maven, caminhos e if: always().
Rerun é experimento para confirmar flakiness. Ele não é correção nem deve desbloquear merge automaticamente.

Prática — do vermelho ao verde, o CI no GitHub Actions e o primeiro ciclo de avaliação arquitetural

A Aula 05 terminou com todas as regras de negócio cobertas por testes que falham. Hoje a equipe escreve a lógica completa até esses testes passarem, põe o projeto sob integração contínua no GitHub Actions (seções 3 a 8) e, com o código de pé, faz o primeiro ciclo do ATAM (Len Bass, Paul Clements e Rick Kazman) sobre o que foi implementado. Cole os prompts abaixo, na ordem, na IA/persona escolhida. O agente pode usar o terminal (bash) para achar os arquivos, rodar a suíte e operar o git e o gh.

Prompt 1 — do vermelho ao verde

Atue como desenvolvedor na fase green do TDD. Você pode usar o terminal (bash), com comandos como ls, find, grep e cat, para localizar os arquivos necessários e rodar ./mvnw -B verify: docs/testes/plano-tdd.md, requisitos, regras de negócio, docs/arquitetura.md, ADRs, código e testes. Os testes vermelhos da aula anterior são a especificação: implemente a lógica completa de todas as regras de negócio até todos passarem. Não apague, não desative com @Disabled, não enfraqueça asserções e não mude o resultado esperado de nenhum teste. Se um teste parecer errado, confronte com a regra na fonte, registre a divergência e pergunte antes de mudar. Respeite os componentes de docs/arquitetura.md e as ADRs. Trabalhe um caso por vez: implemente o mínimo, rode a suíte inteira e refatore só com tudo verde. Termine com ./mvnw -B verify verde e a matriz regra → caso → teste → status atualizada no plano.

Prompt 2 — o CI do projeto no GitHub Actions

Atue como engenheiro de DevOps responsável pela integração contínua. Você pode usar o terminal (bash) para localizar os arquivos do projeto, rodar ./mvnw -B verify e usar o git e o gh. Crie .github/workflows/ci.yml disparado em pull_request e em push na main, com permissions: contents: read, checkout, Java 21 (temurin) com cache Maven, concurrency que cancela execuções obsoletas, timeout-minutes e o mesmo ./mvnw -B verify usado localmente. Publique os relatórios do Surefire e do Failsafe como artifact com if: always() e retenção curta. Não use segredos, continue-on-error nem pull_request_target, e não pule testes. Trabalhe numa branch, abra um pull request e confirme o check verde. Quebre de propósito uma asserção, registre o run vermelho, reverta e confirme o verde de novo. Configure a proteção da main exigindo esse check (sem permissão, liste os passos para quem administra o repositório) e anote no README os IDs dos runs.

Prompt 3 — primeiro ciclo de avaliação arquitetural

Atue como avaliador de arquitetura conduzindo o primeiro ciclo do ATAM, o método de Len Bass, Paul Clements e Rick Kazman. Você pode usar o terminal (bash) para localizar e ler personas, requisitos, docs/arquitetura.md, ADRs, código, testes e os runs do GitHub Actions. Não altere código, não invente requisitos e não trate suposições como fatos. Crie docs/avaliacao-arquitetural/ciclo-01.md com: direcionadores de negócio; cenários de atributo de qualidade em seis partes (fonte, estímulo, artefato, ambiente, resposta e medida de resposta); utility tree com prioridade (importância, dificuldade) em A/M/B; e, para os cenários de maior prioridade, as abordagens e táticas encontradas no código, com arquivo e linha como evidência. Registre pontos de sensibilidade, pontos de trade-off, riscos, não riscos e temas de risco ligados aos direcionadores. Compare o que docs/arquitetura.md promete com o que o código faz e liste as divergências. Termine com ações priorizadas para o próximo ciclo.

Critérios de aceite

  • ./mvnw -B verify passa com todos os testes da Aula 05; o diff não remove, desativa nem enfraquece nenhum deles.
  • .github/workflows/ci.yml versionado, com permissões mínimas, Java 21, cache Maven e o mesmo comando local.
  • Uma execução vermelha intencional e sua recuperação verde estão registradas no README; os relatórios podem ser baixados em sucesso e falha.
  • O merge na main fica bloqueado quando o check falha, e nenhum segredo aparece em log.
  • docs/testes/plano-tdd.md mostra a matriz regra → caso → teste → status, sem regra descoberta.
  • docs/avaliacao-arquitetural/ciclo-01.md traz cenários em seis partes, utility tree priorizada e descobertas com evidência no código.

Síntese e revisão

CI reduz o tamanho do mistério: integra cedo, executa o mesmo contrato em ambiente limpo e torna o resultado visível. Um gate confiável depende tanto do workflow quanto da disciplina da equipe.

  1. Por que verify é melhor ponto de extensão que test?
  2. Qual o risco de dar permissão de escrita ao workflow inteiro?
  3. Quando cancelar execução anterior é seguro?
  4. O que fazer quando um teste passa após rerun sem mudança?
