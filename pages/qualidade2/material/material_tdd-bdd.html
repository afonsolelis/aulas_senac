TDD e BDD: desenvolvimento guiado por testes

Objetivos

Explicar e praticar Red–Green–Refactor, transformar uma regra em cenário Given–When–Then, controlar o tempo com Clock e produzir evidência de uma funcionalidade E3 desenvolvida por TDD/BDD.

Pré-requisito: requisitos E3 numerados, JUnit configurado, suíte verde e RTM iniciada.

1. TDD é um fluxo de design

Test-Driven Development inverte a ordem habitual: primeiro descrevemos um comportamento executável, depois criamos a implementação mínima e, com a suíte verde, melhoramos a estrutura. O ganho não é “mais testes” por si só. É feedback rápido sobre entendimento, acoplamento e interface.

  1. Red: escreva um teste pequeno e veja-o falhar pela razão esperada.
  2. Green: implemente o mínimo, sem antecipar generalizações.
  3. Refactor: remova duplicação, melhore nomes e responsabilidades sem alterar o comportamento.
Se o teste passa antes da implementação, corrija o teste. Se a suíte quebra durante refactor, reverta o último passo e reduza o tamanho da mudança.

2. Escolhendo o primeiro exemplo

Comece pelo caso mais simples que força uma decisão real. Para a assinatura do Foot Fanatics, o caminho “plano FREE não acessa conteúdo exclusivo” exige pouca infraestrutura. Depois avance para premium vigente, fronteira do vencimento, cancelamento e dados inválidos.

3. Controlando o relógio

Código que chama Instant.now() dentro da regra cria dependência global e testes que podem falhar na virada do segundo. Injete Clock ou passe o instante explicitamente.

public boolean estaVigente(Clock clock) {
  Instant agora = clock.instant();
  return status == ATIVA && agora.isBefore(vigenteAte);
}
@Test
void noInstanteDoVencimentoJaEstaVencida() {
  Clock clock = Clock.fixed(vigenteAte, ZoneOffset.UTC);
  assertThat(assinatura.estaVigente(clock)).isFalse();
}

A escolha isBefore, e não “antes ou igual”, materializa uma política. Essa política deve aparecer no requisito e no cenário BDD.

4. BDD como descoberta colaborativa

Behavior-Driven Development usa exemplos para alinhar negócio, desenvolvimento e teste. Given–When–Then não é decoração; cada parte tem uma função.

  • Dado/Given: somente o estado relevante para a regra.
  • Quando/When: um evento observável.
  • Então/Then: resultado de negócio, sem detalhar classes internas.

Cenário: assinatura expirada bloqueia matéria exclusiva

Dado que Ana tem plano premium vencido às 11:59:59

Quando ela solicita uma matéria exclusiva às 12:00:00

Então recebe 403 e nenhum trecho exclusivo é devolvido

Antes de automatizar, faça as “três perguntas”: há um exemplo que contradiz a regra? qual é a fronteira? qual resposta o cliente observa?

5. Do cenário ao código

Um cenário de aceite pode demandar vários microciclos TDD. Primeiro modele a vigência no domínio; depois a política de acesso; por fim o endpoint e o código HTTP.

@ParameterizedTest
@CsvSource({
  "FREE,   2026-10-06T12:00:00Z, false",
  "PREMIUM,2026-10-05T12:00:01Z, true",
  "PREMIUM,2026-10-05T12:00:00Z, false",
  "PREMIUM,2026-10-05T11:59:59Z, false"
})
void decideAcessoPorPlanoEVigencia(
    Plano plano, Instant vigenteAte, boolean esperado) { ... }

Teste parametrizado é bom quando a estrutura do comportamento é a mesma e só os dados mudam. Se cada linha requer explicação diferente, use testes nomeados separados.

6. Qualidade do teste

FIRST

rápido, independente, repetível, autoavaliável e escrito em tempo oportuno.

Uma razão para falhar

um teste expressa uma regra; fixture pequena e intenção visível.

Evite

  • asserção sobre detalhes privados ou ordem incidental;
  • mockar o próprio objeto sob teste;
  • fixture global compartilhada e mutável;
  • Thread.sleep para testar tempo;
  • testes sem asserção ou que aceitam vários resultados;
  • mudar o teste somente para fazê-lo passar sem revisar o requisito.

7. Evidência do ciclo

A avaliação precisa distinguir “há testes agora” de “a funcionalidade foi guiada por testes”. Use um histórico curto e legível.

  1. Commit test: cenário de assinatura vencida (red) com execução falhando pelo motivo esperado.
  2. Commit feat: bloqueia acesso após vencimento (green) com suíte verde.
  3. Commit refactor: extrai política de vigência sem mudança de resultado.
  4. PR descreve cenário, decisão de fronteira e links da execução.
Não quebre deliberadamente a branch principal para provar o Red. Faça o ciclo em branch local e preserve a evidência no histórico/PR.

8. Prática e critérios

Escolha uma regra E3 ainda incompleta: vigência, upgrade, cancelamento ou renovação. Escreva um cenário BDD, automatize limites e negativos e implemente em microciclos.
