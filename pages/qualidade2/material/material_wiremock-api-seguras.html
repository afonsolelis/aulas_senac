WireMock e Chamadas de API Seguras

Resultado de aprendizagem

Ao final, você consegue isolar uma API externa com WireMock, decidir quando usar Testcontainers, testar sucesso e degradação, e registrar a evidência na RTM do Foot Fanatics.

Ponto de partida: suíte de unidade e integração verde, cliente HTTP encapsulado e pipeline executando em pull request.

1. Por que isolar uma integração

Uma chamada externa atravessa uma fronteira que sua equipe não controla. Rede, dados, credencial, cota e contrato podem mudar. Se cada teste chama o provedor verdadeiro, a suíte fica lenta, cara e intermitente. O objetivo não é fingir que o provedor nunca falha: é ensaiar cada falha de forma reproduzível.

2. WireMock, mock de objeto e Testcontainers

Mockito substitui um objeto dentro do processo Java. É ótimo para uma regra isolada, mas não verifica serialização, URL, header ou status HTTP. WireMock sobe um servidor HTTP local e programável; o cliente usa a rede de verdade, porém a resposta está sob controle. Testcontainers sobe um serviço real em container — PostgreSQL, Redis ou outro componente — com ciclo de vida acoplado ao teste.

  • Use mock de objeto para unidade rápida e sem infraestrutura.
  • Use WireMock para contrato da porta HTTP e cenários de degradação.
  • Use Testcontainers quando a fidelidade de banco, constraint ou transação importa.
  • Mantenha poucos testes contra sandbox real para detectar incompatibilidade externa.
Dublê não prova o comportamento do terceiro. Ele prova como nossa aplicação reage ao contrato que declaramos.

3. Configuração mínima

Adicione WireMock apenas ao escopo de teste. A versão deve ser compatível com a versão de Java e Spring Boot do repositório; o princípio é manter a ferramenta fora do artefato de produção.

<dependency>
  <groupId>org.wiremock</groupId>
  <artifactId>wiremock-standalone</artifactId>
  <version>${wiremock.version}</version>
  <scope>test</scope>
</dependency>

O cliente precisa receber a base URL por configuração. No teste, use a porta aleatória do WireMock; em execução real, use a URL do ambiente. Nunca fixe localhost:8080 nem token real.

sports.provider.base-url=${SPORTS_PROVIDER_URL}
sports.provider.token=${SPORTS_PROVIDER_TOKEN}
sports.provider.connect-timeout=500ms
sports.provider.read-timeout=1500ms

4. Primeiro teste: caminho feliz

@Test
void deveMapearPartidaConcluida() {
  stubFor(get(urlEqualTo("/matches/42"))
    .withHeader("X-Api-Key", equalTo("token-de-teste"))
    .willReturn(okJson("""
      {"id":42,"status":"FINISHED","home":2,"away":1}
    """)));

  JogoExterno jogo = client.buscarJogo(42);

  assertThat(jogo.status()).isEqualTo(StatusJogo.ENCERRADO);
  verify(1, getRequestedFor(urlEqualTo("/matches/42")));
}

O teste possui duas asserções distintas: o objeto mapeado está correto e o request emitido respeita o contrato. Uma não substitui a outra.

5. Cenários de degradação

Timeout

Configure um atraso maior que o limite do cliente. Meça o tempo apenas com tolerância suficiente para não criar teste instável; a asserção principal é o tipo de resposta e a ausência de efeito colateral.

stubFor(get("/matches/42").willReturn(aResponse()
  .withFixedDelay(2000).withStatus(200)));

assertThatThrownBy(() -> client.buscarJogo(42))
  .isInstanceOf(IntegracaoIndisponivelException.class);
assertThat(jogoRepository.findByExternalId(42)).isEmpty();

Status 4xx e 5xx

4xx normalmente aponta problema permanente no request ou credencial e não deve ser repetido. 5xx pode ser transitório, mas retry só é seguro com limite, backoff e operação idempotente. O cliente traduz ambos para exceções do próprio domínio, sem devolver corpo externo ao usuário.

Corpo inválido

Status 200 não significa dado válido. Teste campo obrigatório ausente, enum desconhecido, tipo incompatível e JSON malformado. A aplicação deve rejeitar o conteúdo antes de alterar estado.

6. Segurança da chamada

  1. Mínimo privilégio: chave externa somente com as permissões necessárias.
  2. Configuração externa: segredo em variável/cofre, nunca no Git.
  3. Mascaramento: logs registram correlação, status e duração; nunca Authorization, cookie ou corpo sensível.
  4. Validação: limite de tamanho, content type, schema e valores de domínio.
  5. Erro neutro: cliente recebe código e mensagem próprios; stack trace fica fora da resposta.
Teste negativo obrigatório: force o provedor a devolver seu próprio token dentro do corpo de erro e prove que esse conteúdo não atravessa a API do Foot Fanatics.

Critérios de aceite

  • suíte executa offline e repete o mesmo resultado;
  • nenhuma credencial real aparece no código, fixture, relatório ou log;
  • cenários rodam no pipeline;
  • RTM liga requisito, risco, teste e execução;
  • README explica como executar localmente.
