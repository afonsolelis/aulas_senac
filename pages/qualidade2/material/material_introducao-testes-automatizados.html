Introdução a Testes Automatizados

Objetivos da aula

Transformar a primeira regra do Foot Fanatics em documentação executável.

  • Distinguir teste manual de verificação automatizada e escolher o nível adequado.
  • Estruturar testes em Arrange–Act–Assert e reconhecer propriedades de uma suíte confiável.
  • Escrever casos positivos e negativos com JUnit 5, isolando fronteiras com dublês.
  • Iniciar a matriz de rastreabilidade ligando requisito, risco, teste e evidência.

1. Por que automatizar?

Teste é uma atividade intelectual: alguém modela riscos, escolhe entradas e define um oráculo. Automação é a execução repetível dessa decisão. Ela reduz o custo da regressão, antecipa feedback e dá coragem para refatorar, mas não substitui exploração, crítica ou entendimento do usuário.

Manual

Descoberta, usabilidade, exploração e situações ainda instáveis. A pessoa adapta o caminho conforme aprende.

Automatizado

Regressão, regras críticas e combinações repetíveis. A máquina aplica sempre o mesmo critério.

Heurística: automatize verificações frequentes, determinísticas, valiosas e suficientemente estáveis. Não automatize uma interface descartável apenas porque é possível.

2. Níveis e pirâmide de testes

A pirâmide não define uma porcentagem universal; ela orienta o portfólio para feedback rápido na base e confiança sistêmica no topo.

Escolha o teste mais baixo que captura o risco sem perder o comportamento relevante. Duplicar o mesmo caso em todos os níveis aumenta manutenção sem aumentar proporcionalmente a confiança.

3. Anatomia e qualidade do teste

Arrange–Act–Assert

  1. Arrange: prepare somente o estado que explica o cenário.
  2. Act: execute uma ação de negócio.
  3. Assert: observe resultado, estado ou interação essencial.

Propriedades desejáveis

A suíte deve ser rápida, isolada, repetível, autoavaliável e escrita no momento oportuno. Falhas intermitentes ensinam a equipe a ignorar o vermelho; por isso não use internet, data atual, ordem global ou Thread.sleep() em teste unitário.

Teste de sanidade: altere ou remova a regra. Se o teste continuar verde, ele não protege aquilo que promete.

4. Caso Foot Fanatics — E1

RF-E1-01 — cadastrar conta

Com e-mail válido, senha forte e e-mail ainda não usado, o sistema cria uma conta ativa e persiste apenas o hash da senha. O cadastro deve ser rejeitado quando o e-mail já existe, é inválido ou a senha não atende à política.

CT-E1-03E-mail inválidoErro de validação; repositório não consultado

5. Implementação mínima

Mantenha a regra de aplicação dependente de portas. Assim o teste troca banco e codificador por dublês sem alterar o comportamento testado.

public class CadastroContaService {
  private final ContaRepository repositorio;
  private final CodificadorSenha codificador;

  public Conta cadastrar(CadastroConta cmd) {
    validar(cmd);
    if (repositorio.existePorEmail(cmd.email()))
      throw new EmailJaCadastradoException();
    var conta = Conta.ativa(cmd.email(), codificador.hash(cmd.senha()));
    return repositorio.salvar(conta);
  }
}

O exemplo omite detalhes de produção para destacar a fronteira testável. Validação, normalização de e-mail e política de senha precisam de decisões explícitas no projeto.

6. Testes com JUnit 5 e Mockito

@ExtendWith(MockitoExtension.class)
class CadastroContaServiceTest {
  @Mock ContaRepository repositorio;
  @Mock CodificadorSenha codificador;
  @InjectMocks CadastroContaService servico;

  @Test
  void dadoEmailNovo_quandoCadastrar_entaoSalvaContaAtiva() {
    var cmd = new CadastroConta("ana@email.com", "Senha#123");
    when(repositorio.existePorEmail(cmd.email())).thenReturn(false);
    when(codificador.hash(cmd.senha())).thenReturn("hash-seguro");

    var conta = servico.cadastrar(cmd);

    assertAll(
      () -> assertEquals(StatusConta.ATIVA, conta.getStatus()),
      () -> assertEquals("hash-seguro", conta.getSenhaHash())
    );
    verify(repositorio).salvar(conta);
  }
}

Teste negativo

@Test
void dadoEmailExistente_quandoCadastrar_entaoRejeitaSemSalvar() {
  var cmd = new CadastroConta("ana@email.com", "Senha#123");
  when(repositorio.existePorEmail(cmd.email())).thenReturn(true);

  var erro = assertThrows(EmailJaCadastradoException.class,
      () -> servico.cadastrar(cmd));

  assertEquals("CONTA_EMAIL_DUPLICADO", erro.getCodigo());
  verify(repositorio, never()).salvar(any());
}
Não superespecifique: verifique interações que representam obrigação de negócio. Não valide cada chamada privada ou detalhe de implementação.

7. Dublês de teste

  • Stub: fornece resposta programada.
  • Mock: permite verificar mensagens/interações esperadas.
  • Fake: implementação simplificada, como repositório em memória.
  • Spy: envolve objeto real e observa ou substitui parte do comportamento; use com cautela.

No teste unitário, banco, e-mail, relógio e serviço externo são fronteiras. A própria regra de cadastro não é simulada. Mais tarde, testes de integração provarão que adaptadores reais cumprem o contrato dessas portas.

8. Primeira matriz de rastreabilidade

Crie docs/RTM.md. O documento deve evoluir durante o semestre, não nascer completo no final.

| Requisito | Risco | Casos automatizados | Evidência | Status |
| RF-E1-01 | conta duplicada / senha exposta | CT-E1-01..04 | ./mvnw test | coberto |

A evidência não é um print isolado. O comando reprodutível, o arquivo de teste e o resultado versionado formam uma trilha auditável.

Prática guiada

  1. Criar CadastroContaService, ContaRepository e erros de domínio.
  2. Escrever CT-E1-01 a CT-E1-04 antes de ampliar o endpoint.
  3. Executar ./mvnw test e guardar o comando no README.
  4. Remover temporariamente uma validação e confirmar que um teste fica vermelho.
  5. Registrar RF-E1-01 na RTM e fazer um commit coerente.

Critérios de aceite

  • Quatro testes verdes, incluindo cenários negativos.
  • Suíte independe de rede, banco, data real e ordem.
  • Nomes comunicam contexto, ação e resultado.
  • A RTM liga requisito, risco, casos e evidência.

Síntese e autoavaliação

Automação é útil quando acelera aprendizado e reduz risco. Testes unitários dão feedback rápido; níveis maiores validam integrações e jornadas. AAA dá estrutura; oráculos claros dão significado; rastreabilidade transforma o resultado em evidência.
