Aula 09: TDD e BDD no projeto

Regras de aprovação e bloqueio guiadas por teste

Agenda da prática

Implementar as regras de aprovação de recurso restrito e de bloqueio por manutenção começando pelo exemplo: cenário BDD, teste vermelho, código mínimo, refatoração e rastreabilidade.

  2. Prompt 1 · cenários BDD (35 min)
  3. Prompt 2 · ciclos TDD (55 min)

21h05–22h45

  1. Prompt 2 · ciclos restantes (30 min)
  2. Prompt 3 · automação e RTM (45 min)
  3. Checagem na mesa (25 min)

Antes de abrir o agente

Pré-requisitos

  • Projeto compilando com ./mvnw -B verify e CI verde na main.
  • docs/rtm.md com os requisitos de aprovação e manutenção identificados.
  • Agente de código com acesso ao terminal aberto na raiz do repositório.

Uso do agente

  • Trabalhe numa branch da prática, nunca direto na main.
  • Leia o diff inteiro antes de aceitar a mudança proposta pelo agente.
  • Rode ./mvnw -B verify antes de cada commit e abra pull request no fim.
  • Não cole token, senha nem dado pessoal real no prompt.
Os prompts estão no material escrito, prontos para copiar. O projeto é o de cada equipe, o sistema de Organização de Recursos.
Prompt 1 de 335 min

Cenários BDD antes do código

Atue como analista de qualidade do sistema de Organização de Recursos (Java 21, Spring Boot 3). Você pode usar o terminal (bash), com ls, find, grep e cat, para ler docs/prd.md, docs/rtm.md e o código das reservas. Não altere código nesta etapa. Escreva em docs/testes/bdd-aprovacao-bloqueio.md os cenários Dado/Quando/Então para quatro regras: recurso restrito exige aprovação de um Responsável; Solicitante não aprova a própria reserva; recurso em manutenção não pode ser reservado; reserva só muda de estado pelas transições SOLICITADA → APROVADA → EM_USO → CONCLUÍDA e pelas alternativas rejeitada, cancelada e não compareceu. Para a manutenção, monte uma tabela de exemplos com as fronteiras do período: reserva que termina exatamente no início, que começa exatamente no fim e que cruza um segundo. Quando o PRD não decidir uma fronteira, registre a pergunta em aberto em vez de inventar a política. Liste no fim quais cenários viram teste de unidade e quais viram teste de API.

Antes de aceitar: Cada cenário tem um único Quando e um Então observável; as perguntas em aberto foram levadas ao grupo.
Prompt 2 de 385 min

Red, Green e Refactor com evidência

Atue como desenvolvedor em par praticando TDD estrito no sistema de Organização de Recursos. Você pode usar o terminal (bash) e o git. Leia docs/testes/bdd-aprovacao-bloqueio.md e trate um cenário por vez. Para cada um: escreva um único teste JUnit 5 com nome que descreva condição e resultado, rode ./mvnw -B test e mostre que ele falha pela razão esperada (falha de asserção, não erro de compilação ou de configuração); faça commit test(red): <cenário>. Depois implemente o mínimo para a suíte inteira ficar verde e faça commit feat(green): <cenário>. Só então refatore nomes e duplicação, sem mudar comportamento, e faça commit refactor: <motivo>. Injete Clock nas regras de manutenção; nunca use Instant.now() escondido nem Thread.sleep. É proibido escrever vários testes de uma vez, alterar um teste para ele passar ou pular o vermelho. Registre em docs/testes/evidencia-tdd.md uma tabela cenário → commit red → commit green → commit refactor → trecho da saída do teste.

Antes de aceitar: O histórico mostra o vermelho antes do verde em todos os cenários; nenhum teste foi enfraquecido.
Prompt 3 de 345 min

Cenários executáveis ligados à RTM

Atue como engenheiro de qualidade. Você pode usar o terminal (bash), o git e o gh. Transforme os cenários de API de docs/testes/bdd-aprovacao-bloqueio.md em especificação executável com Cucumber-JVM (cucumber-java e cucumber-junit-platform-engine), com o arquivo src/test/resources/features/aprovacao-bloqueio.feature e steps que chamam a API por MockMvc com tokens de cada perfil. Use as mesmas palavras do cenário escrito, sem reescrever a regra. Garanta que ./mvnw -B verify executa as features no CI e que o gate do JaCoCo continua passando. Atualize docs/rtm.md ligando cada requisito ao cenário, ao teste ou feature (caminho e nome) e ao commit. Abra um pull request com a descrição dos ciclos e confira o Quality Gate do SonarCloud; trate cada apontamento corrigindo ou justificando, nunca baixando a meta.

Antes de aceitar: As features rodam no CI; cada linha nova da RTM abre um arquivo que existe.
Entregável da Aula 09

Pull request com os commits red, green e refactor, a feature executável, docs/testes/evidencia-tdd.md e a RTM atualizada.

O que confiro na mesa

  • Abro o histórico e procuro o commit vermelho de um cenário à sua escolha.
  • Peço para quebrar a regra de manutenção e mostrar qual teste falha.
  • Escolho uma linha da RTM e sigo até o teste.
