Semana 34 · hoje
A técnica

Você já sabe o que testar. Falta saber de onde olhar.

E hoje o caso de teste deixa de ser exercício: ele passa a ter um software com nome.

Toda técnica de teste nasce de uma única pergunta:

Você pode ver o código?

Não

Você testa o contrato.
Caixa preta.

Sim

Você testa o caminho.
Caixa branca.

Não é sobre qual é melhor. É sobre qual defeito cada uma consegue enxergar.

Caixa Preta · black box

Testar pelo contrato

Você conhece a especificação. O código é opaco — e isso é proposital.

Você tem
  • Entradas válidas e inválidas
  • Saídas esperadas
  • Requisitos e regras de negócio
  • O contrato da API
Você não tem
  • O código-fonte
  • Os ramos do if
  • A estrutura interna
  • Qualquer desculpa técnica
Pega bem
  • Requisito mal implementado
  • Regra de negócio errada
  • Validação ausente
  • Funcionalidade que falta
É o olhar de quem usa o sistema. Inclusive o olhar de quem ataca.
Caixa Branca · white box

Testar pelo caminho

Você abre o código e pergunta: por quais linhas eu ainda não passei?

Você tem
  • O código-fonte
  • O fluxo de controle
  • Cada condição e ramo
  • Relatório de cobertura
Você perde
  • A visão do usuário
  • O requisito que ninguém escreveu
  • A integração entre partes
  • O viés: você testa o que escreveu
Pega bem
  • Ramo nunca executado
  • Código morto
  • Condição impossível
  • Erro de lógica fino
É o olhar de quem escreve o sistema. Por isso é o olhar mais fácil de se enganar.

Lado a lado

Caixa Preta Caixa Branca

Quem costuma fazer QA, analista de teste, cliente A pessoa que desenvolve

No Foot Fanatics POST /auth/login devolve 401 com senha errada? O ramo "token expirado" do filtro chegou a rodar?
Os pontos cegos são complementares. Por isso nenhuma equipe séria escolhe só uma.

Cobertura: três réguas diferentes

O mesmo código, medido de três formas — com resultados bem diferentes.

if (token != null && !token.expirado()) { liberarAcesso(); }
Comando (linha)

Toda linha foi executada ao menos uma vez.

1 teste basta Token válido → 100%.

Ramo (decisão)

O if foi verdadeiro e falso.

2 testes Precisa do caso que não libera.

Condição

Cada operando testado V e F isoladamente.

3 testes Token nulo e token expirado são bugs diferentes.

Um relatório dizendo "100% de cobertura" sem dizer de quê não significa nada.

Caixa preta não é chutar entrada

Existem técnicas com nome, e elas reduzem drasticamente o número de testes.

Partição de equivalência

Entradas que o sistema trata do mesmo jeito formam uma classe. Teste uma por classe.

Plano de assinatura: free · premium · inválido.

Valor limite

O defeito mora na fronteira. Teste no limite, logo antes e logo depois.

Sessão de 30 min: 29:59 · 30:00 · 30:01.

Tabela de decisão

Quando várias condições se combinam, monte a tabela e cubra cada regra.

Logado? × Assinante? × Conteúdo pago? → libera ou 403.

Bem aplicadas, transformam milhares de entradas possíveis em dezenas de testes que importam.
Caixa Cinza · grey box

O que a gente faz de verdade

Teste de API é quase sempre caixa cinza: você chama pelo contrato, mas sabe o que tem atrás.

No Foot Fanatics você vai fazer exatamente isto:

  • Chamar POST /auth/login como um cliente qualquer — caixa preta.
  • Mas escolher os casos sabendo que existe um filtro de sessão com ramo de expiração — caixa branca.
  • E conferir no banco que a sessão foi mesmo invalidada — conhecimento interno.
  • O relatório de cobertura te diz o que ainda não foi tocado por nenhum desses testes.
Na prática você não escolhe uma caixa. Você escolhe o que quer enxergar naquele teste.

A armadilha dos 100%

Cobertura mede o que foi executado.

Não mede o que foi verificado.

O teste sem asserção

Chama o método, não verifica nada, passa sempre. E soma 100% de cobertura naquela linha. É o defeito mais comum em projeto com meta de cobertura.

O requisito ausente

Se ninguém implementou "bloquear conta após 5 tentativas", não existe linha para cobrir. Cobertura: 100%. Sistema: vulnerável.

Cobertura é bom para achar o que falta testar. É péssimo como nota.
Parte 2 · Mão na massa

Chega de exemplo genérico.

A partir de hoje, todo conceito desta disciplina tem um endereço.

Foot Fanatics

O case do semestre

Uma API de conteúdo esportivo — mesma espinha dorsal do remo-api — com assinatura.

O que herdamos do remo-api
  • API REST de conteúdo de futebol
  • Clubes, jogos, resultados
  • Leitura pública, dados estruturados
  • Java + Spring Boot
O que é novo aqui
  • Conta — cadastro, credencial, perfil
  • Assinatura — plano free e premium
  • Sessão — login, token, expiração, logout
  • Acesso — conteúdo que só assinante vê
E nós vamos codificar isso em todas as etapas — da semana 34 até a entrega final.

Por que assinatura, e não só CRUD

Porque conta, acesso e sessão são o terreno mais rico que existe para qualidade.

Tem tempo

Token expira. Assinatura vence. Valor limite deixa de ser exercício e vira bug real.

Tem risco

Falha de autorização não é bug de conforto: é vazamento. Caixa preta agressiva importa.

Tem ramo

Logado × assinante × conteúdo pago gera combinação real. Cobertura de ramo fica visível.

Tem estado

Sessão é estado compartilhado. Concorrência, carga e JMeter ganham sentido.

Cada tema das próximas semanas tem um alvo concreto dentro deste sistema.

Escopos iniciais

Quatro. Nem um a mais. Hoje só definimos — não implementamos.

E1Identidade & Conta

Cadastro, credencial, perfil, recuperação. É a porta de entrada — e a primeira superfície de ataque.

E2Sessão & Acesso

Login, emissão de token, expiração, renovação, logout. Quem é você agora.

E3Assinatura

Planos free e premium, vigência, upgrade e cancelamento. O que você pode.

E4Conteúdo

Clubes, jogos e matérias. Parte pública, parte só para assinante. O núcleo herdado do remo-api.

Fora do escopo: pagamento real, app mobile, notificação push, painel administrativo.

Passo 1

Instalar o AIOX

mkdir foot-fanatics && cd foot-fanatics && git init
npx aiox-core@latest install
O que o instalador pergunta

Quais squads instalar. Para hoje, o squad de development já basta.

O que aparece depois

A pasta .aiox-core/ com os agentes: pm, po, architect, dev, qa, devops.

Requisito: Node.js instalado. Confira com node --version.

Passo 2

Java + Spring Boot

Java 21 (LTS)
curl -s "https://get.sdkman.io" | bash
sdk list java
sdk install java 21.0.5-tem

Use a versão 21 que aparecer no sdk list da sua máquina. Confira com java -version.

Projeto em start.spring.io
  • Maven · Java 21 · Spring Boot 3.x estável
  • Group br.senac · Artifact foot-fanatics

Dependências:

Spring Web · Spring Security · Spring Data JPA · Validation · PostgreSQL Driver · Testcontainers

./mvnw test && ./mvnw spring-boot:run
Critério do passo 2: a suíte roda verde com zero teste seu. Esse é o marco zero da cobertura.

Passo 4 · o entregável de hoje

Criar as personas

A única seção do PRD que sai desta aula preenchida.

Torcedor casual

plano free

Quer resultado e escalação rápido, no celular, sem criar conta se puder evitar. Testa: o limite entre público e pago.

Torcedor assinante

plano premium

Paga por análise, estatística e conteúdo exclusivo. Usa em vários dispositivos. Testa: sessão, renovação e vigência.

Editor de conteúdo

operação

Publica matérias e marca o que é exclusivo. Testa: autorização — o que acontece se ele acessar sem permissão.

Cada persona escrita com objetivo, contexto e frustração. Sem isso ela não gera caso de teste.
