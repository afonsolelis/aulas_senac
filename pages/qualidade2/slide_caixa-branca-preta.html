Semana 34 · hoje
A técnica

Você já sabe o que testar. Falta saber de onde olhar.

E hoje o caso de teste deixa de ser exercício: ele passa a ter um software com nome.

Toda técnica de teste nasce de uma única pergunta:

Você pode ver o código?

Não

Você testa o contrato.
Caixa preta.

Sim

Você testa o caminho.
Caixa branca.

Não é sobre qual é melhor. É sobre qual defeito cada uma consegue enxergar.

Caixa Preta · black box

Testar pelo contrato

Você conhece a especificação. O código é opaco — e isso é proposital.

Você tem
  • Entradas válidas e inválidas
  • Saídas esperadas
  • Requisitos e regras de negócio
  • O contrato da API
Você não tem
  • O código-fonte
  • Os ramos do if
  • A estrutura interna
  • Qualquer desculpa técnica
Pega bem
  • Requisito mal implementado
  • Regra de negócio errada
  • Validação ausente
  • Funcionalidade que falta
É o olhar de quem usa o sistema. Inclusive o olhar de quem ataca.
Caixa preta · em código

Tudo o que você recebeu foi o contrato

Foot Fanatics · E2 Sessão & Acesso. Nenhuma linha de implementação à vista.

# acesso.py — a especificacao
#
# pode_assistir(sessao, conteudo) -> str
#   "LIBERADO"
#       sessao valida e plano compativel
#   "SESSAO_INVALIDA"
#       sem sessao ou sessao expirada
#   "ASSINATURA_NECESSARIA"
#       conteudo premium e plano free

O código existe, mas você não abre.

# test_acesso.py
def test_assinante_ve_conteudo_premium():
    s = Sessao(plano="premium", idade_s=10)
    assert pode_assistir(s, Conteudo(premium=True)) == "LIBERADO"

def test_free_nao_ve_conteudo_premium():
    s = Sessao(plano="free", idade_s=10)
    assert pode_assistir(s, Conteudo(premium=True)) == "ASSINATURA_NECESSARIA"

def test_sem_sessao_nao_ve_nada():
    assert pode_assistir(None, Conteudo(premium=False)) == "SESSAO_INVALIDA"
3 testes, 3 requisitos cobertos, tudo verde. E você não faz ideia de quanto do código rodou.
Caixa Branca · white box

Testar pelo caminho

Você abre o código e pergunta: por quais linhas eu ainda não passei?

Você tem
  • O código-fonte
  • O fluxo de controle
  • Cada condição e ramo
  • Relatório de cobertura
Você perde
  • A visão do usuário
  • O requisito que ninguém escreveu
  • A integração entre partes
  • O viés: você testa o que escreveu
Pega bem
  • Ramo nunca executado
  • Código morto
  • Condição impossível
  • Erro de lógica fino
É o olhar de quem escreve o sistema. Por isso é o olhar mais fácil de se enganar.

Os mesmos 3 testes, agora com o fonte aberto

Cobertura: três réguas diferentes

O mesmo código, medido de três formas — com resultados bem diferentes.

if (token != null && !token.expirado()) { liberarAcesso(); }
Comando (linha)

Toda linha foi executada ao menos uma vez.

1 teste basta Token válido → 100%.

Ramo (decisão)

O if foi verdadeiro e falso.

2 testes Precisa do caso que não libera.

Condição

Cada operando testado V e F isoladamente.

3 testes Token nulo e token expirado são bugs diferentes.

Um relatório dizendo "100% de cobertura" sem dizer de quê não significa nada.

As três réguas, com o pytest na mão

Uma linha de código. Três suítes diferentes. Três números diferentes.

def liberar(token):
    if token is not None and not token.expirado:   # 2 condicoes, 1 decisao
        conceder_acesso()
1 Comando
# token valido
liberar(Token(expirado=False))

--cov: 100%. E o acesso indevido nunca foi testado.

2 Ramo
liberar(Token(expirado=False))
liberar(Token(expirado=True))

--cov-branch: agora o if foi V e F.

3 Condição
liberar(Token(expirado=False))
liberar(Token(expirado=True))
liberar(None)

Token nulo e token expirado são bugs diferentes.

pytest --cov mede comando. --cov-branch mede ramo. Nenhum dos dois mede condição.

Caixa preta não é chutar entrada

Existem técnicas com nome, e elas reduzem drasticamente o número de testes.

Partição de equivalência

Entradas que o sistema trata do mesmo jeito formam uma classe. Teste uma por classe.

Plano de assinatura: free · premium · inválido.

Valor limite

O defeito mora na fronteira. Teste no limite, logo antes e logo depois.

Sessão de 30 min: 29:59 · 30:00 · 30:01.

Tabela de decisão

Quando várias condições se combinam, monte a tabela e cubra cada regra.

Logado? × Assinante? × Conteúdo pago? → libera ou 403.

Bem aplicadas, transformam milhares de entradas possíveis em dezenas de testes que importam.
Técnica 1 · Partição de equivalência

Um representante por classe

Se o sistema trata dois valores do mesmo jeito, testar os dois é desperdício.

import pytest

@pytest.mark.parametrize("plano, esperado", [
    ("free",    "ASSINATURA_NECESSARIA"),   # classe 1: sem direito
    ("premium", "LIBERADO"),                # classe 2: com direito
    ("pirata",  "PLANO_INVALIDO"),          # classe 3: entrada invalida
])
def test_plano_decide_acesso_a_conteudo_premium(plano, esperado):
    sessao = Sessao(plano=plano, idade_s=10)
    assert pode_assistir(sessao, Conteudo(premium=True)) == esperado
3 testes cobrem qualquer string de plano que exista hoje ou amanhã.
A classe inválida é a que mais gente esquece — e a que o atacante usa.
Técnica 2 · Análise de valor limite

O defeito mora na fronteira

Regra: a sessão vale 30 minutos. Aos 1800s ela ainda vale.

@pytest.mark.parametrize("idade_s, esperado", [
    (1799, "LIBERADO"),           # logo antes do limite
    (1800, "LIBERADO"),           # NO limite — o caso que pega o bug
    (1801, "SESSAO_INVALIDA"),    # logo depois
])
def test_fronteira_de_expiracao_da_sessao(idade_s, esperado):
    sessao = Sessao(plano="premium", idade_s=idade_s)
    assert pode_assistir(sessao, Conteudo(premium=False)) == esperado
- if sessao.idade_s >= 1800:   # errado
+ if sessao.idade_s >  1800:   # certo
O caso 1799 passa nas duas versões. O caso 1801 também. Só o 1800 denuncia o >=.
Técnica 3 · Tabela de decisão

3 condições, 8 combinações, 4 regras

O — é um don't care: colapsa duas combinações numa regra só.

REGRAS = [
    # logado, assinante, premium, esperado
    (False, False, False, "SESSAO_INVALIDA"),
    (True,  False, False, "LIBERADO"),
    (True,  False, True,  "ASSINATURA_NECESSARIA"),
    (True,  True,  True,  "LIBERADO"),
]

@pytest.mark.parametrize("logado, assinante, premium, esperado", REGRAS)
def test_matriz_de_acesso(logado, assinante, premium, esperado):
    sessao = Sessao(plano="premium" if assinante else "free",
                    idade_s=10) if logado else None
    assert pode_assistir(sessao, Conteudo(premium=premium)) == esperado
A tabela vira a lista de casos. A lista vira parametrize. O parametrize vira evidência.
Caixa Cinza · grey box

O que a gente faz de verdade

Teste de API é quase sempre caixa cinza: você chama pelo contrato, mas sabe o que tem atrás.

No Foot Fanatics você vai fazer exatamente isto:

  • Chamar POST /auth/login como um cliente qualquer — caixa preta.
  • Mas escolher os casos sabendo que existe um filtro de sessão com ramo de expiração — caixa branca.
  • E conferir no banco que a sessão foi mesmo invalidada — conhecimento interno.
  • O relatório de cobertura te diz o que ainda não foi tocado por nenhum desses testes.
Na prática você não escolhe uma caixa. Você escolhe o que quer enxergar naquele teste.

A armadilha dos 100%

Cobertura mede o que foi executado.

Não mede o que foi verificado.

O teste sem asserção

Chama o método, não verifica nada, passa sempre. E soma 100% de cobertura naquela linha. É o defeito mais comum em projeto com meta de cobertura.

O requisito ausente

Se ninguém implementou "bloquear conta após 5 tentativas", não existe linha para cobrir. Cobertura: 100%. Sistema: vulnerável.

Cobertura é bom para achar o que falta testar. É péssimo como nota.

Como provar que o teste protege alguma coisa

A cobertura não responde isso. Quebrar a regra de propósito, responde.

O teste que soma 100% e não protege nada
def test_pode_assistir():
    sessao = Sessao(plano="free", idade_s=10)
    pode_assistir(sessao, Conteudo(premium=True))
    # fim. nenhum assert.

1 passed · acesso.py 100%
O teste de mutação na unha
# sabote a regra e rode a suite
- if conteudo.premium and sessao.plano != "premium":
+ if False:

1 passed  → o teste era decoracao
1 failed  → o teste era protecao
Regra da casa para o semestre inteiro: apague a regra, rode a suíte. Se não ficar vermelha, o teste não existe.

Prática em sala · entregável de hoje

Elicitação de requisitos com IA

As personas já existem. Agora elas viram requisito — e requisito que dá para testar.

  1. Partir das três personas escritas na aula do ATAM e, para cada uma, levantar candidatos a requisito com apoio de IA. A IA gera volume; a turma decide o que entra.
  2. Separar cada item em RF (o que o sistema faz) e RNF (com que qualidade faz).
  3. Reescrever todo RNF de forma medível: "rápido" não é requisito; p95 < 2s é.
  4. Amarrar cada requisito ao escopo que o originou — E1 Conta, E2 Sessão, E3 Assinatura, E4 Conteúdo.
  5. Numerar tudo (RF-01, RNF-01) e registrar no docs/prd.md.
Fim da aula: RF e RNF numerados, medíveis e ligados ao escopo que os originou.
