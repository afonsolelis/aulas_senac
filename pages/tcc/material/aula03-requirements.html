Aula 03

Engenharia de Requisitos

O Guia Definitivo para definir O QUE seu sistema vai fazer antes de escrever uma linha de código.

"A parte mais difícil de construir um sistema de software é decidir precisamente o que construir."
- Fred Brooks

Neste guia, você aprenderá a traduzir ideias vagas em especificações técnicas precisas, garantindo que seu TCC resolva o problema certo.

Capítulo 1: O Que é Engenharia de Requisitos?

Engenharia de Requisitos não é burocracia. É o processo de descobrir, analisar, documentar e verificar os serviços que o sistema deve fornecer e as restrições sob as quais deve operar.

Sem Requisitos
  • Você constrói a coisa errada.
  • O escopo explode (feature creep).
  • A banca reprova por falta de clareza.
  • O código vira uma "colcha de retalhos".
Com Requisitos
  • Escopo definido e "fechado".
  • Critérios claros de sucesso.
  • Base sólida para a arquitetura.
  • Testes fáceis de planejar.

Capítulo 2: Requisitos Funcionais (RF)

O que o sistema FAZ

Requisitos Funcionais descrevem as **funções** do software. São verborrágicos, diretos e testáveis. Devem descrever o comportamento do sistema em resposta a entradas.

Como Escrever (Sintaxe Recomendada)

[RF01] - Nome Curto: O sistema deve permitir que o [ATOR] realize [AÇÃO] para [OBJETIVO].

Exemplos:

  • [RF001] - Cadastro de Usuário: O sistema deve permitir que visitantes se cadastrem informando e-mail, senha e nome completo.
  • [RF002] - Geração de Relatório: O sistema deve gerar um PDF com o histórico de vendas do mês selecionado.
  • [RF003] - Alerta de Estoque: O sistema deve enviar um e-mail ao gerente quando um produto atingir o estoque mínimo.
Erro Comum: Misturar "como" com "o que".
Errado: "O sistema deve usar um botão azul para salvar." (Isso é design/interface)
Certo: "O sistema deve permitir salvar as alterações do perfil."

Capítulo 3: Requisitos Não-Funcionais (RNF)

Como o sistema se COMPORTA (Qualidade)

Definem atributos de qualidade como desempenho, segurança, confiabilidade e usabilidade. São os "adjetivos" do sistema.

Categoria Descrição Exemplo (TCC)
Desempenho Velocidade, latência, throughput. [RNF01] O sistema deve carregar a dashboard em menos de 2 segundos em conexões 4G.
Segurança Acesso, criptografia, proteção. [RNF02] As senhas devem ser armazenadas com hash BCrypt.
Disponibilidade Uptime, recuperação de falhas. [RNF03] O sistema deve estar disponível 99.5% do tempo no horário comercial.
Portabilidade Onde roda (OS, Navegadores). [RNF04] A aplicação web deve ser responsiva e funcionar em Chrome, Firefox e Safari.

Capítulo 4: Histórias de Usuário & Casos de Uso

Ágil vs. Tradicional (Escolha sua arma)
Histórias de Usuário (Agile)

Focadas no valor para o usuário. Ótimas para TCCs de desenvolvimento ágil/apps.

Template:
"Como [ATOR], eu quero [AÇÃO], para que [VALOR/BENEFÍCIO]."

Ex: "Como aluno, eu quero visualizar minhas notas, para monitorar meu desempenho."

Casos de Uso (UML/Tradicional)

Detalhados, focados na interação passo-a-passo. Ótimos para sistemas complexos/bancários.

  • Ator: Quem interage.
  • Fluxo Principal: O caminho feliz.
  • Fluxos Alternativos: O que acontece se algo der errado (ex: senha incorreta).

Capítulo 5: MVP (Minimum Viable Product)

Corte o que não é essencial

O maior erro em TCC é querer "abraçar o mundo". Defina o MVP: a menor versão do produto que ainda resolve o problema central e prova sua tese.

A Técnica MoSCoW

Use para priorizar seus requisitos:

  • Must Have (Deve ter): Se não tiver, o sistema não funciona. (Faz parte do MVP)
  • Should Have (Deveria ter): Importante, mas pode esperar uma v2.
  • Could Have (Poderia ter): Desejável, "nice to have".
  • Won't Have (Não terá): Fora do escopo por enquanto.

Para o TCC1, foque 100% no "Must Have"!
